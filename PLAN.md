# PLAN — Фаза 12: портфель объектов (ADR-0028)

> Источник задачи — `docs/DEV_STATE.md`: Фаза 9 закрыта (ADR-0027),
> владелец продукта выбрал Фазу 12 следующей. Решения приняты в интервью
> 2026-08-24 и фиксируются в **ADR-0028 до кода** (правило `CLAUDE.md`).
>
> **Ревизия 2** — после состязательного разбора. Главное изменение:
> деньги портфеля считаются **в том же проходе по договорам**, что и
> существующие блоки, а не отдельным запросом. Первая редакция
> предлагала вторую независимую агрегацию — это давало ровно ту ловушку,
> ради ухода от которой затевалось: два места считают одно и то же и
> однажды разойдутся.

## 1. Что делаем

`/reports` перестаёт быть плоским списком по темам: сверху появляется
блок «По объектам» — строка на каждый объект собственника, включая
простаивающие, с доходом, долгом, статусом аренды, заявками и деньгами
на подходе. Группировка по городам — та, что уже сделана в Фазе 8.

## 2. Что уже есть (не переписывать)

- `ReportsService.getLandlordSummary(landlordId)` уже агрегирует по всем
  договорам собственника: доход по подтверждённым платежам с разбивкой
  по месяцам, задолженность с пенями, просрочки, сроки договоров.
- `GET /reports/summary`, фронт `app/reports/page.tsx` (195 строк).
- Группировка по городам на фронте — Фаза 8, `app/properties/page.tsx`.
- Услуги из заявок с `billedAt`/`sourceRequestId` и знаком по
  плательщику — Фаза 6 (ADR-0025).

**Чего нет:**

1. Объекты в отчётах не видны как сущности — агрегация идёт по
   договорам, поэтому **объект без договора не появляется нигде**.
2. Нет агрегата по заявкам на обслуживание.
3. Нет суммы согласованных, но ещё не выставленных услуг.

## 3. Решения интервью (входные данные, не пересматривать)

| № | Решение |
|---|---------|
| Р1 | Блок «По объектам» добавляется **сверху** `/reports`; существующие тематические секции остаются ниже без изменений |
| Р2 | В блок попадают **все** объекты собственника, включая простаивающие — статус «Свободен», нулевой доход |
| Р3 | Агрегат по заявкам — счётчики `open`/`in_progress` **и** сумма согласованных, но не выставленных услуг («деньги на подходе») |

### Не в скоупе

- Фаза 7 (карта) — ждёт CEO; OCR (ADR-0008) — отдельный разговор.
- Фазы 10 и 11.
- Экспорт, графики, фильтры по периодам.
- Переработка существующих секций `/reports` (Р1).

## 4. Backend

### B1. Деньги портфеля считаются в существующем проходе

`getLandlordSummary` уже перебирает договоры и их счета, вычисляя доход и
задолженность. **Копилки по объектам заводятся в этом же цикле**, а не
вторым запросом:

- в существующий `lease.findMany` добавить в выборку `propertyId`
  (скалярное поле, отношение `property` уже подключено);
- завести `Map<propertyId, { income, outstanding }>` и наполнять её
  **теми же выражениями и в тех же ветках**, где сейчас растут
  `incomeTotal` и `outstandingTotal`.

Почему так, а не отдельным запросом: любая вторая реализация «дохода» и
«долга» однажды разойдётся с первой. Здесь расхождение невозможно по
построению — число берётся из той же строки кода.

**Пеня считается ровно тем выражением, что уже стоит в отчёте:**

```ts
const penalty = bill.penaltyWaived ? 0 : computeAccruedPenalty({...});
```

Прямой вызов `computeAccruedPenalty` без внешней проверки `penaltyWaived`
дал бы другое число: внутри функции прощённая пеня возвращается как
`penaltyWaivedAmount`, а отчёт исторически показывает по ней ноль. Это
расхождение существует в коде и **в этой фазе не исправляется** — Фаза 12
обязана лишь не создать второго поведения. Записать в ADR как известное
и намеренно не тронутое.

### B2. Остальные данные — три узких запроса

Одним `include` их не достать: `Service` висит на `Property`, а не на
`Lease`, а считать заявки через двойную вложенность неудобно.

1. **Объекты** (нужны все, включая без договоров):
   `property.findMany({ where: { ownerId: landlordId }, select: { id, address, city }, orderBy: [{ city: 'asc' }, { street: 'asc' }, { house: 'asc' }, { createdAt: 'desc' }] })`.
   `NULL` при `ASC` в Postgres уходит в конец — объекты без города
   окажутся последними, как в `properties.service.ts` (Фаза 8).
2. **Заявки** — агрегатом, а не выборкой строк:
   `maintenanceRequest.groupBy({ by: ['leaseId', 'status'], where: { status: { in: [open, in_progress] }, lease: { landlordId } }, _count: { _all: true } })`.
   `leaseId → propertyId` берётся из уже загруженных договоров.
3. **Услуги** — фильтр на стороне БД:
   ```ts
   service.findMany({
     where: {
       property: { ownerId: landlordId },
       serviceType: one_time,
       billedAt: null,
       // Не только объект мой, но и заявка — по моему договору: иначе
       // объект с чужим договором получил бы «деньги на подходе»
       // вопреки правилу §B4 (там обещаны нули).
       sourceRequest: { lease: { landlordId } },
     },
     select: { propertyId: true, price: true, payer: true },
   })
   ```
   Фильтр по `sourceRequest` заодно заменяет `sourceRequestId: { not: null }`:
   услуга без заявки этому условию не удовлетворяет.

Широких `include` не заводить: существующий запрос по договорам и так
тянет все счета со строками, второй такой же был бы лишним.

### B3. Единый помощник знака по плательщику

Знак сейчас вычисляется внутри приватного `billServiceIntoBill`
(`billing.service.ts`). Отчёту нужен тот же расчёт, дублировать нельзя.
Вынести в `billing.util.ts`:

```ts
// Доля арендатора по плательщику (ADR-0025): tenant — вся сумма,
// split — половина, owner — вычет со знаком минус. Единственное место
// расчёта: им пользуются и выставление услуги, и портфельный отчёт.
export function tenantShareForPayer(price: unknown, payer: SettlementPayer): number;
```

**Возвращает `number`, округлённый `round2`** — ровно то, что делает
сегодняшний инлайн-код (`toNumber` + `round2`). Не `Decimal`: денежные
вычисления в этом проекте ведутся на `number` с округлением до копеек,
так написано в шапке `billing.util.ts`, и вводить второй стиль в этой
фазе незачем. `billServiceIntoBill` переходит на помощник — поведение
обязано остаться прежним, тесты Фазы 6 должны пройти без правок.

### B4. Принадлежность договоров

Старый блок берёт договоры по `Lease.landlordId`, объекты берутся по
`Property.ownerId`. Схема равенства этих полей не гарантирует.
**Копилки наполняются только из договоров, попавших в существующий
запрос** (то есть по `landlordId`) — значит числа блоков и портфеля
согласованы. Объект, у которого есть только чужой договор, попадёт в
список со статусом «Свободен» и нулями: это честнее, чем показать чужие
деньги.

### B5. Контракт ответа

```ts
export type PortfolioStatus = 'rented' | 'pending' | 'vacant';

export interface PortfolioEntry {
  propertyId: string;
  address: string;               // кеш из ADR-0026
  city: string | null;           // для группировки на фронте
  status: PortfolioStatus;
  tenantEmail: string | null;    // арендатор действующего договора
  monthlyRent: number | null;    // аренда действующего договора
  incomeTotal: number;
  outstandingTotal: number;
  openRequests: number;
  inProgressRequests: number;
  pendingServicesAmount: number; // может быть < 0
}

export interface PortfolioTotals {
  properties: number;
  rented: number;
  pending: number;               // «ожидают арендатора»
  vacant: number;
  activeRequests: number;        // open + in_progress по всем объектам
  pendingServicesAmount: number;
}
```

В `LandlordSummary` добавляется
`portfolio: { totals: PortfolioTotals; entries: PortfolioEntry[] }`.
Существующие поля не трогаются.

**Правила:**

- `status`: есть договор `active` → `rented`; иначе есть `draft`/`sent` →
  `pending`; иначе → `vacant`.
- **Действующий договор выбирается детерминированно:** среди `active` —
  с наибольшим `startDate`. Схема «не более одного active» не
  обеспечивает уникальным индексом, и молчаливое «какой попадётся»
  недопустимо для денег на экране.
- `tenantEmail`, `monthlyRent` — из этого договора; иначе `null`.
- `incomeTotal`, `outstandingTotal` — из копилок §B1.
- `openRequests`/`inProgressRequests` — из §B2.2, считаются **по всем
  договорам объекта, включая расторгнутые**: незакрытая заявка не
  перестаёт быть работой оттого, что договор кончился.
- `pendingServicesAmount` — сумма `tenantShareForPayer(price, payer)` по
  §B2.3, округление итога `round2`.
- `totals.properties === rented + pending + vacant` — закрепить тестом.

### B6. Тесты (backend)

**Меняется намеренно:** `reports.service.spec.ts` — в мок Prisma
добавляются `property.findMany`, `maintenanceRequest.groupBy` и
`service.findMany` (иначе существующие сценарии просто упадут на
отсутствующем моке). Существующие assertions и смысл сценариев не
трогать; новых ослаблений нет.

1. Объект без договоров → `vacant`, нули, но в `entries` присутствует.
2. `draft` → `pending`; `sent` → `pending`.
3. `active` → `rented`, `tenantEmail` и `monthlyRent` заполнены.
4. Только `terminated` → `vacant`, доход прошлых периодов сохранён.
5. **Числа портфеля совпадают с тематическими блоками** на одних данных:
   сумма `incomeTotal` по объектам равна `income.total`, сумма
   `outstandingTotal` равна `outstanding.totalDue`.
6. **Прощённая пеня:** счёт с `penaltyWaived = true` и
   `penaltyWaivedAmount > 0` даёт в долге объекта ноль пени — так же,
   как в существующем блоке.
7. Два `active`-договора у объекта → берётся с наибольшим `startDate`.
8. Заявки считаются по всем договорам объекта, включая расторгнутые;
   `resolved` не считается.
9. `pendingServicesAmount`: `tenant` → `+price`, `split` → `+price/2`,
   `owner` → `−price`.
10. Выставленная услуга (`billedAt` не `null`) и ручная
    (`sourceRequestId = null`) в сумму не входят.
11. `totals.properties === rented + pending + vacant`;
    `totals.activeRequests` равен сумме двух счётчиков по объектам.
12. Сортировка: объекты без города — в конце.
13. Чужие объекты в выдачу не попадают; объект с чужим договором →
    `vacant` с нулями (§B4).
14. `tenantShareForPayer`: три плательщика и нечётная копейка при `split`
    (`10.01` → `5.01`, как в ADR-0025).

- строка сводки: «Объектов N · сдано N · свободно N», и «ожидают
  арендатора N» — только если больше нуля; рядом «Заявок в работе N» и
  «Деньги на подходе: X ₽» — каждое только если не ноль;
- список объектов, **сгруппированный по городам** тем же приёмом, что в
  `app/properties/page.tsx`: заголовки показываются, если групп больше
  одной; объекты без города — последняя группа «Город не указан»;
- строка объекта: адрес (ссылка на `/properties/[id]`); пилюля статуса
  (`success` «Сдан», `warn` «Ожидает арендатора», `neutral` «Свободен»);
  **арендатор и аренда в подписи строки, когда объект сдан** (иначе поля
  контракта не используются, и их незачем отдавать); доход; долг
  акцентом, если больше нуля; счётчик заявок, если больше нуля; «на
  подходе» со знаком, если не ноль;
- если объектов нет вовсе — `EmptyState` «Объектов пока нет» с обычной
  ссылкой на `/properties` и текстом «Перейти к объектам». Ссылку,
  открывающую форму создания, не делать: форма на `/properties`
  управляется локальным состоянием и параметр URL не читает.

Подзаголовок страницы дополнить: сейчас «Доходы, задолженность и сроки
договоров» — станет неполным.

## 6. Крайние случаи (проверить явно)

| Случай | Ожидаемое поведение |
|---|---|
| Объект без договоров | В списке, «Свободен», нули |
| Только расторгнутый договор | «Свободен», доход прошлых периодов виден |
| Черновик договора | «Ожидает арендатора», аренда и арендатор пусты |
| Два `active`-договора | Берётся с наибольшим `startDate` |
| Объект с чужим договором | «Свободен», нули — чужих денег не показываем |
| Прощённая пеня | В долге объекта ноль пени, как в старом блоке |
| Незакрытая заявка по расторгнутому договору | Считается |
| Заявка `resolved` | Не считается |
| Плательщик — собственник | «На подходе» отрицательное, показывается со знаком |
| Услуга выставлена / ручная | В «на подходе» не входит |
| Объектов нет вовсе | Пустое состояние со ссылкой на `/properties` |
| Один город | Заголовки групп не показываются |
| Объекты без города | Последняя группа «Город не указан» |
