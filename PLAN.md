# PLAN — фронт ADR-0021 + согласие на обработку ПДн (ADR-0022)

> Рабочий план для сессии реализации. Источник задачи —
> `docs/DEV_STATE.md`, раздел «Рекомендуемый следующий шаг»: бэкенд
> ADR-0021 готов, фронта нет. Решения ниже приняты в интервью с
> владельцем продукта 2026-08-20 и должны быть зафиксированы в
> **ADR-0022 до написания кода** (правило `CLAUDE.md`).

## 1. Что делаем

Экран внесения персональных данных стороны договора + всё, что нужно,
чтобы им можно было пользоваться: согласие на обработку с фиксацией в
БД, страница политики, статус заполнения обеих сторон, напоминание на
«Сегодня», уведомление второй стороне.

## 2. Решения интервью (входные данные, не пересматривать)

| № | Решение |
|---|---------|
| Р1 | Отдельный роут `/leases/[id]/party-info` + секция-статус на `/leases/[id]` |
| Р2 | Правка данных разрешена на `draft`/`sent`/`active`; на `terminated` — только чтение |
| Р3 | Виден свой статус **и** статус контрагента (только флаг+дата, без ПДн) + пункт на «Сегодня» |
| Р4 | Согласие: обязательный чекбокс + ссылка на политику + **фиксация факта в БД** (дата + версия редакции) |
| Р5 | Политика: механизм сейчас, юридический текст потом — текст живёт в одном файле репозитория, заглушка честно говорит, что редакция готовится |
| Р6 | При изменении ПДн — уведомление второй стороне + подсказка арендодателю «договор сгенерирован раньше, перегенерируйте» |
| Р7 | Согласие, данное под **черновой** редакцией политики, юридически действующим не считается — см. §2.1 |

### 2.1. Почему это не противоречит ADR-0021

ADR-0021 запрещает **фактическое использование реальными людьми** до
готовности политики, и прямо оговаривает, что ограничение
организационное, а не техническое («Технически ничего не гейтится
флагом… но фактическое использование реальными людьми, а не тестовыми
аккаунтами, ждёт готовой политики»). Сам экран этот ADR не запрещает —
он назначен следующим шагом в `docs/DEV_STATE.md`.

Чтобы заглушка не выдавала себя за действующее согласие, версия
черновой редакции несёт суффикс `-draft`, и **механизм версионирования
согласия сам решает проблему перехода**: когда юрист даст финальный
текст, версия бампится, и у всех, кто согласился под черновиком,
согласие автоматически перестаёт быть актуальным — форма запросит его
заново. Это должно быть записано в ADR-0022 явно.

### Не в скоупе

- Реальный юридический текст политики (готовит владелец продукта;
  оригиналы `.docx` лежат вне репозитория, в `soft_rent/`, и пока
  написаны под другой сервис — `flashformat.ru`).
- Отдельный документ «Согласие на обработку» как печатная форма.
- Фаза 5 и далее.
- OCR (ADR-0008) — запрещено начинать без отдельного разговора.

### B2. Политика живёт на бэкенде целиком: текст и версия неразделимы

Держать текст во фронте, а версию — на бэке нельзя: тогда пользователь
видит редакцию X, сервер фиксирует согласие под редакцией Y, и никакая
сверка этого не поймает (фронт может лишь эхом вернуть то, что ему дал
сервер). Поэтому **текст и версия — один артефакт на бэкенде**.

Новый модуль `backend/src/legal/`:

- `privacy-policy.const.ts`:
  ```ts
  // Текст политики обработки ПДн (ADR-0022) — единственный экземпляр в
  // системе; фронт получает его отсюда и нигде не дублирует.
  export const PRIVACY_POLICY_HTML = `…`;          // фрагмент, без <html>
  export const PRIVACY_POLICY_UPDATED_AT = '2026-08-20';

  // Версия = ручная метка + короткий хеш текста. Хеш нужен, чтобы текст
  // физически нельзя было поменять, «забыв» поднять версию: любая правка
  // сама делает прошлые согласия неактуальными и заставляет запросить их
  // заново. Суффикс -draft означает: текст ещё не юридический (§2.1).
  export const PRIVACY_POLICY_VERSION = `2026-08-20-draft+${createHash('sha256')
    .update(PRIVACY_POLICY_HTML)
    .digest('hex')
    .slice(0, 8)}`;
  ```
- `legal.controller.ts` — **публичный** (без `JwtAuthGuard`; политика по
  152-ФЗ должна открываться без входа):
  `GET /legal/privacy-policy` → `{ version, updatedAt, html }`.
- `legal.module.ts`, подключается в `app.module.ts`. `PartyInfoModule`
  импортирует константу напрямую (не через HTTP).

Проверка при сохранении: фронт присылает `policyVersion` — ту, что
пришла вместе с показанным текстом. Не совпала с
`PRIVACY_POLICY_VERSION` → `ConflictException('Политика обработки данных
обновилась — обновите страницу')`. Подделать согласие клиент не может:
он способен только совпасть или получить отказ.

### B3. DTO — разделить «запрос», «то что шифруется» и «ответ»

`backend/src/party-info/dto/party-info.dto.ts`:

- **`PartyInfoDto`** (то, что лежит в `dataEnc`) — состав полей не
  меняется, но валидация ужесточается:
  - `passportSeries` — `@Matches(/^\d{4}$/)`
  - `passportNumber` — `@Matches(/^\d{6}$/)`
  - `passportIssuedBy` — `@Length(5, 200)`
  - `birthDate` — `@Matches(/^\d{4}-\d{2}-\d{2}$/)` **строго календарная
    дата без времени и зоны** (`@IsDateString()` в одиночку пропускает
    полный ISO-timestamp, и тогда «возраст» начинает зависеть от часового
    пояса)
  - `registrationAddress` — `@Length(10, 300)`
  - `phone` — `@IsOptional() @Matches(/^\+7\d{10}$/)`
  - Все сообщения об ошибках — по-русски (`{ message: '...' }`).
- **`SavePartyInfoDto extends PartyInfoDto`** — добавляет
  `@IsOptional() @IsBoolean() consentAccepted?: boolean` и
  `@IsOptional() @IsString() policyVersion?: string` (та редакция, что
  фронт показал пользователю).
  **Ни `consentAccepted`, ни `policyVersion` не шифруются** и не попадают
  в `dataEnc` — сервис снимает их перед `JSON.stringify`. В приложении
  включён `ValidationPipe({ whitelist: true })` (`backend/src/main.ts:16`),
  лишние поля в теле запроса отсекаются им.
- **`PartyInfoView`** (ответ `GET`) — `PartyInfoDto` +
  `consentAcceptedAt: string | null`, `consentPolicyVersion: string | null`,
  `currentPolicyVersion: string`, `updatedAt: string`.
- **`PartyInfoStatusView`** — про себя знаем больше, про контрагента
  отдаём необходимый минимум (его состояние согласия — не наше дело):
  ```ts
  {
    role: 'landlord' | 'tenant';          // кто спрашивает
    currentPolicyVersion: string;         // нужен фронту ДО того, как строка появилась
    self:         { filled: boolean; updatedAt: string | null; needsConsent: boolean };
    counterparty: { filled: boolean; updatedAt: string | null };
  }
  ```
  Точные формулы (обе стороны считаются одинаково, роль контрагента —
  инверсия своей, независимо от того, привязан ли уже `tenantId`):

  ```
  filled       = row != null && row.consentAcceptedAt != null
  needsConsent = row == null || row.consentAcceptedAt == null
                             || row.consentPolicyVersion !== PRIVACY_POLICY_VERSION
  updatedAt    = row?.updatedAt ?? null
  ```

  Строки нет вообще → `{ filled: false, updatedAt: null }`, а для `self`
  ещё и `needsConsent: true`. Проверка `consentAcceptedAt != null` в
  `needsConsent` обязательна отдельно от версии: иначе битая строка
  `{ consentAcceptedAt: null, consentPolicyVersion: <текущая> }` прошла бы
  без галочки. `needsConsent` — единственный источник правды для галочки
  на форме и для пункта на «Сегодня».

### B4. `party-info.service.ts`

**`resolveParty`** — добавить в запрос `include: { property: { select: { address: true } } }`
(адрес нужен в теле уведомления), тип возврата обновить.

**`upsert(userId, leaseId, dto: SavePartyInfoDto)`** — порядок шагов:

1. `resolveParty` → `lease`, `role`.
2. Если `lease.status === LeaseStatus.terminated` →
   `ForbiddenException('Договор расторгнут — персональные данные больше нельзя изменить')`.
3. Проверка `birthDate` — отдельным чистым помощником
   `parseBirthDate(value: string): { y: number; m: number; d: number }`,
   чтобы её можно было покрыть тестами напрямую:
   - разобрать `YYYY-MM-DD` на компоненты вручную и убедиться, что
     `new Date(Date.UTC(y, m - 1, d))` даёт **ровно те же** компоненты —
     иначе `2025-02-31` тихо станет 3 марта;
   - сравнение с сегодняшним днём — по календарной дате в UTC (не по
     миллисекундам, иначе граница возраста плавает от часового пояса);
   - границы включительные: ровно 18 лет — можно, ровно 120 — можно;
   - ошибки: `BadRequestException('Дата рождения указана неверно')` для
     несуществующей даты/будущего, `('Сторона договора должна быть
     совершеннолетней')` для возраста < 18.
4. Прочитать существующую строку `leasePartyInfo.findUnique`.
5. Гейт согласия — формула та же, что в `getStatus`:
   `needsConsent = !existing || !existing.consentAcceptedAt || existing.consentPolicyVersion !== PRIVACY_POLICY_VERSION`.
   Если `needsConsent`:
   - `dto.consentAccepted !== true` →
     `BadRequestException('Нужно согласие на обработку персональных данных')`;
   - `dto.policyVersion !== PRIVACY_POLICY_VERSION` →
     `ConflictException('Политика обработки данных обновилась — обновите страницу')`.
6. `payload: PartyInfoDto` = `dto` без `consentAccepted`/`policyVersion`.
   **Пустой телефон — это отсутствие ключа, а не `phone: undefined`:**
   собирать объект полями явно, и `phone` добавлять только когда строка
   непустая (`JSON.stringify` молча выбрасывает `undefined`, но полагаться
   на это нельзя — важно, чтобы старое значение исчезло из расшифрованного
   JSON после очистки поля).
7. `changed = !existing || this.crypto.decrypt(existing.dataEnc) !== JSON.stringify(payload)`.
8. **Если `!changed && !needsConsent` — выйти, ничего не записывая**,
   вернуть `{ leaseId, role }`. Без этого Prisma-`@updatedAt` обновлялся бы
   при каждом «Сохранить», и подсказка «договор устарел» загоралась бы,
   хотя данные те же.
9. Иначе `upsert`: `dataEnc`, `enteredById`; поля согласия пишутся
   **только** когда `needsConsent` (`consentAcceptedAt: new Date()`,
   `consentPolicyVersion: PRIVACY_POLICY_VERSION`) — иначе прошлая дата
   согласия затирается и перестаёт доказывать первичное согласие.
10. Если `changed` и вторая сторона существует (`lease.tenantId` не
    `null`) — уведомить её (см. B5).
11. Вернуть `{ leaseId, role }` (контракт не меняется).

**`getOwn`** → возвращает `PartyInfoView`. Поведение «не заполнено»
остаётся `404` (фронт уже работает с этой идиомой у `getDocument`).
Если запись есть, но согласие устарело (или его нет) — **всё равно
отдаём расшифрованные данные**: человек редактирует то, что уже внёс, и
одновременно видит запрос нового согласия. Пустая форма в этом случае
была бы потерей уже введённых данных.

**`getAsSuperAdmin`** → тоже `PartyInfoView` (для спора важна именно
дата согласия и редакция).

**Новый `getStatus(userId, leaseId): Promise<PartyInfoStatusView>`** —
через `resolveParty` (то есть только стороне договора, чужому — 404),
`findMany({ where: { leaseId }, select: { role: true, updatedAt: true, consentAcceptedAt: true, consentPolicyVersion: true } })`,
персональных данных не расшифровывает и не отдаёт (`crypto.decrypt` в
этом методе не вызывается вовсе). Поля согласия контрагента наружу не
отдаются — они участвуют только в расчёте своего `needsConsent`.

**`runRetention`** — не трогать.

### B4.1. Использовать только те ПДн, на которые есть зафиксированное согласие

`backend/src/leases/lease-documents.service.ts`, `loadPartyInfo` — добавить
в `where` условие `consentAcceptedAt: { not: null }`. Записи без
зафиксированного согласия в договор не подставляются (в шаблоне остаются
прочерки, генерация не падает). Практически таких строк сейчас нет — но
правило «печатаем только то, на что есть согласие» должно жить в коде, а
не в устной договорённости.

**Фильтровать здесь ещё и по актуальности версии — сознательно не
делаем.** Иначе замена текста политики задним числом вычищала бы
паспортные данные из всех уже действующих договоров, и арендодатель
получал бы документ с прочерками из-за правки, к которой он отношения не
имеет. Смена редакции управляет тем, **когда заново спросить согласие**
(следующая правка данных), а не тем, **можно ли пользоваться уже
собранными данными**: согласие, данное под прежней редакцией, было
действительным в момент, когда его давали. Записать это решение в
ADR-0022 явным абзацем — это ровно то место, где легко принять
противоположное решение молча.

### B5. Уведомление второй стороне

`PartyInfoModule` импортирует `NotificationsModule`; сервис получает
`NotificationsService`.

**Вызов обязательно обернуть в `try/catch` на стороне `PartyInfoService`.**
`NotificationsService.notify()` называет себя best-effort, но его
внутренний `try` покрывает только доставку в канал —
`prisma.user.findUnique` и `prisma.notification.create` вне него
(`backend/src/notifications/notifications.service.ts:33-44`). Без внешнего
`catch` сбой уведомления превратил бы уже сохранённые персональные данные
в ошибку 500 для пользователя. Ошибку — в `Logger.warn`, ответ не менять.

- `type`: `'party_info_submitted'`
- Получатель — противоположная сторона (`role === landlord` → `lease.tenantId`, иначе `lease.landlordId`).
- Арендодателю: title «Арендатор внёс персональные данные», body
  «По договору на объект «<адрес>» вторая сторона внесла свои
  паспортные данные. Если текст договора уже сгенерирован —
  перегенерируйте его, иначе в нём останутся прочерки.»
- Арендатору: title «Собственник внёс персональные данные», body
  «По договору на объект «<адрес>» вторая сторона внесла свои
  паспортные данные.» (без совета перегенерировать — генерация
  доступна только собственнику).
- Не отправлять, если `changed === false` (повторное сохранение тех же
  значений) или второй стороны ещё нет.

### B8. Тесты (`backend/src/party-info/party-info.service.spec.ts`)

Существующие тесты поправить под новый `resolveParty` (мок `lease.findUnique`
теперь возвращает объект с `property.address` и `status`). Добавить:

1. `terminated` → `ForbiddenException`, `leasePartyInfo.upsert` не вызван.
2. Первое сохранение без `consentAccepted` → `BadRequestException`.
3. `consentAccepted: true`, но `policyVersion` чужой → `ConflictException`.
4. Первое сохранение с согласием → в `upsert.create` ушли
   `consentAcceptedAt` и `consentPolicyVersion === PRIVACY_POLICY_VERSION`.
5. Изменение данных при той же версии политики без флага → проходит,
   и в `update` **нет** полей согласия (прошлая дата не затёрта).
6. Версия политики изменилась → согласие требуется заново (400 без флага).
7. Сохранение тех же данных при действующем согласии → `upsert`
   **не вызывается вовсе**, уведомления нет (защита `updatedAt`).
8. Ни `consentAccepted`, ни `policyVersion` не попали в зашифрованный
   payload (`crypto.encrypt` вызван со строкой без этих ключей).
9. Телефон очищен → в строке, переданной в `crypto.encrypt`, ключа
   `phone` нет вообще.
10. Уведомление ушло второй стороне при изменении данных; тексты для
    landlord и tenant различаются.
11. Падение `notifications.notify` не ломает сохранение (мок бросает —
    `upsert` всё равно успешен, метод возвращает `{ leaseId, role }`).
12. Уведомления нет, когда `tenantId === null`.
13. `birthDate`: в будущем → 400; несуществующая `2025-02-31` → 400;
    существующая `2024-02-29` → проходит; возраст ровно 18 → проходит;
    17 лет и 364 дня → 400; ровно 120 → проходит; 121 → 400.
    (Тесты фиксируют «сегодня» — `jest.useFakeTimers` или явная передача
    `now` в помощник, иначе пограничные случаи протухнут со временем.)
16. Битая строка `{ consentAcceptedAt: null, consentPolicyVersion: <текущая> }`
    → согласие всё равно требуется (400 без флага).
17. Устаревшая `consentPolicyVersion` → `getOwn` по-прежнему отдаёт
    расшифрованные данные, а `getStatus` ставит `needsConsent: true`.
14. `getStatus` отдаёт `self`/`counterparty`/`currentPolicyVersion`,
    `needsConsent` считается по версии политики, и `crypto.decrypt`
    не вызывается ни разу.
15. `getStatus` для не-стороны → `NotFoundException`.

Плюс в `backend/src/leases/lease-documents.service.spec.ts` (если файл

## 6. Крайние случаи (проверить явно)

| Случай | Ожидаемое поведение |
|---|---|
| `draft`, арендатора ещё нет | `status.tenant.filled === false`, уведомление не отправляется, на «Сегодня» пункта нет |
| Не сторона договора зовёт `GET status` | 404 «Договор не найден» (как `resolveParty` везде) |
| SuperAdmin, не являющийся стороной | те же 404 на `status`; свои данные читает через `GET /lease-party-info/:leaseId/:role` |
| Повторное сохранение тех же значений | 200, записи в БД нет вовсе, `updatedAt` не сдвинулся, уведомления нет |
| Версия политики сменилась | следующее сохранение снова требует галочку; `needsConsent` загорается и на «Сегодня». Уже собранные данные из договоров **не исчезают** (B4.1) |
| Запись есть, согласие устарело | форма открывается заполненной, но с запросом нового согласия — введённое не теряется |
| Фронт показал устаревшую редакцию | `PUT` → 409, а не молчаливая фиксация согласия под невидимым текстом |
| `terminated` | `PUT` → 403 и на бэкенде, и в UI (не только в UI) |
| Телефон стёрли | ключа `phone` нет в payload, в договоре снова прочерк |
| Запись без зафиксированного согласия | в договор не подставляется (B4.1), в статусе — `needsConsent: true` |
| Ретеншен удалил строку | согласие уходит вместе с данными — так и задумано |
| Гонка `PUT` с ретеншеном | практически исключена: ретеншен трогает только `terminated`, а `PUT` на `terminated` запрещён шагом 2. Транзакцию не вводим — записать в ADR как осознанный допуск |
| Две вкладки правят одновременно | `PUT` — полная замена своей записи, побеждает последний. Два одновременных одинаковых `PUT` могут прочитать старое значение и оба отправить уведомление — дубль уведомления считаем допустимым, сериализацию не вводим (записать в ADR) |

## 8. Чего делать нельзя

- Не вносить реальные персональные данные — только синтетические.
- Не подставлять текст из `politika-pdn-IP-Sidorovnin*.docx` в продукт:
  он написан под другой сервис и не проверен юристом под SoftRent.
- Не начинать OCR (ADR-0008) и не трогать Фазы 5+.
- Не менять контракт `PUT /leases/:leaseId/party-info` в части ответа
  (`{ leaseId, role }`) — фронт и тесты на него опираются.
