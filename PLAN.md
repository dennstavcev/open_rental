# PLAN — Фазы 33 и 34: остатки после «пункта 0»

> Источник задачи — `docs/DEV_STATE.md`, Фазы 33 и 34. Их authz-части закрыты
> коммитом `37118c5` («пункт 0»); здесь добираются все оставшиеся пункты обеих
> фаз. Новых ADR не требуется: ADR-0034 уже принят и эту часть не затрагивает,
> остальное — UX/контракт без новых сущностей. Миграции БД не нужны.
>
> Решение владельца (2026-08-25): у расторгнутого договора показываются **все**
> вкладки плюс явная пометка «Архив»; скрываются кнопки «Внести показание»,
> «Новая заявка» и форма отправки сообщения. Действия по счетам при этом
> **остаются** — оплата и подтверждение последнего счёта после расторжения
> обязательны, ради них фаза и затевалась.
>
> Ревизия 3 (2026-08-25, после двух раундов ревью). Добавлено сверх ревизии 2:
> `expectedPreviousValue` стал обязательным и валидируемым при `confirm`;
> расписаны ветки «аномалия исчезла» и «база выросла выше введённого»;
> серверные гарды поставлены на мутации заявок, которые ломают данные;
> в архиве убраны действия черновика счёта; сканы можно открыть, а не только
> увидеть строку «Загружен».
>
> Ревизия 2 (2026-08-25, после первого раунда ревью). Изменено по итогам:
> у `submitReading` есть **второй потребитель** — карточка объекта, он тоже
> обязан понимать двухшаговость; `confirm` идёт **шестым** аргументом, чтобы не
> сдвинуть позиционный `readingDate`; добавлена защита от подтверждения
> устаревших чисел; `maintenance.create` статус договора **не проверяет** —
> нужен серверный гард, иначе «новые заявки недоступны» держится на одной лишь
> скрытой кнопке; архив делает экран заявок целиком read-only (иначе оставшиеся
> действия создают неоплачиваемые услуги) и показывает подписанные сканы.

## 33-1. Двухшаговое подтверждение аномалии

Сейчас `MeterReadingsService.create` считает `warning` (расход >10× среднего,
`meter-readings.service.ts:108`), но **уже после** этого безусловно сохраняет
фото, показание и строку счёта — предупреждение возвращается постфактум, а
диалог на фронте просто закрывается (`frontend/app/leases/[id]/meters/page.tsx:81-84`).
Пользователь не получает паузы на проверку.

### Backend

`backend/src/meters/dto/create-reading.dto.ts` — добавить необязательное поле
`confirm`. Приходит из `multipart/form-data` строкой, поэтому повторить
готовый приём из `backend/src/messages/dto/send-message.dto.ts` (поле
`isOfficial`) буква в букву:
```ts
// multipart-форма присылает строку "true"/"false" — приводим к boolean.
@IsOptional()
@Transform(({ value }) => value === true || value === 'true')
@IsBoolean()
confirm?: boolean;
```
Своего варианта приведения не изобретать.

`backend/src/meters/meter-readings.service.ts`, `create()`:

- `confirm` добавляется **шестым** аргументом `create()`, после `readingDate`.
  Пятый аргумент сейчас позиционно передаётся существующим тестом
  (`meter-readings.service.spec.ts:247-252`) — вставка `confirm` перед ним
  молча изменит смысл вызова.
- **Порядок обязателен**: расчёт `previousValue` / `consumption` / `warning`
  уже происходит до `ocr.recognize` и `storage.put` — сразу после вычисления
  `warning` вставить ранний выход:
  ```ts
  if (warning && !confirm) {
    return {
      requiresConfirmation: true,
      consumption,
      cost,
      previousValue,
      warning,
    };
  }
  ```
  где `cost` считается тут же (сейчас он вычисляется ниже — поднять расчёт
  выше раннего выхода).
- На этом шаге **не должно происходить ничего необратимого**: ни
  `this.ocr.recognize`, ни `this.storage.put`, ни `billing.ensureCurrentDraft`,
  ни транзакции. Иначе в хранилище копятся осиротевшие фото.
- При `confirm === true` поведение прежнее: сохраняем всё и возвращаем
  `warning` вместе с показанием (пользователь его уже видел, но ответ остаётся
  информативным).
- **Защита от подтверждения устаревших чисел.** Между шагами по тому же
  счётчику может пройти показание от второй стороны — тогда пользователь
  подтвердит один расход, а сохранится другой (несколько показаний за период
  разрешены, это закреплено тестом `meter-readings.service.spec.ts:257`).
  Поэтому шаг 1 возвращает ещё и `previousValue`, а шаг 2 обязан прислать его
  назад полем `expectedPreviousValue`.
  - В DTO поле **должно быть валидируемым**, иначе глобальный
    `ValidationPipe({ whitelist: true })` (`backend/src/main.ts:15-17`) его
    просто вырежет, и защита тихо перестанет работать:
    `@IsOptional() @Type(() => Number) @IsNumber({ maxDecimalPlaces: 3 }) @Min(0)`.
  - **При `confirm === true` поле обязательно.** Если его нет — `BadRequest`
    («Подтверждение без исходного значения»). Необязательным его оставлять
    нельзя: клиент, который его не пришлёт, обойдёт защиту целиком.
  - Сравнение вести числами после `toNumber(...)` либо через `Decimal.equals`;
    сырые строки не сравнивать (`value` в БД — `Decimal(12,3)`).
  - На фронте поле добавляется в `FormData` по условию `!== undefined`, а не
    по truthiness — иначе законная база `0` потеряется.
  - Три ветки, когда база изменилась (`expectedPreviousValue !== previousValue`):
    1. новое `previousValue > confirmedValue` → обычная ошибка
       `BadRequest('Новое показание не может быть меньше предыдущего')`, как и
       при первом шаге; фронт возвращает пользователя к форме;
    2. аномалия при пересчёте **сохранилась** → снова `requiresConfirmation` с
       новыми `consumption`/`cost`/`previousValue`;
    3. аномалия при пересчёте **исчезла** (расход стал нормальным) → тоже
       вернуть шаг подтверждения, но с `warning: null`, поэтому в объединении
       у ветки `requiresConfirmation` поле `warning` должно быть
       `string | null`, а фронт в этом случае показывает нейтральное
       «Показания изменились — проверьте расход» вместо предупреждения.
       Молча сохранять нельзя: пользователь подтверждал другие числа.
- **Вне скоупа, не чинить здесь** (существующее поведение, не привнесённое
  этой задачей): возможность подать несколько показаний за период,
  дублирование при повторной отправке одного и того же запроса и гонка
  check-then-create в `ensureCurrentDraft` (`billing.service.ts:588`).
  Упомянуть в отчёте, отдельного решения владельца пока нет.
- Тип ответа — размеченное объединение, экспортируется из того же файла:
  ```ts
  export type ReadingResult =
    | {
        requiresConfirmation: true;
        consumption: number;
        cost: number;
        previousValue: number;
        // null — аномалия исчезла после пересчёта, но числа изменились
        warning: string | null;
      }
    | {
        requiresConfirmation?: false;
        reading: MeterReading;
        consumption: number;
        cost: number;
        warning: string | null;
      };
  ```
  Существующее имя `ReadingResult` сохранить — оно используется в контроллере.
- Валидации, которые обязаны срабатывать **до** проверки аномалии и вести себя
  как раньше: тип фото, дата в будущем, отсутствие счётчика, отключённый
  счётчик, отсутствие активного договора, не сторона договора, показание
  меньше предыдущего. Двухшаговость их не отменяет.

`backend/src/meters/meter-readings.controller.ts` — прокинуть `dto.confirm` в
сервис. Маршрут и остальной контракт не меняются.

### Frontend

`frontend/lib/catalog.ts`:

- `submitReading(meterId, confirmedValue, photo, confirm = false, expectedPreviousValue?)`
  — добавить `confirm` (строкой `'true'`, только когда `true`) и
  `expectedPreviousValue` в `FormData`.
- Описать тип ответа тем же размеченным объединением, что на бэкенде.
- **У функции два потребителя, оба обязаны понимать двухшаговость.** Второй —
  карточка объекта (`frontend/app/properties/[id]/page.tsx:253`), где ответ
  сейчас безусловно трактуется как успех: показывается «Принято: расход …» и
  закрывается шит (`:254-261`). Поля `consumption`/`cost`/`warning` есть в
  обеих ветках объединения, поэтому без явной проверки `requiresConfirmation`
  собственник увидит «Принято» там, где ничего не сохранено.

`frontend/app/leases/[id]/meters/page.tsx`:

- Состояние
  `pending: { consumption: number; cost: number; previousValue: number; warning: string | null; photo: File } | null`
  (`warning` именно nullable — в ветке «аномалия исчезла» его нет).
- **`File` обязан лежать в состоянии, а не только в `readFileRef`.** Второй шаг
  скрывает форму, `<input type="file">` размонтируется, и `readFileRef.current`
  станет `null` — подтверждение отправить будет нечем. Файл берётся из инпута
  один раз, в `onSubmitReading`, и кладётся в `pending`.
- `onSubmitReading`: если ответ содержит `requiresConfirmation` — не закрывать
  диалог, а перевести его во второй шаг (`setPending(...)`), форму скрыть.
- Второй шаг внутри того же `DialogContent`: текст предупреждения, введённое
  значение, расход и сумма; кнопки **«Всё верно, сохранить»**
  (`submitReading(id, value, pending.photo, true, pending.previousValue)`,
  заново выбирать фото пользователь не должен) и **«Исправить»** (возврат к
  форме, `pending` сбрасывается, введённое значение сохраняется).
- Если подтверждение снова вернуло `requiresConfirmation` (за это время
  подали другое показание) — обновить `pending` новыми числами и показать
  строку «Показания изменились, проверьте ещё раз», не сохраняя молча.
- Закрытие диалога сбрасывает `pending`, значение и файл.
- Обычный расход (без `warning`) проходит в один шаг, как раньше.

Аналогичный второй шаг сделать в шите показаний на карточке объекта
(`frontend/app/properties/[id]/page.tsx`), той же логикой и теми же текстами.

### Тесты (`backend/src/meters/meter-readings.service.spec.ts`)

- аномалия без `confirm` → возвращён `requiresConfirmation: true`; **не
  вызваны** `storage.put`, `ocr.recognize`, `prisma.$transaction`,
  `billing.ensureCurrentDraft`, `billing.addUtilityLine`;
- аномалия с `confirm: true` → показание и строка счёта созданы, `warning`
  возвращён;
- обычный расход без `confirm` → сохраняется сразу, `requiresConfirmation`
  отсутствует;
- показание меньше предыдущего при `confirm: true` → по-прежнему
  `BadRequestException` (подтверждение не обходит валидацию);
- отключённый счётчик при `confirm: true` → по-прежнему `ConflictException`;
- `confirm: true` с совпадающим `expectedPreviousValue` → сохранение проходит;
- `confirm: true` без `expectedPreviousValue` → `BadRequestException`, ничего
  не сохранено;
- база изменилась, аномалия сохранилась → `requiresConfirmation` с новыми
  числами, ничего не сохранено;
- база изменилась, аномалия исчезла → `requiresConfirmation` с `warning: null`,
  ничего не сохранено;
- база изменилась и стала **больше** введённого значения →
  `BadRequestException` («Новое показание не может быть меньше предыдущего»),
  а не `requiresConfirmation`.

## 34-1. Архивная навигация для расторгнутого договора

`frontend/app/leases/[id]/page.tsx:363` — сейчас
`{lease.status === 'active' && lease.tenantId && <LeaseTabs id={id} />}`,
поэтому у расторгнутого договора исчезает путь к последнему счёту, хотя
backend его отдаёт.

- Условие показа: `(lease.status === 'active' || lease.status === 'terminated') && lease.tenantId`.
  Для `draft`/`sent` навигация по-прежнему скрыта — там ещё нет ни счетов, ни
  показаний.
- `frontend/components/LeaseTabs.tsx` — новый необязательный проп
  `archived?: boolean`. При `archived` над полосой вкладок рендерится строка-
  пометка: заголовок **«Архив»** и текст «Договор завершён. Новые показания,
  заявки и сообщения добавить нельзя; счета и вся история открыты.» —
  формулировка не должна намекать, что вкладка показаний или переписка
  недоступны: недоступен только ввод Оформить существующими
  токенами (нейтральный `StatusPill` / `text-content-muted`), новых компонентов
  не заводить.
- `LeaseTabs` вызывается на пяти экранах (`page.tsx`, `bills`, `meters`,
  `requests`, `chat`) — на каждом передать `archived={lease?.status === 'terminated'}`.
  Экраны `meters`, `requests`, `chat` для этого должны знать статус договора;
  `meters` получает договор по пункту 33-3, `bills` и `requests` загружают его
  уже сейчас (`requests/page.tsx:225` — `Promise.all([getLease(id), listRequests(id)])`),
  так что добавить `getLease(id)` нужно только на экране чата
  (`frontend/app/leases/[id]/chat/page.tsx` договор сейчас не загружает вовсе).
### Серверный гард на создание заявки

`backend/src/maintenance/maintenance.service.ts:54-57` — `create()` проверяет
только роль арендатора; **статус договора не проверяется**, заявку можно
создать и по расторгнутому. Скрытая кнопка это не закрывает (прямой вызов API,
polling, открытый до расторжения диалог). Добавить после проверки роли:

```ts
if (lease.status !== LeaseStatus.active) {
  throw new ConflictException('Договор не действует — новые заявки недоступны');
}
```

Тот же гард нужен на остальных мутациях заявок, иначе объявленный read-only
держится на скрытых кнопках: `changeStatus` (`:96-147`), предложение суммы и
`confirmSettlement` (`:151-206`). Последний особенно важен — именно он создаёт
услугу с `billedAt: null`, которую после расторжения уже нельзя выставить в
счёт, то есть ровно то, ради чего экран и объявлен read-only. Во всех случаях
гард ставится **после** проверки прав и **до** любых записей и `storage.put`.

**Граница проведена сознательно:** серверные гарды ставим там, где мутация
портит данные (заявки/услуги), и **не** ставим на `messages`
(`messages.service.ts:38-98`). Скрытие формы чата — решение владельца про
интерфейс; закрывать API дополнительно не нужно, счета после расторжения
остаются к оплате, и обсуждать их сторонам может понадобиться. Эту
асимметрию — «чат закрыт только в UI» — зафиксировать в отчёте владельцу.

Тесты в `maintenance.service.spec.ts`: по `terminated`-договору
`create`/`changeStatus`/`confirmSettlement` → `ConflictException`; ни
`prisma.maintenanceRequest.create`, ни создание услуги не вызваны; фото в
хранилище не положено (гард стоит до `storage.put`, `:59-67`).

### Что скрыть и что показать при `terminated`

- `meters` — кнопка «Внести» **и открытый диалог показаний**: если договор
  расторгли, пока диалог открыт (polling обновляет данные каждые 30 с), диалог
  должен закрыться, а не оставаться рабочим до 409. Также скрыть блок
  «Текущий период / срок подачи» (`meters/page.tsx:124-140`) — в архиве он
  показывает выдуманный период.
- `requests` — экран целиком **read-only**: помимо «Новой заявки»
  (`requests/page.tsx:266`, `:293`, `:311`) убрать смену статуса, предложение
  суммы и подтверждение урегулирования (`:104`, `:168-201`). Это шире, чем
  «скрыть создание», но необходимо: перевод в `resolved` с невыставленной
  услугой на завершённом договоре отвечает 409
  (`maintenance.service.ts:105-117`), а подтверждение урегулирования создаёт
  услугу с `billedAt: null`, которую уже нельзя выставить в счёт. Оставлять
  кнопки, ведущие в тупик, хуже, чем убрать их.
- `chat` — форма отправки (`chat/page.tsx:148-192`), вместо неё строка
  «Договор завершён — переписка доступна только для чтения». Экран сейчас
  договор не загружает вовсе; форму нельзя показывать, **пока статус
  неизвестен** — до загрузки договора рендерить состояние загрузки, а не
  форму, иначе на секунду появится действие, которого в архиве быть не должно.

  Включить `terminated` в загрузку и показ секции; **загрузку нового скана
  оставить только для `sent`**.
- Пустые состояния в архиве не должны звать к действию: чат

## 34-2. Счета: «Требуют действия» / «История» и честные подписи

`frontend/app/leases/[id]/bills/page.tsx`. Backend отдаёт счета
`orderBy: { periodStart: 'desc' }` (`billing.service.ts:104`) — единственная
просрочка за старый период оказывается внизу списка. Группировку делать **на
фронте**, контракт API не менять.

- Разделение (по уже существующим полям `BillView`):
  - **Требуют действия**:
    - собственник: `bill.stage === 'draft'` (нужно сформировать) либо
      `bill.paymentStatus === 'payment_claimed'` (нужно подтвердить оплату);
    - арендатор: `bill.stage === 'final' && bill.paymentStatus === 'pending' && totalDue > 0`.
      **Именно `pending`, а не `!== 'paid'`**: `payment_claimed` означает, что
      арендатор уже заявил оплату и ждёт собственника — так это и трактует
      дашборд (`frontend/app/dashboard/page.tsx:151-170`). Замена чека при
      `payment_claimed` остаётся доступной, но действием не считается.
  - **История** — все остальные, включая счета с `paymentStatus === null`
    (`frontend/lib/billing.ts:19` допускает null, схема тоже —
    `schema.prisma:295-324`): такой счёт не принимается ни `claimPaid`, ни
    `confirmPaid` (`billing.service.ts:365-372`), звать к действию по нему
    нельзя.
  - Классификация — строго одна ветка на счёт: сначала правило текущей роли,
    всё остальное в «Историю». Ни один счёт не должен попасть в обе группы или
    выпасть из обеих.
- Порядок:
  - внутри «Требуют действия» — сначала `overdue`, затем по `periodStart`
    **по возрастанию** (самая старая просрочка первой);
  - внутри «Истории» — по `periodStart` по убыванию (как сейчас).
- Заголовки секций — существующий `Section`. Если группа пуста, её секция не
  рендерится вовсе (не рисовать пустой заголовок). Если пусты обе — текущий
  `EmptyState`.
- **Роль обязана быть известна до группировки.** Сейчас `isLandlord` и
  `isTenant` оба равны `false`, пока `lease` не загружен
  (`bills/page.tsx:55-56`), поэтому нельзя писать `isLandlord ? A : B` —
  неизвестная роль молча станет арендаторской. Список рендерить только после
  того, как загружены и `lease`, и `user`; до этого — состояние загрузки из
  пункта 34-3.
- Подпись суммы (`bills/page.tsx:273-292`) — сейчас «к оплате» приписывается
  любому счёту с ненулевой суммой, включая оплаченный. Исправить:
  - `unpaid` → «к оплате» (как сейчас);
  - оплаченный → «оплачено»;
  - черновик → «предварительно».
  Цветовые правила (`danger` при просрочке, `terracotta` при неоплате) не
  менять.

## 34-3. Разведение загрузки, ошибки и пустоты

Сейчас ошибка загрузки маскируется под успешный результат:

- `bills/page.tsx:236-243` — при провале `load()` `lease` остаётся `null`, и
  экран навсегда показывает «Загрузка…» рядом с баннером ошибки;
- `meters/page.tsx:143-150` — при провале `loading` становится `false`, список
  пуст, и пользователь видит «Счётчиков пока нет», хотя данные просто не
  загрузились.

Ввести на обоих экранах **три различных понятия** — их смешение и есть корень
проблемы:

- `loading` — идёт первая загрузка (или ручной повтор). Фоновый опрос
  `usePolling` (`frontend/lib/usePolling.ts:9`, каждые 30 с) его **не
  выставляет**, иначе показанные данные будут мигать в «Загрузка…» дважды в
  минуту. Один и тот же `load()` не может одновременно всегда ставить
  `loading` (для «Повторить») и никогда его не ставить (для опроса) —
  завести две точки входа: `load({ foreground })` либо отдельные
  `loadForeground()` и `refresh()`; в `usePolling` передавать фоновую;
- `loaded` — был хотя бы один успешный снимок. Проверять «ничего не
  загружено» через `meters.length === 0` нельзя: успешно загруженный пустой
  список — это тоже данные, и при последующей ошибке опроса экран обязан
  сохранить честный `EmptyState` с баннером, а не уходить в полноэкранную
  ошибку;
- `error` — последняя ошибка, независимо от того, есть ли снимок.

Порядок ветвления:

1. `error && !loaded` → только состояние ошибки с кнопкой «Повторить»
   (`load()` с `loading = true`); ни «Загрузка…», ни `EmptyState`;
2. `loading && !loaded` → «Загрузка…»;
3. `loaded` и данных нет → `EmptyState`;
4. `loaded` и данные есть → данные.

При `loaded` ошибка остаётся баннером над уже показанными данными — данные не
прятать ни при каких обстоятельствах.

На странице счетов завести явные `loading`/`loaded` (сейчас их роль играет
`lease === null`, `bills/page.tsx:236`). Успешная загрузка на этих экранах
атомарна — `lease` и список приходят одним `Promise.all`, поэтому `loaded`
ставится один раз после успеха обоих.

## Критерии приёмки

1. Аномальный расход (>10×) без подтверждения: ответ содержит
   `requiresConfirmation`, в БД нет ни показания, ни строки счёта, в хранилище
   нет файла фото, `ocr.recognize` не вызывался. Повтор с подтверждением
   сохраняет всё.
2. Обычный расход сохраняется одним шагом; ни одна прежняя валидация не
   обойдена подтверждением (меньше предыдущего, отключённый счётчик, чужой
   договор, дата в будущем).
3. Пользователь не выбирает фото повторно на шаге подтверждения — проверить
   именно после того, как форма скрыта (это ломается, если `File` остался
   только в `ref`).
4. **Оба** входа подачи показаний — хаб аренды и карточка объекта — показывают
   шаг подтверждения. Карточка объекта не пишет «Принято», пока запись не
   создана.
5. Если между шагами появилось другое показание, подтверждение не сохраняет
   старые числа: возвращается новый `requiresConfirmation` с пересчитанными
   расходом и суммой.
6. Отключённый счётчик стоит ниже активных и на карточке объекта, и в хабе
   аренды.
7. Пустое состояние счётчиков различается для собственника и арендатора.
8. На расторгнутом договоре: видны все вкладки (включая экран истории
   показаний) и пометка «Архив»; доступен последний счёт; видны подписанные
   сканы; скрыты «Внести», блок текущего периода, все действия на экране
   заявок и форма чата; пустые состояния сформулированы в прошедшем времени;
   **действия по оплате счёта работают**.
9. По расторгнутому договору прямые вызовы API отвечают 409 и ничего не
    меняют — не только кнопки спрятаны: создание заявки, смена её статуса и
    подтверждение урегулирования. Проверять вызовом API, а не через
    интерфейс.
9a. В архиве не показываются «Сформировать счёт» и «Добавить статью», даже
    если черновик пережил расторжение; оплата при этом доступна.
9b. Подписанный скан из архива открывается обеими сторонами, а не только
    числится строкой «Загружен».
10. Диалог показаний, открытый до расторжения, не остаётся рабочим после того,
    как polling принёс новый статус.
11. На активном договоре навигация и все действия — как раньше.
12. Счета разделены на «Требуют действия» и «Историю» по роли; матрица
    проверена для обеих ролей и всех статусов (`draft`, `final+pending`,
    `final+payment_claimed`, `final+paid`, `final+null`): каждый счёт ровно в
    одной группе. Самая старая просрочка первой. Оплаченный счёт не подписан
    «к оплате».
13. Пока роль и статус не известны (не загружены `lease`/`user`), не
    рендерятся ни список счетов по правилам ролей, ни форма чата, ни действия
    на экране заявок.
14. Сбой первой загрузки на экранах счетов и счётчиков показывает ошибку с
    «Повторить»; сбой фонового опроса при уже показанных данных — только
    баннер, данные и пустые состояния остаются на месте; «Загрузка…» не
    появляется каждые 30 секунд.
15. Ветки изменившейся базы покрыты: база выросла выше введённого → 400;
    аномалия сохранилась → повторное подтверждение с новыми числами; аномалия
    исчезла → подтверждение с `warning: null` и нейтральным текстом.
    Подтверждение без `expectedPreviousValue` → 400, ничего не сохранено.
16. Все команды из раздела «Проверка» проходят; тесты покрывают пункты 1, 2,
    5, 9, 15.
