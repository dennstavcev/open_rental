> **несколько** `pending`-заявок на договор и захват одной строки гонку не
> закрывает; добавлено явное дочитывание строки (`updateMany` возвращает
> только `count`, а методы обязаны вернуть сущность); бросок при неудачном

> правило о побочных эффектах (создание `Service` обязано остаться в
> транзакции); контур приглашений расширен на `send`/`cancelInvitation`;
> добавлен раздел фронта — новый 409 иначе становится необработанным
> rejection.
>
> Все дефекты **существовали до Фазы 13**. Механизм лечения один: условный
> атомарный `updateMany` вместо «прочитал снимок → безусловно записал»,
> уже отработанный в Фазе 13.
>
> **ADR не нужен:** контракты сущностей и модель данных не меняются, миграций
> нет. Но **поведение API меняется**: где параллельный запрос молча выигрывал
> гонку, теперь возвращается 409. Фиксируется в `docs/CHANGELOG.md`.

## Общее правило

```ts
const claimed = await tx.model.updateMany({
  where: { id, /* + все поля, на снимке которых основано решение */ },
  data: { /* … */ },
});
```

Что делать при `count !== 1` — зависит от того, что уже записано:

| Эффект | Где выполняется |
|---|---|
| Связанные записи БД (создание `Service`, проставление `tenantId`) | **Внутри** той же транзакции |
| Бросок при неудачном захвате, если часть транзакции уже записана | **Внутри** транзакции — только так откатится записанное |
| Уведомления, вызовы биллинга, любые внешние эффекты | **После** коммита и только при успешном захвате |

Ошибка ревизии 1 была в том, что правило требовало выносить наружу *все*
побочные эффекты. Для `Service` это создало бы новую дыру: услуга,
созданная после коммита, не откатится вместе с заявкой.

### Порядок захвата строк — обязателен и единый

Там, где транзакция трогает **и** `Lease`, **и** `Invitation`, захват идёт
строго в порядке **`Lease` → `Invitation`**. Всегда, во всех методах.

Это не стилистика. Ревизия 2 разошлась: `acceptInvitation` брала
`Invitation → Lease`, а `send`/`cancelInvitation` — `Lease → Invitation`.
Две транзакции, идущие навстречу, дают взаимную блокировку, и PostgreSQL
убьёт одну из них по deadlock detection. Разный порядок захвата опаснее той
гонки, которую мы чиним, потому что проявляется как случайный 500 под
нагрузкой.

## 1. Расхождение суммы (`maintenance.service.ts`)

### Механизм

`proposeSettlement` читает снимок через `load()`, проверяет
`settlementAppliedAt`, затем делает **безусловный** `update`, переписывая
сумму, плательщика и сбрасывая подтверждения.

`confirmSettlement` в применяющей ветке захватывает заявку по
`{ id, settlementAppliedAt: null }`, но `Service` создаёт с ценой
`request.settlementAmount!` — **из снимка, прочитанного до транзакции**.

1. A предлагает 1000 ₽.
2. B вызывает `confirmSettlement`, снимок читает 1000 ₽.
3. A успевает предложить 2000 ₽ — строка обновлена, подтверждения сброшены.
4. Транзакция B видит `settlementAppliedAt === null`, захватывает заявку и
   создаёт `Service` **на 1000 ₽**, тогда как в заявке 2000 ₽.

Арендатору выставляется счёт на сумму, которой никто не подтверждал.

### Правка

**`confirmSettlement`, применяющая ветка** — пин на весь снимок:

```ts
const claimed = await tx.maintenanceRequest.updateMany({
  where: {
    id: request.id,
    settlementAppliedAt: null,
    // Пин на прочитанный снимок: если вторая сторона успела изменить
    // условия, захват не сработает и услуга не создастся по устаревшей цене.
    settlementAmount: request.settlementAmount,
    settlementPayer: request.settlementPayer,
    confirmedByTenant: request.confirmedByTenant,
    confirmedByLandlord: request.confirmedByLandlord,
  },
  data: {
    confirmedByTenant: true,
    confirmedByLandlord: true,
    settlementAppliedAt: appliedAt,
  },
});
```

`Decimal` сравнивается корректно: Prisma сериализует его в decimal-литерал,
PostgreSQL сравнивает `numeric` по значению (`1000`, `1000.0`, `1000.00`
равны). Никаких строковых обходных путей не нужно.

Создание `Service` — **внутри** транзакции и только при `claimed.count === 1`
(как сейчас). При `count === 0` бросить **внутри транзакции**:

```
ConflictException('Условия урегулирования изменились или уже применены — обновите страницу')
```

Текст намеренно широкий: `count === 0` означает не только смену суммы, но и
параллельное применение или изменение подтверждений. Обещать пользователю
конкретную причину, которую мы не выясняли, нельзя.

**`proposeSettlement`** — условный захват:

```ts
const claimed = await this.prisma.maintenanceRequest.updateMany({
  where: { id: request.id, settlementAppliedAt: null },
  data: { /* amount, payer, confirmedBy* */ },
});
```

`count === 0` → `ConflictException('Сумма уже согласована и применена')`
(тот же текст, что в существующей проверке по снимку). Проверку по снимку
**оставить** — быстрый путь с точным сообщением; захват страхует от гонки.

После захвата дочитать строку `findUniqueOrThrow` и вернуть её.

### Edge cases

- уведомление контрагенту в `proposeSettlement` — только при `count === 1`
  и после коммита;
- `maintenance_settlement_applied` уже завязано на `result.applied` —
  проверить, что после правки оно завязано на новый, более строгий захват;
- частичная ветка `confirmSettlement` уже условная (Фаза 13) — не трогать.

## 2. Двойная финализация расторжения (`termination.service.ts`)

### Механизм

`finalize` читает заявку, проверяет `status !== pending` → бросок. Затем
транзакция делает **безусловные** `lease.update` и
`terminationRequest.update`. Условного захвата нет вообще.

**Две разные гонки, и захват заявки закрывает только первую:**

1. Двойной клик по одной заявке — оба запроса видят `pending`, оба проходят.
2. **Две разные `pending`-заявки на один договор** (схема это допускает:
   `TerminationRequest` не имеет уникальности по `leaseId`+`status`) — каждый
   запрос успешно захватит **свою** строку, и оба перепишут `Lease` и оба
   вызовут биллинг. Захват заявки здесь бесполезен.

### Правка

Внутри транзакции — **два** захвата, договор первым:

```ts
// Договор: закрывает гонку двух РАЗНЫХ заявок по одному договору.
const leaseClaimed = await tx.lease.updateMany({
  where: { id: lease.id, status: LeaseStatus.active },
  data: {
    status: LeaseStatus.terminated,
    effectiveEndDate,
    ...(dto.depositReturnAmount !== undefined
      ? { depositReturnAmount: dto.depositReturnAmount }
      : {}),
  },
});
if (leaseClaimed.count !== 1) {
  throw new ConflictException('Договор уже расторгнут');
}

// Заявка: закрывает двойной клик по одной и той же заявке.
const claimed = await tx.terminationRequest.updateMany({
  where: { id, status: TerminationStatus.pending },
  data: {
    status: TerminationStatus.finalized,
    finalizedById: userId,
    finalizedAt: new Date(),
    periodEndOverride: override,
  },
});
if (claimed.count !== 1) {
  throw new ConflictException('Заявка уже обработана');
}

// Остальные pending-заявки по этому договору больше не могут быть
// финализированы (захват Lease по status: active им не дастся), но
// висели бы как «ожидает» вечно. Закрываем их явно.
await tx.terminationRequest.updateMany({
  where: {
    leaseId: lease.id,
    status: TerminationStatus.pending,
    id: { not: id },
  },
  data: { status: TerminationStatus.cancelled },
});

// updateMany возвращает только count — сущность дочитываем явно.
return tx.terminationRequest.findUniqueOrThrow({ where: { id } });
```

`TerminationStatus.cancelled` в схеме уже есть (`schema.prisma`, enum на
строке 459) — миграция не нужна.

**Остаточный риск, который этим не закрывается:** `create` может создать
новую заявку по устаревшему снимку уже после расторжения — она не изменяет
`Lease`, поэтому захватывать нечего. Ущерб ограничен: такую заявку никогда
не удастся финализировать (захват `Lease` по `status: active` не дастся).
Записать в `docs/DEV_STATE.md`.

Оба броска — **внутри** транзакции: только так откатится уже записанный
захват договора, если заявку захватить не удалось.

Снаружи транзакции: `billing.applyTermination` и уведомление выполняются
только если транзакция не бросила (то есть оба захвата удались).

Существующие проверки по снимку (`status !== pending` → бросок,
`landlordId !== userId` → Forbidden) **оставить** — быстрый путь.

### Явно НЕ чиним (и почему)

`applyTermination` вызывается **после** коммита; при его падении договор
остаётся `terminated` без последнего счёта, а повторный вызов получает
«заявка уже обработана». Условным захватом это не лечится: нужно либо
втягивать биллинг в ту же транзакцию (у него своя логика и свои транзакции),
либо делать финализацию возобновляемой — отдельная задача с собственным
проектным решением.

Эта правка **сужает** проблему (двойной вызов биллинга исчезает), но не
устраняет её. Запись в `docs/DEV_STATE.md` **сохранить**, переформулировав.

## 3. Согласованность приглашения и договора (`leases.service.ts`)

### Механизм

`acceptInvitation` и `declineInvitation` читают приглашение через
`getPendingInvitationFor`, затем делают **безусловный** `update` статуса.
Параллельные принятие и отказ дают договор с привязанным арендатором и
приглашением «отклонено» (или наоборот).

Шире: `send` и `cancelInvitation` тоже проверяют состояние снимком
(`getOwnedInvitable`) и затем **безусловно** меняют `Lease`. Возможны
`draft` с заполненным `tenantId` (accept гонится с cancel) и новое
pending-приглашение при уже привязанном арендаторе (accept гонится с send).
Чинить только accept/decline — оставить контур дырявым наполовину.

### Правка

**`acceptInvitation`** — внутри существующей транзакции. Порядок строго
`Lease` → `Invitation` (см. общее правило о порядке захвата):

```ts
// СНАЧАЛА договор — тот же порядок, что в send/cancelInvitation.
// Обратный порядок дал бы взаимную блокировку с ними.
const leaseClaimed = await tx.lease.updateMany({
  where: { id: lease.id, tenantId: null },
  data: { tenantId: user.id },
});
if (leaseClaimed.count !== 1) {
  throw new ConflictException('К договору уже привязан арендатор');
}

const claimed = await tx.invitation.updateMany({
  where: { id: invitationId, status: InvitationStatus.pending },
  data: { status: InvitationStatus.accepted },
});
if (claimed.count !== 1) {
  // ВНУТРИ транзакции: иначе tenantId закоммитится, а приглашение
  // останется pending — ровно то расхождение, которое мы чиним.
  throw new ConflictException('Приглашение уже обработано');
}
```

Уведомление `invitation_accepted` — после коммита.

**`declineInvitation`**:

```ts
const claimed = await this.prisma.invitation.updateMany({
  where: { id: invitationId, status: InvitationStatus.pending },
  data: { status: InvitationStatus.declined },
});
if (claimed.count !== 1) {
  throw new ConflictException('Приглашение уже обработано');
}
```

Уведомление `invitation_declined` — только при `count === 1`.

**`send`** — захват договора по ожидаемому состоянию, внутри существующей
транзакции:

```ts
const leaseClaimed = await tx.lease.updateMany({
  where: {
    id: leaseId,
    tenantId: null, // арендатор не должен был привязаться, пока мы читали
    status: { in: [LeaseStatus.draft, LeaseStatus.sent] },
  },
  data: { status: LeaseStatus.sent },
});
if (leaseClaimed.count !== 1) {
  throw new ConflictException('К договору уже привязан арендатор');
}
```

Создание нового `Invitation` и отзыв прежних — после успешного захвата,
в той же транзакции.

**`cancelInvitation`** — тем же приёмом, захват по
`{ id: leaseId, status: LeaseStatus.sent, tenantId: null }`, при
`count !== 1` → `ConflictException('Договор уже изменился')`.

Существующие проверки `getOwnedInvitable` / `getPendingInvitationFor`
**оставить**: они дают точные сообщения и проверяют права, чего условный
захват не делает.

### Граница

Ограничиваемся захватом переходов состояния в этих четырёх методах.
Пересмотр модели приглашений (уникальность pending на договор, отдельный
статус договора) — **не** в этой задаче; если по ходу окажется, что без
этого не закрыть, остановиться и сообщить.

## 4. Фронт: обработка нового 409

Новый 409 сам по себе контракт не ломает, но текущий фронт к нему не готов.

**`frontend/app/leases/[id]/requests/page.tsx`, `RequestCard.run()`** —
сейчас `try/finally` **без `catch`**: любой отказ уходит в необработанный
rejection, `reload()` пропускается, экран остаётся с устаревшими данными.
Это уже дефект (403 и существующие 409 ведут себя так же), но новый захват
делает его частым. Добавить `catch`: показать сообщение из `ApiError` и
**всё равно вызвать `reload()`** — после проигранной гонки экран обязан
показать актуальное состояние, иначе пользователь снова нажмёт ту же кнопку.

Сообщение показывать существующим для этого экрана способом; если своего
состояния ошибки у `RequestCard` нет — прокинуть его от родителя, как это
сделано для `reload`.

**Экран договора `frontend/app/leases/[id]/page.tsx`** — новый 409 приходит
и сюда, из `send` и `cancelInvitation`. `onSend` и `onCancelInvite`
показывают ошибку, но `load()` после конфликта не вызывают: собственник
видит устаревший блок «Приглашение» и жмёт ту же кнопку снова. Добавить
перечитывание в ветке ошибки.

**Экран расторжения и экран приглашений** — там же: `load()` сейчас
выполняется только при успехе. Добавить перечитывание после отказа.

**Кнопка финализации расторжения** показывается для `pending`-заявки даже
когда договор уже `terminated`. После правки backend такая заявка будет
переведена в `cancelled` в той же транзакции, поэтому в норме кнопка
исчезнет сама. Но заявка, созданная по устаревшему снимку уже после
расторжения (остаточный риск из пункта 2), останется `pending` — поэтому
на фронте дополнительно скрыть действие финализации при
`lease.status !== 'active'`. Это дешевле и честнее, чем показывать кнопку,
которая гарантированно вернёт 409.

Общий принцип для всех четырёх правок: **после проигранной гонки экран
обязан показать актуальное состояние**, иначе пользователь повторит то же
действие с тем же результатом.

## Тесты

`maintenance.service.spec.ts`, `termination.service.spec.ts`,
`leases.service.spec.ts`:

1. `confirmSettlement`: при `count === 0` бросает `ConflictException` и
   **`Service` не создаётся**.
2. `confirmSettlement`: при успешном захвате создаёт `Service` и уведомляет
   один раз.
3. `proposeSettlement`: при `count === 0` бросает и не уведомляет.
4. `termination.finalize`: при неудачном захвате **договора** бросает, **не
   вызывает `applyTermination`**, не уведомляет.
5. `termination.finalize`: при неудачном захвате **заявки** бросает и не
   вызывает `applyTermination` (захват договора должен откатиться).
6. `termination.finalize`: при успехе вызывает `applyTermination` ровно раз
   и возвращает дочитанную заявку.
7. `acceptInvitation`: неудачный захват приглашения → бросок, `tenantId` не
   проставлен, уведомления нет.
8. `acceptInvitation`: неудачный захват договора → бросок **внутри
   транзакции** (проверить, что уведомление не отправлено).
9. `declineInvitation`: неудачный захват → бросок, landlord не уведомлён.
10. `send`: неудачный захват договора → бросок, новое приглашение не создано.
11. `cancelInvitation`: неудачный захват → бросок.
12. `termination.finalize`: при успехе остальные `pending`-заявки этого
    договора переведены в `cancelled`, а заявка другого договора — нет.
13. Порядок захвата: в `acceptInvitation` `lease.updateMany` вызывается
    **раньше** `invitation.updateMany` (проверяется порядком вызовов моков).
    Тот же порядок в `send` и `cancelInvitation`.

**Честная граница тестов.** Все спеки проекта — unit с замоканной Prisma.
Они проверяют **ветвление** (нет побочных эффектов при `count === 0`), но
не проверяют, что SQL действительно выполняет CAS, и не воспроизводят
реальную конкурентность. Интеграционного стенда на PostgreSQL в проекте нет
вообще — его заведение остаётся отдельной задачей, **записать это в
`docs/DEV_STATE.md`**, а не делать вид, что unit-тесты закрывают вопрос.
Фактическую конкурентность проверю вручную на живой БД после реализации.

## Критерии приёмки

- [ ] `cd backend && npm run build && npm test` — зелено.
- [ ] `cd frontend && npm run build && npx tsc --noEmit` — зелено.
- [ ] Ни один побочный эффект (создание `Service`, `applyTermination`, любое
      уведомление, проставление `tenantId`, создание `Invitation`) не
      выполняется при `count === 0`.
- [ ] Записи БД, сделанные до неудачного захвата, откатываются — бросок
      внутри транзакции, а не после неё.
- [ ] Проигравший гонку запрос получает 409, а не молчаливый успех.
- [ ] Существующие проверки по снимку сохранены как быстрый путь.
- [ ] Порядок захвата `Lease` → `Invitation` соблюдён во всех методах,
      трогающих обе строки — дедлока по встречному порядку нет.
- [ ] `RequestCard.run()` не оставляет необработанный rejection и
      перечитывает данные после отказа.
- [ ] После 409 перечитывают данные все четыре экрана: заявки, договор,
      расторжение, приглашения.
- [ ] Действие финализации не показывается при `lease.status !== 'active'`.
- [ ] Миграций нет, схема БД не изменена.
- [ ] `docs/DEV_STATE.md` не числит закрытое открытым и не числит открытое
      закрытым.
