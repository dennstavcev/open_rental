# Бриф на редизайн (для сессии в WSL со Stitch)

Рабочий документ этапа. Решение и обоснование —
`docs/adr/0023-visual-redesign-tailwind-stitch.md`. Статус этапов —
`docs/DEV_STATE.md`, раздел «Редизайн (ADR-0023)». Удаляется после мержа
`redesign/stitch` в `main`.

## Что прочитать до первого действия

1. Корневой `CLAUDE.md` — правила ведения документации, они обязательны.
2. `docs/adr/0023-visual-redesign-tailwind-stitch.md` — целиком.
3. `docs/DEV_STATE.md` — раздел «Редизайн (ADR-0023)» и «Как запустить /
   проверить».
4. `docs/USER_FLOWS.md`, `docs/MVP_SCOPE.md`, `docs/IDEA.md` — что вообще
   за продукт.
5. `docs/DESIGN_SYSTEM.md` — **действующая** система. На этапе R4 она
   переписывается, но раздел «Тон и стиль текста» переносится в новую
   почти без изменений: тон уже утверждён продуктом, не переизобретать.

## Среда — три вещи, которые ломаются чаще всего

- **npm-команд не запускать вообще.** Ни `install`, ни `run dev`, ни
  `run build`. В `frontend/node_modules` лежит
  `@next/swc-win32-x64-msvc` — установка из WSL подменит нативные
  бинарники на linux-овые и сломает запуск на стороне Windows. Нужны
  пакеты или сборка — остановиться и попросить владельца выполнить их на
  Windows (см. «Чекпоинты»).
- **Дев-сервер поднимает владелец на Windows**, `http://localhost:3001`.
  Из WSL он доступен: в `.wslconfig` включён `networkingMode=mirrored`.
  Проверять свою работу — по этому адресу.
- **Правки только в исходниках.** Файлы лежат на NTFS через `/mnt/c`,
  Next подхватывает изменения по HMR. Если пересборка не подхватилась —
  это повод попросить перезапуск, а не чинить сборку из WSL.

## Инварианты (нарушение = ошибка, а не «улучшение»)

- `frontend/lib/*` **не трогать** — 17 модулей, контракт с backend.
  Понадобилась правка там — записать в чекпоинт и спросить, не чинить
  по ходу.
- Продуктовое поведение экранов сохраняется 1:1. Редизайн — про визуал
  и структуру компонентов. Логика ADR-0016 (polling), ADR-0021/0022 (ПДн,
  согласие) не пересматривается.
- Тексты интерфейса не переписывать «под красоту»: тон утверждён
  (`docs/DESIGN_SYSTEM.md`, «Тон и стиль текста»), эмодзи не
  используются нигде.
- Работа идёт в ветке `redesign/stitch`. Не коммитить в `main`,
  не пушить без явной просьбы.
- Направление правок дизайна: **Stitch → код**. Не подкручивать визуал
  в коде мимо макета.

## Этапы

### R1 — дизайн в Stitch, кода нет

1. Завести Stitch-проект и загрузить в него **текущее** приложение,
   чтобы Stitch редизайнил именно этот продукт, а не рисовал абстрактный
   SaaS: скиллы `stitch-extract-design-md` (по `frontend/`),
   `stitch-extract-static-html` (по ключевым экранам с запущенного
   `localhost:3001`), `stitch-code-to-design` (загрузка).
2. Конституция проекта — скилл `site-md`, на вход `docs/IDEA.md`,
   `docs/USER_FLOWS.md`, `docs/MVP_SCOPE.md` и раздел «Тон и стиль
   текста» из `docs/DESIGN_SYSTEM.md`.
3. **Чекпоинт 1 — выбор направления.** Сгенерировать варианты 3 опорных
   экранов: `/login`, `/dashboard` («Сегодня») и `/leases/[id]` (хаб
   договора — самый плотный, 493 строки). Дальше не идти: направление
   выбирает владелец продукта.
4. После выбора — зафиксировать дизайн-систему
   (`stitch-manage-design-system`): палитра, типографика, шкала отступов,
   радиусы, тени, состояния компонентов.
5. **Чекпоинт 2 — утверждение дизайн-системы.** Показать её до прогона
   на остальные экраны, иначе 19 экранов разъедутся между собой.
6. По утверждённой системе — все экраны. Полный список ниже. Каждый
   экран рисуется **со состояниями**: пусто, загрузка, ошибка,
   просрочено, «ждём вторую сторону». Состояние, не нарисованное в
   Stitch, потом доделывается в коде на глаз — именно там теряется
   полировка.
7. Десктопная сетка обязательна. Сейчас в `globals.css` четыре
   медиазапроса и мобильный макет по центру широкого экрана — это как
   раз то, что чинится.

**Экраны (19):** `/` · `/login` · `/register` · `/onboarding` ·
`/dashboard` · `/properties` · `/properties/[id]` · `/invitations` ·
`/notifications` · `/reports` · `/legal/privacy` · `/leases/[id]` ·
`/leases/[id]/bills` · `/leases/[id]/chat` · `/leases/[id]/meters` ·
`/leases/[id]/meters/[meterId]/history` · `/leases/[id]/party-info` ·
`/leases/[id]/requests` · `/leases/[id]/termination`.

### R2 — фундамент в коде

1. **Чекпоинт 3 — установка пакетов.** Составить точный список
   (Tailwind 3.4 + postcss/autoprefixer, зависимости выбранных
   примитивов shadcn/ui) и попросить владельца выполнить установку на
   Windows. Самому не запускать.
2. Tailwind-тема ссылается на CSS custom properties, а не дублирует
   значения хардкодом. Механизм «семантические алиасы поверх сырых
   токенов» из текущего `globals.css` сохраняется — он себя оправдал.
3. Примитивы shadcn/ui копируются в `frontend/components/ui/` и
   перекрашиваются под тему. Это не UI-кит целиком: продуктовые
   компоненты (`Row`, `PageHeader`, `LeaseTabs`, `EmptyState`, `Sheet`,
   `Segmented`) переписываются своими поверх примитивов.
4. Оболочка: `app/layout.tsx`, `TopBar`, навигация, фон.

### R3 — перенос экранов

По одному, от оболочки к листьям. Порядок разумный: `/login` →
`/register` → `/dashboard` → `/leases/[id]` → вкладки договора →
остальное.

Правила переноса:

- Разметку выносить в компоненты, а не оставлять в `page.tsx`. Сейчас
  4062 строки в `app/` против 660 в `components/` — это и есть причина,
  по которой правка дизайна требует обхода всех экранов вручную.
- Каждый перенесённый экран проверять живьём на `localhost:3001`.
  Фронтовых тестов **ноль**, CI гоняет только `npm run build` — сеть
  ловит лишь ошибки компиляции, но не то, что экран поехал.
- Способ проверки — из `docs/DEV_STATE.md`, раздел «Как запустить /
  проверить»: throwaway-аккаунты через `POST /api/auth/register`, вход
  не через форму, а токенами в `localStorage`
  (`softrent.accessToken` / `softrent.refreshToken`). После проверки —
  убирать за собой по инструкции оттуда же.
- Старые классы из `globals.css` удаляются по мере переноса, а не
  «потом»: файл на 1544 строки и 159 классов иначе останется навсегда.

### R4 — документация

- `docs/DESIGN_SYSTEM.md` переписать из нового Stitch-проекта. Раздел
  «Тон и стиль текста» перенести. Старую редакцию и происхождение
  (Claude Design handoff, 2026-07-23) оставить исторической справкой.
- `.claude/agents/designer.md` — источник дизайна с MCP `claude_design`
  на Stitch; правило «референс — отправная точка, не спецификация»
  сохранить.
- Записи в `docs/CHANGELOG.md`, статус в `docs/ROADMAP.md`, этапы в
  `docs/DEV_STATE.md`.

## Чекпоинты — где обязательно остановиться

Владелец продукта работает асинхронно: он может уйти и вернуться через
несколько часов. Поэтому на чекпоинте нужно **не просто спросить в чат**,
а записать вопрос и варианты в `docs/DEV_STATE.md` (блок этапов R0–R4),
чтобы ответ можно было дать позже и из другой сессии.

| № | Когда | Что нужно от человека |
|---|---|---|
| 1 | R1, после вариантов 3 опорных экранов | выбрать направление дизайна |
| 2 | R1, перед прогоном на все экраны | утвердить дизайн-систему |
| 3 | R2, до первой строки кода | выполнить установку пакетов на Windows |
| 4 | R3, после первых 2–3 перенесённых экранов | подтвердить, что перенос идёт в нужную сторону |
| 5 | перед мержем `redesign/stitch` в `main` | приёмка |

Между чекпоинтами работать самостоятельно и не спрашивать разрешения на
каждый шаг — вопросы копить и задавать пачкой на ближайшем чекпоинте.

## Как вести статус

Свой прогресс писать **только** в блок этапов R0–R4 в
`docs/DEV_STATE.md`. Остальные разделы файла не переписывать: их ведут
две другие параллельные сессии (планирующий чат и чат разработки), и
этот файл — единственный канал синхронизации между всеми тремя.
