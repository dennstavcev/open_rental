# Структура агентной команды

Разработка ведётся в CLI (Claude Code, модель Fable 5/Opus) через набор
сабагентов, определённых в `.claude/agents/`. Ниже — иерархия,
режим работы и правила эскалации. Это процессное решение проекта,
зафиксировано как `ADR-0002` (`docs/adr/0002-agent-team-structure.md`),
состав ролей обновлён `ADR-0010` (добавлена `designer`,
`docs/adr/0010-add-designer-role.md`).

## Иерархия

```
                          project-ceo
                               |
   -------------------------------------------------------------------
   |          |          |          |           |          |          |          |
product-   architect   designer  backend-   frontend-    qa-      devops   security
analyst                             dev        dev      engineer
   \__________________________________________________________________/
                               |
                          docs-keeper
        (проверяет документацию по каждому решению любого агента)
```

`project-ceo` — единственная точка приёмки. Ни один агент не помечает
свою задачу как завершённую самостоятельно — решает CEO на основе
отчёта и собственной проверки.

## Роли коротко

| Агент | Отвечает за | Не делает |
|---|---|---|
| `project-ceo` | Декомпозиция, параллельный запуск, приёмка, разрешение конфликтов | Не пишет код и фичи сам |
| `product-analyst` | Требования, сценарии, backlog, `docs/IDEA.md` | Не решает архитектуру/стек/визуал |
| `architect` | Архитектура, модель данных, API-контракты, ADR | Не пишет прикладной код |
| `designer` | Дизайн-система, спеки экранов из референсов (Figma и т.п.) и сценариев | Не решает продуктовые вопросы (что делает фича) |
| `backend-dev` | Реализация сервера по контракту architect | Не меняет контракт без согласования |
| `frontend-dev` | Реализация клиента по контракту architect и спеке designer | Не додумывает визуал сам, не читает сырые референсы как спецификацию |
| `qa-engineer` | Тест-планы, проверка критериев приёмки, баг-репорты | Не чинит баги сам |
| `devops` | CI/CD, окружения, деплой | Не проектирует архитектуру приложения |
| `security` | Ревью доступа/данных, блокировка релиза при критичных находках | Не пишет фичи |
| `docs-keeper` | Синхронизация ADR/ROADMAP/CHANGELOG | Не принимает продуктовые/архитектурные решения — только фиксирует |

## Режим параллельного взаимодействия

Это обязательный режим, а не опция:

1. CEO раскладывает крупную задачу на независимые куски по ролям.
2. Куски без взаимных зависимостей запускаются параллельно (несколько
   вызовов `Task` в одном сообщении CEO).
3. Куски с зависимостями (например, `backend-dev` ждёт контракт от
   `architect`) запускаются только после того, как CEO принял
   блокирующую часть — не после того, как она просто "сдана".
4. `qa-engineer` и `docs-keeper` подключаются на выходе почти любого
   куска — тестирование и документирование не откладываются "на потом".
5. `designer` работает на шаг впереди `frontend-dev`: спека экрана
   должна быть готова до того, как `frontend-dev` начинает вёрстку, не
   параллельно с ней.

## Эскалация

- Агент не может закрыть открытый вопрос за пределами своей роли
  (например, `backend-dev` не решает продуктовый вопрос) — эскалирует
  CEO, который направляет вопрос профильному агенту или пользователю
  (владельцу продукта), если вопрос продуктовый и не закрыт в
  `docs/PRODUCT_QUESTIONS.md` / `docs/IDEA.md`.
- `qa-engineer` и `security` имеют право заблокировать приёмку — CEO не
  принимает решение, отменяющее их блокировку, без явного нового
  аргумента, зафиксированного в отчёте.
- Конфликт между агентами по архитектурному вопросу решает CEO,
  результат фиксируется как ADR через `architect`/`docs-keeper`.

## Определение "готово" на уровне проекта

Задача/этап считается готовым, когда одновременно верно:

1. Реализация соответствует зафиксированным требованиям и архитектуре.
2. `qa-engineer` подтвердил прохождение критериев приёмки.
3. `security` не имеет открытых критичных находок по этой части.
4. `docs-keeper` подтвердил синхронизацию документации.
5. `project-ceo` принял результат явно (не по умолчанию).

Без пункта 5 задача не считается завершённой, даже если все остальные
пункты выполнены.
