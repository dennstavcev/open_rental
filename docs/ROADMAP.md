## Phase 1 — MVP

Статус: **в работе** (старт 2026-07-21)

**Технические развилки перед стартом (аудит 2026-07-22,
`docs/READINESS_AUDIT.md`) — закрыты, кроме хостинга/юр.части
(сознательно, тесты пока на localhost):**

- [x] Backend-фреймворк — NestJS (ADR-0004)
- [x] Модульный монолит (ADR-0005)
- [x] Механизм аутентификации — email+пароль, собственный JWT (ADR-0006)
- [x] Файловое хранилище — интерфейс + локальная реализация для
      localhost (ADR-0007); провайдер для прод — вместе с хостингом
- [x] OCR-движок для показаний счётчика — Tesseract (ADR-0008)
- [x] Realtime чата — не обязателен в MVP (ADR-0009)
- [~] **Хостинг и локализация ПДн (152-ФЗ)** — направление решено
      (2026-08-19, ADR-0021): сервер с российской локализацией, оператор
      ПДн — ИП или самозанятый. Закрывает требование 152-ФЗ ст. 18.
      Фактическое поднятие инфраструктуры хостинга — отдельная задача,
      не блокирует разработку на localhost.
- [ ] **Юридический текст договора / оферта** — сознательно отложено,
      требует юриста, не блокирует разработку на localhost

Модули и экраны — подробно в `docs/MVP_SCOPE.md`.

**Frontend (Next.js, ADR-0001/0003) — в работе:** скаффолд App Router +
Auth (регистрация/вход, JWT access+refresh, auth-context) + модуль
объектов (список/создание) ✓. UI — функциональный placeholder
(дизайн-спеки `designer` из Claude Design недоступны в среде). Остальные
экраны (договоры, платежи, чат, отчёты) — следующими инкрементами.

- [~] Auth: регистрация/вход, роли landlord/tenant, онбординг собственника
      — **в работе**: скаффолд backend NestJS + модуль Auth
      (register/login/refresh/logout/me, JWT access+refresh, argon2).
      Онбординг собственника (мастер) — следующим шагом.
- [~] Модуль объектов: список объектов, карточка объекта — **в работе**:
      Property core CRUD (list/create/get/update, scoped к владельцу)
      ✓; каталог на объекте — счётчики (Meter config: тип/название/тариф)
      и услуги (Service: цена/тип monthly|one_time) ✓; фото объекта и
      показания счётчиков (MeterReading) отложены до Documents/storage +
      OCR + tenant-доступа (модуль биллинга).
- [~] Модуль договоров: мастер создания договора по шаблону РФ (или
      загрузка готового файла), отправка арендатору, загрузка сканов
      подписанного документа обеими сторонами (см. `docs/MVP_SCOPE.md`)
      — **в работе**. Инкремент 1: `Lease` core (draft/sent) +
      `Invitation` (отправка арендатору по email, accept/decline,
      привязка tenant) ✓; с 2026-08-20 (ADR-0020) приглашение видно
      отправителю, переотправляется на исправленный адрес и отзывается,
      а договор отдаётся вместе с объектом и сторонами (`LeaseView`) ✓.
      Отложено: активация (`active`) через сканы
      `LeaseDocument` — нужен `StorageProvider`; генерация текста договора
      (шаблон/PDF); расторжение и режим коммуналки — модуль биллинга.
      Персональные данные сторон (`LeasePartyInfo`) — см. отдельный пункт
      ниже, статус менялся дважды за 2026-08-19 (ADR-0017 → ADR-0021).
      Инкремент 2: `StorageProvider` (ADR-0007) + `LocalFsStorageProvider`
      + `LeaseSignedScan` — активация `sent`→`active` по загрузке сканов
      с подписью обеими сторонами ✓.
      Инкремент 3 (2026-08-19): акт приёма-передачи имущества —
      `LeaseInventoryItem` + Приложение №1 «Акт приёма-передачи имущества»
      (тип техники, бренд, модель, количество), версионируется как второй
      `kind` в `LeaseDocument` (ADR-0018) ✓ — бэкенд и фронт: шаг «Опись
      имущества» в мастере сдачи объекта, секции описи и акта на карточке
      договора (правка описи — собственнику и только в черновике) ✓. Не
      зависел от статуса ПДн и не пересматривался вместе с ним.
      Инкремент 4 (2026-08-20, ADR-0021): персональные данные сторон
      (ФИО/паспорт/адрес регистрации/телефон) возвращены в текст
      договора — `LeasePartyInfo` (backend), обе стороны, field-level
      шифрование (`CryptoService`, AES-256-GCM) ✓. Фронт-экран сбора
      данных — ещё не реализован (см. пункт ниже).
- [~] Модуль платежей и коммуналки: настройка платежей по договору,
      счета (гибкий состав), показания счётчиков (ручной ввод + фото),
      фиксация факта оплаты вручную (без эквайринга) — **в работе**.
      Инкремент 1: `Bill` (draft→final) + `BillLineItem` + `Payment`,
      расчётный период, статусы pending→payment_claimed→paid (ADR-0012),
      пеня (ленивый расчёт), прощение пени ✓. Инкремент 2:
      `MeterReading` (фото + **замоканный OCR**) + коммунальная строка +
      гард финализации при непо́данных показаниях ✓.
      Планировщик авто-перехода периодов — `@nestjs/schedule`,
      идемпотентный скан (ADR-0013; BullMQ отложен) ✓.
      Инкремент 3 (2026-08-20, ADR-0019): заявление об оплате только с
      чеком (`PaymentProof`, замена до подтверждения, виден обеим
      сторонам и после оплаты) + реквизиты арендодателя для перевода
      (`User.payoutPhone`/`payoutBankName`/`payoutNote`, блок «Куда
      платить» с копированием на экране счетов) ✓.
      **Отложено (флаг):** полный таймзонный авто-переход по
      `Property.timezone` (сейчас границы 12:00 UTC); BullMQ/Redis
      (ADR-0013); реальный Tesseract OCR (ADR-0008); уведомления —
      модуль Notifications.
- [~] Модуль коммуникации: чат по договору, заявки на обслуживание со
      статусами — **в работе**. Заявки (Maintenance): tenant создаёт
      (опц. фото), landlord ведёт статус (open→in_progress→resolved),
      двустороннее согласование суммы урегулирования → строка в текущий
      счёт (доля арендатора) ✓. Чат (`Message`): send/list/edit,
      флаг «официальное», без realtime (ADR-0009) ✓; вложения к
      сообщениям ✓ и удаление переписки/документов (только SuperAdmin) ✓.
      Расторжение (`termination`) — реализовано отдельным пунктом ниже.
- [~] Генерация текста договора (`LeaseDocument`): Handlebars-шаблон РФ
      (из `dogovor_arendy.docx`), заполнение известными полями +
      персональными данными сторон, если внесены (`LeasePartyInfo`,
      ADR-0021), версионирование ✓. PDF отложен (HTML print-ready;
      Puppeteer — уточнение ADR-0004).
- [~] `LeasePartyInfo` (паспорт, обе стороны) — **статус менялся дважды
      2026-08-19–20, актуальное решение — ADR-0021, собираем.** Хронология:
      прототип `TenantInfo` (только арендатор) реализован 2026-07-22,
      полностью удалён 2026-07-23 по фидбэку клиента; 2026-08-19 клиент
      сначала явно закрыл вопрос как «не собираем вообще, вне периметра
      152-ФЗ» (ADR-0017), затем в тот же день пересмотрел решение на
      противоположное после разговора с партнёром (ADR-0021) — обе
      стороны, RU-хостинг, оператор ИП/самозанятый, поэтапно (сначала
      механизм строится и проверяется на синтетических данных, реальные
      пользователи — после готовой политики конфиденциальности/согласия).
      Backend (2026-08-20) ✓: `LeasePartyInfo` (одна запись на сторону,
      по образцу `LeaseSignedScan`), `CryptoService`/`CryptoModule`
      (AES-256-GCM, восстановлены), ретеншен 3 года после Lease
      (`PartyInfoService.runRetention`, ежедневный `@Cron`) ✓, вывод в
      `LeaseDocument` ✓. **Не сделано:** фронт-экран сбора данных для
      каждой стороны (аналог прежнего `/leases/[id]/tenant-info`, теперь
      нужен для обеих сторон) — следующий шаг.
- [x] Расторжение договора (`termination`): любая сторона инициирует
      (30 дней), landlord финализирует → `terminated` + пропорция
      последнего периода (`periodEndOverride`), возврат задатка.
- [~] Модуль отчётов: доходы и просрочки, сроки договоров — **в работе**.
      Сводка landlord (`GET /reports/summary`): доходы (всего + по
      месяцам), просрочки (с контактом арендатора и вычисленной пеней),
      сроки договоров (30/60/90 дней) ✓. График «по месяцам» —
      агрегированные данные (отрисовка на фронте).
- [~] Базовые уведомления (email; SMS/мессенджер — по возможности) —
      **в работе**. `NotificationChannel` (интерфейс) +
      `ConsoleNotificationChannel` (dev-заглушка), персист `Notification`,
      list/markRead. Триггеры: «проверьте оплату» при claim (ADR-0012),
      алерт обеим сторонам при пропуске периода из-за показаний ✓.
      Каскад напоминаний (за 3/1 день до оплаты — подать показания;
      в день оплаты — алерт обеим сторонам) ✓. Отложено: реальный
      email/SMS-провайдер (с хостингом).

- [~] **Полный визуальный редизайн фронта (ADR-0023)** — Tailwind 3.4 +
      токены на CSS custom properties + примитивы shadcn/ui, макеты в
      Stitch. Идёт **до** оставшихся фаз плана качества (5–12): почти все
      они тянут за собой фронт, иначе те же экраны верстаются дважды. На
      время редизайна фронтовые фазы заморожены, backend идёт параллельно.
      R1 (все 19 маршрутов нарисованы в двух раскладках) и R2 (тема,
      примитивы, оболочка) закрыты; R3 — весь код перенесён, старый слой
      удалён (`globals.css` 1544 → 253 строки), часть экранов ждёт живой
      проверки; R4 — документация. Текущий статус — `docs/DEV_STATE.md`.
