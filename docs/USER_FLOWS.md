## Часть 1. Сквозные сценарии (user flows)

### 1.1. Онбординг собственника → первый объект → первый договор

1. Landlord регистрируется, явно выбирает роль «арендодатель»
   (`MVP_SCOPE.md`, «Роль пользователя»).
2. Экран «Онбординг собственника» — мини-мастер: добавить объект →
   добавить арендатора → создать договор → настроить платёж.
3. «Добавить объект» → экран «Карточка объекта»: адрес, тип, площадь,
   фото, часовой пояс объекта (`Property.timezone`, по умолчанию
   Europe/Moscow).
4. «Добавить счётчики» → для каждого счётчика: тип из списка
   (электричество/вода/газ/отопление) + своё название (нужно, если
   счётчиков одного типа несколько — например ГВС/ХВС).
5. «Добавить услуги» (опционально) → экран «Услуги»: название,
   стоимость, тип (ежемесячная/разовая). Каталог привязан к объекту, не
   к договору — переживает смену арендатора.
6. «Создать договор» → мастер: срок, дата начала, сумма аренды,
   обеспечительный платёж (0 по умолчанию), логика коммуналки, ставка
   пени за просрочку оплаты (% в день, задаёт landlord), дата подачи
   показаний.
7. Текст договора либо генерируется по шаблону, либо landlord
   загружает готовый файл как альтернативу.
8. Landlord отправляет приглашение арендатору (email/телефон) →
   создаётся `Invitation` + договор в статусе «отправлен».

### 1.2. Приглашение и онбординг арендатора

1. Tenant получает приглашение (email/ссылка), регистрируется, явно
   выбирает роль «арендатор» — сценарий короче, чем у собственника (без
   мастера «добавить объект»).
2. Открывает договор в статусе «отправлен» → видит текст (сгенерирован
   или загруженный файл) → заполняет свои данные (`TenantInfo`, включая
   паспортные — хранятся зашифрованными, видит только `SuperAdmin`).
3. Стороны подписывают текст физически (вне сервиса), каждая
   загружает в систему скан документа со своей подписью, дополнительно
   нажимает «подтверждаю» (техническое действие, не замена подписи).
4. Как только **сканы загружены обеими сторонами** — договор считается
   заключённым (статус → «подписан»/`active`), объект получает статус
   «занято», начинает работать график расчётных периодов. Юридически
   значимый факт — именно сканы с подписью, не клик «подтверждаю» сам
   по себе (см. `docs/MVP_SCOPE.md`, «Факт заключения договора»).

### 1.3. Расчётный период — happy path

1. При активации договора автоматически создаётся график будущих
   периодов (от `paymentDay`, границы 12:00–11:59) и первый
   предварительный счёт (черновик) с позицией аренды.
2. За 3 дня до даты оплаты — напоминание tenant: подать показания
   счётчиков.
3. Tenant фотографирует счётчик → OCR подставляет цифру → tenant
   подтверждает/поправляет → отправляет. Валидация: новое ≥
   предыдущее; если расход > 10× среднего — мягкое предупреждение, не
   блокирует отправку.
4. Черновик счёта пересчитывается в реальном времени: аренда +
   ежемесячные услуги (авто) + коммуналка по показаниям.
5. За 1 день до оплаты — повторное напоминание, если показания всё ещё
   не поданы.
6. В день оплаты (12:00, часовой пояс объекта) планировщик
   финализирует черновик → статус «ожидает оплаты», создаёт новый
   черновик на следующий период.
7. Landlord/tenant видят финальный счёт в «Графике платежей», tenant
   оплачивает вне системы (перевод/наличка — как удобно) и нажимает
   «Я оплатил» → статус счёта «оплата заявлена».
8. Landlord получает уведомление «проверьте, что оплата пришла»,
   проверяет у себя и нажимает «Оплата получена» → только это
   переводит счёт в статус «оплачен» (ADR-0012, номинальный флоу без
   реального эквайринга — см. `docs/MVP_SCOPE.md`).
9. Если оплата просрочена — со следующего дня начисляется пеня (% в
   день от суммы счёта, ставка из договора), пеня считается на лету, не
   батчем, и продолжает копиться даже после клика tenant «Я оплатил» —
   останавливается только по подтверждению landlord (см. п.8).

### 1.4. Расчётный период — показания не поданы

1. Дата оплаты наступила, показания не поданы.
2. Планировщик **не финализирует** черновик — счёт остаётся в
   состоянии «нерассчитан».
3. Алерт уходит **обеим сторонам** одновременно: «расчёт не готов» (не
   «просрочка оплаты» — это разные состояния).
4. Как только показания поданы — черновик пересчитывается и может быть
   финализирован (автоматически при следующем прогоне планировщика или
   вручную кнопкой «Сформировать счёт», доступной обеим сторонам).

### 1.5. Заявка на обслуживание с урегулированием

1. Только tenant создаёт заявку: категория, описание, фото (например
   «сломался кран»).
2. Landlord видит заявку, меняет статус (новая → в работе), стороны
   обсуждают в чате по договору (вложения и редактирование сообщений
   разрешены, удаление — только `SuperAdmin`).
3. Стороны договариваются, кто платит (пополам/одна сторона) и на
   какую сумму → сумма вносится в систему.
4. Сумма требует **обязательного двустороннего подтверждения** — без
   этого не становится частью счёта.
5. После подтверждения обеими сторонами сумма сразу добавляется
   строкой в **текущий открытый черновик счёта** (не в следующий
   период), заявка помечается «решено».

### 1.6. Расторжение договора

1. Тикет категории `termination` может создать **любая сторона** — в
   т.ч. tenant, если сам хочет съехать (формальное уведомление).
2. Минимальный срок уведомления — 30 дней до фактической даты
   расторжения.
3. **Финализирует расторжение только landlord** — подтверждение tenant
   не требуется (в отличие от урегулирования по обычной заявке, п.1.5).
4. При финализации landlord может сдвинуть границу текущего периода на
   дату расторжения — это даёт пропорциональный расчёт аренды/
   коммуналки за неполный период (дни).
5. Отдельно landlord решает сумму возврата обеспечительного платежа
   (полностью/частично/не возвращать) — единолично, без подтверждения
   tenant; возврат не смешивается со счетами за аренду/коммуналку.
6. Договор → статус `terminated`, объект → статус «свободно», история
   договора и переписки сохраняется, доступ к ней остаётся только у
   landlord.

### 1.7. Смена арендатора

1. После расторжения (1.6) объект свободен, landlord может пригласить
   нового арендатора (см. 1.1, шаг 8, только для уже существующего
   объекта).
2. История прошлого договора (переписка, счета, показания) видна в
   «истории арендаторов» на карточке объекта — доступ только у
   landlord, у бывшего арендатора доступ закрыт.
3. ПДн бывшего арендатора хранятся ещё 3 года после окончания договора
   (дефолт, см. `docs/MVP_SCOPE.md`, «Роли и доступ»), затем
   автоудаление/анонимизация фоновой задачей, если нет активного спора.

### 1.8. Отчёты (landlord)

1. Экран «Доходы и просрочки»: карточки по объектам, график поступлений
   по месяцам, список текущих просрочек с контактами.
2. Экран «Сроки договоров»: лента с датой окончания, виджеты
   «истекают в ближайшие 30/60/90 дней», кнопка «создать продление».
3. Выгрузки (CSV/PDF) не нужны в MVP — всё доступно на экранах.

## Часть 2. User stories по модулям

Формат: **Как** роль, **хочу** действие, **чтобы** ценность.
Критерии приёмки — коротко, только нетривиальные правила (не дублируют
очевидные CRUD-операции).

### Модуль 1 — Объекты

**US-1.1.** Как landlord, хочу добавить объект с адресом, фото и
часовым поясом, чтобы вести учёт по каждой квартире отдельно.
- Критерии: часовой пояс по умолчанию Europe/Moscow, редактируемый;
  адрес обязателен.

**US-1.2.** Как landlord, хочу видеть на карточке объекта средний
расход по каждому счётчику, чтобы замечать аномалии в показаниях.
- Критерии: среднее считается по истории показаний этого счётчика;
  используется для предупреждения при вводе новых показаний (см.
  US-3.5).

**US-1.3.** Как landlord, хочу добавлять несколько счётчиков одного
типа на один объект (например, ГВС и ХВС отдельно) с собственными
названиями, чтобы не путать их в интерфейсе.

### Модуль 2 — Договоры

**US-2.1.** Как landlord, хочу создать договор мастером с генерацией
текста по шаблону РФ, чтобы не составлять документ вручную.
- Критерии: один договор — ровно один tenant; на объект — не более
  одного активного договора одновременно (без посуточной сдачи).

**US-2.2.** Как landlord, хочу вместо генерации по шаблону загрузить
уже готовый файл договора, чтобы использовать свой юридический
документ.
- Критерии: независимо от источника текста, факт заключения
  определяется загруженными сканами подписей обеих сторон, не
  генерацией текста.

**US-2.3.** Как tenant, хочу подписать договор физически и загрузить
скан своей подписи, чтобы это стало юридически значимым подтверждением
без встроенной в сервис электронной подписи.
- Критерии: пока сканы не загружены обеими сторонами — статус договора
  не переходит в «подписан»/`active`; клик «подтверждаю» в интерфейсе
  дополняет, но не заменяет загрузку скана.

### Модуль 3 — Платежи и коммуналка

**US-3.1.** Как landlord, хочу завести каталог услуг на объекте
(интернет, уборка и т.п.) с типом ежемесячная/разовая, чтобы не
перезаводить его для каждого нового договора.
- Критерии: каталог живёт на Property, переиспользуется во всех
  договорах по этому объекту; ежемесячные — авто в каждый период,
  разовые — вручную в конкретный период.

**US-3.2.** Как tenant, хочу видеть предварительный счёт, который
обновляется в реальном времени по ходу месяца, чтобы заранее знать
сумму к оплате.
- Критерии: черновик пересчитывается при каждом изменении состава
  (услуга, показания, урегулирование по заявке).

**US-3.3.** Как любая сторона договора, хочу получить напоминание за 3
и за 1 день до оплаты, если показания счётчиков ещё не поданы, чтобы не
пропустить срок.
- Критерии: если к дате оплаты показания всё ещё не поданы — счёт не
  финализируется, обеим сторонам уходит алерт «расчёт не готов»
  (отдельно от обычной просрочки оплаты).

**US-3.4.** Как tenant, хочу подать показания счётчика с фото, чтобы
подтвердить значение и не считать коммуналку вручную.
- Критерии: фото обязательно; OCR распознаёт цифру и подставляет в
  поле, я подтверждаю/правлю перед отправкой (не слепая автоматика).

**US-3.5.** Как tenant, хочу получить предупреждение, если введённое
показание сильно (>10×) отличается от среднего расхода, чтобы
проверить, не опечатался ли я.
- Критерии: новое значение не может быть меньше предыдущего (жёсткая
  проверка); превышение среднего в 10 раз — мягкое предупреждение, не
  блокирует отправку.

**US-3.6.** Как landlord, хочу задать ставку пени (% в день) при
создании договора, чтобы штраф за просрочку соответствовал моим
условиям.
- Критерии: пеня начисляется только за просрочку **оплаты**, не за
  просрочку показаний; ставка — поле договора, не общий параметр
  продукта; пеня считается «на лету» по текущему времени, не батчем.

**US-3.6b.** Как tenant, хочу нажать «Я оплатил» после того, как
перевёл деньги вне сервиса, чтобы уведомить landlord о необходимости
проверить оплату.
- Критерии: клик переводит счёт в статус «оплата заявлена», не
  «оплачен»; пеня (если уже начислялась) продолжает капать.

**US-3.6c.** Как landlord, хочу получить уведомление и подтвердить
«Оплата получена» после того, как реально увидел деньги, чтобы счёт
закрылся только когда оплата подтверждена с моей стороны.
- Критерии: только это действие переводит счёт в «оплачен» и
  останавливает пеню; клик tenant сам по себе этого не делает
  (ADR-0012).

**US-3.6d.** Как landlord, хочу простить начисленную пеню по
договорённости с tenant (например, задержка была уважительной), чтобы
не настаивать на штрафе формально.
- Критерии: одностороннее действие, подтверждение tenant не требуется;
  доступно, пока счёт не в статусе «оплачен»; после прощения сумма и
  дата видны обеим сторонам в счёте (не скрывается сам факт просрочки);
  действие необратимо.

**US-3.7.** Как любая сторона, хочу видеть таблицу всех периодов
договора (прошедшие/текущий/будущие) с суммами и статусами, чтобы
понимать историю и предстоящие обязательства одним взглядом.

**US-3.8.** Как tenant, съезжающий посреди периода, хочу, чтобы аренда
и коммуналка были посчитаны пропорционально прожитым дням, а не как за
полный период.

### Модуль 4 — Коммуникация и заявки

**US-4.1.** Как tenant, хочу создать заявку на обслуживание с фото и
описанием, чтобы сообщить о проблеме.
- Критерии: заявки создаёт только tenant (landlord заявки не создаёт,
  только обрабатывает), кроме отдельного случая расторжения (US-4.3).

**US-4.2.** Как любая сторона, хочу согласовать в чате денежную сумму
по заявке и подтвердить её, чтобы она попала в счёт.
- Критерии: сумма требует подтверждения **обеих** сторон; после
  подтверждения попадает строкой в текущий открытый черновик счёта, не
  в следующий период.

**US-4.3.** Как tenant, хочу создать тикет о своём желании расторгнуть
договор, чтобы формально уведомить собственника.
- Критерии: тикет может создать любая сторона, но исполняет
  (финализирует) расторжение только landlord — моё подтверждение как
  tenant не требуется и не блокирует решение.

**US-4.4.** Как landlord, хочу при расторжении сдвинуть границу
текущего периода на дату расторжения, чтобы получить корректный
пропорциональный счёт.

**US-4.5.** Как landlord, хочу единолично решить сумму возврата
обеспечительного платежа при расторжении, чтобы учесть повреждения
объекта, если они были.
- Критерии: не требует подтверждения tenant; не является строкой
  `Bill` — отдельный трек.

**US-4.6.** Как участник чата, хочу прикладывать фото/файлы и
редактировать свои сообщения, чтобы точнее фиксировать договорённости.
- Критерии: удаление сообщений недоступно ни landlord, ни tenant —
  только `SuperAdmin`.

### Модуль 5 — Отчёты

**US-5.1.** Как landlord, хочу видеть доходы и текущие просрочки по
каждому объекту, чтобы контролировать финансовое состояние портфеля.

**US-5.2.** Как landlord, хочу видеть список договоров, истекающих в
ближайшие 30/60/90 дней, чтобы заранее планировать продление.

### Модуль 6 — Онбординг, роли и доступ

**US-6.1.** Как пользователь, хочу явно выбрать роль (арендатор/
арендодатель) при регистрации, при этом иметь возможность быть
арендодателем по одному объекту и арендатором по другому одновременно.
- Критерии: роль — не глобальный атрибут профиля, определяется по
  каждой связи объект/договор.

**US-6.2.** Как SuperAdmin, хочу быть единственной ролью с доступом на
просмотр паспортных данных арендатора и правом удаления документов/
сообщений, чтобы обеспечить доверие к истории и защиту ПДн.
- Критерии: ПДн хранятся зашифрованными; хранение — весь срок
  действия договора + 3 года после окончания (дефолт, требует
  юридического подтверждения), затем автоудаление, с паузой при
  активном споре.

**US-6.3.** Как landlord, хочу использовать сервис преимущественно с
телефона (фото показаний и т.п.), чтобы не быть привязанным к
компьютеру.
- Критерии: адаптивный веб обязателен в MVP; с десктопа — фото
  загружается файлом вместо камеры.
