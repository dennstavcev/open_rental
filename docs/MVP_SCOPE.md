## 1. Модули MVP

1. Объекты (Property & Tenancy)
2. Договоры (Leases)
3. Платежи и коммуналка (Billing & Utilities)
4. Коммуникация и заявки (Chat & Requests)
5. Простые отчёты (Analytics)
6. Онбординг и профиль пользователя (Onboarding & Settings)

## 2. Модуль объектов

### Экран «Список объектов»

Быстрый обзор по всем объектам собственника:

- карточки объектов: адрес, фото, статус (сдаётся / свободно / скоро
  освобождается);
- краткая информация: текущий арендатор, размер аренды, состояние
  оплат (ОК / есть просрочка);
- индикация ближайших событий: истекает договор, скоро платёж, есть
  незакрытые заявки.

### Экран «Карточка объекта»

- основные данные: адрес, тип объекта, площадь, описание, фотографии;
- текущий договор аренды (ссылка на модуль договоров);
- история арендаторов (список прошлых договоров);
- быстрые действия: «создать договор», «отправить сообщение», «выставить
  счёт», «добавить показания».

## 3. Модуль договоров

### Экран «Создать договор»

Ключевой экран MVP — пошаговый мастер:

- кто собственник, кто арендатор;
- срок аренды, дата начала;
- сумма аренды, обеспечительный платёж (задаток) — не обязателен, по
  умолчанию 0, если по договору его нет;
- кто платит коммуналку и как она считается;
- дополнительные условия (животные, ремонт, досрочное расторжение).

На основе ответов генерируется текст договора по шаблону РФ (единый
рынок запуска — см. `docs/IDEA.md`). Предпросмотр и редактирование
(добавить/убрать стандартные блоки).

Один договор — ровно один арендатор (без со-арендаторов/соседей по
одному договору в MVP) и ровно один активный договор на объект в любой
момент времени (посуточная/параллельная сдача не поддерживается).

Альтернатива генерации по шаблону — загрузка уже готового файла
договора вместо генерации внутри сервиса.

**Приложение №1 — акт приёма-передачи имущества (добавлено 2026-08-19,
ADR-0018).** Персональные данные сторон (ФИО, паспорт, адрес, телефон) в
тексте договора — прочерки, заполняются от руки (ADR-0017); взамен
собственник может построчно описать имущество, передаваемое вместе с
помещением (тип техники, бренд, модель, количество) — генерируется
отдельным приложением к договору, тем же механизмом версионирования.
Опись необязательна: пустая — акт формируется с пометкой об этом.

### Экран «Договор в работе»

- статус: черновик / отправлен арендатору / подписан;
- кнопка «отправить арендатору» (email/ссылка);
- загрузка скана подписанного документа каждой стороной, история
  версий.

**Факт заключения договора (решено, 2026-07-22) — больше не блокер.**
Основное юридическое подтверждение — подписанный скан документа,
который есть на руках у обеих сторон: стороны подписывают текст
(сгенерированный или загруженный) физически, вне сервиса, каждая
загружает в систему скан со своей подписью. Сервис не вводит
собственную электронную подпись и не берёт на себя роль
удостоверяющего центра — используется обычная письменная форма
(бумажная подпись + скан), юридическая сила которой не вызывает
вопросов. Кнопка «подтверждаю» в интерфейсе — техническое действие («я
загрузил свой скан / ознакомился»), не заменяет и не имитирует
физическую подпись. Договор переходит в статус «подписан»/`active`,
когда сканы загружены обеими сторонами. Это снимает единственный ранее
открытый блокер по юридической значимости e-signature (был отмечен в
`docs/IDEA.md`, открытый вопрос 3, и `docs/ROADMAP.md`, Phase 0).

## 4. Модуль платежей и коммуналки

> Обновлено ТЗ от клиента (2026-07-20, прототип-набросок
> `electricity_counter_master2`) — детализирует биллинг-логику ниже.
> Статус — черновик, требует подтверждения `product-analyst`/CEO перед
> финализацией `architect`.

### Экран «Услуги» (новый, отдельный модуль)

Каталог услуг, привязанных к конкретному объекту (не к договору — чтобы
переживать смену арендатора):

- список услуг объекта с созданием/редактированием/удалением;
- поля услуги: название, стоимость, тип (`ежемесячная` / `разовая`),
  описание;
- ежемесячные услуги автоматически добавляются в каждый новый
  расчётный период; разовые добавляются в счёт вручную, в конкретный
  период.

### Экран «Настройки платежей по договору»

Привязан к конкретному договору:

- сумма аренды, периодичность (ежемесячно), дата платежа;
- реквизиты для оплаты (карта, счёт, онлайн-ссылка);
- логика коммуналки: фиксированная сумма, или по показаниям счётчиков
  (список счётчиков, тарифы);
- дата, до которой арендатор обязан подать показания в текущем периоде;
- ставка пени за просрочку оплаты — % от суммы счёта за день просрочки,
  задаётся собственником при создании договора (не фиксирована на
  уровне продукта, у каждого договора своя, см. раздел «Пени» ниже).

### Расчётный период

- период = от 12:00 дня оплаты до 11:59 следующего дня оплаты
  (пример: 20.09 12:00 – 20.10 11:59); дата оплаты берётся из
  договора (`paymentDay`) — конкретное число не хардкодится, всегда из
  договора;
- график будущих периодов создаётся автоматически сразу при создании
  договора (не по одному при наступлении).

### Напоминания по периоду

Каскад привязан к дате оплаты по договору (`paymentDay`), не к
конкретному числу:

- **за 3 дня до оплаты** — напоминание арендатору: подать показания
  счётчиков;
- **за 1 день до оплаты** — повторное напоминание, если показания всё
  ещё не поданы;
- **в день оплаты** — если показания так и не поданы и счёт не
  рассчитан, алерт уходит **обеим сторонам** сразу (и арендатору, и
  собственнику): «расчёт не готов», а не просто «просрочка оплаты».

### Пени

Только за просрочку **оплаты**, не за просрочку подачи показаний:

- % от суммы счёта за каждый день просрочки оплаты, ставку задаёт
  собственник в договоре — единого значения на уровне продукта нет;
- просрочка подачи показаний деньгами не наказывается — только
  каскад напоминаний выше и алерт в день оплаты;
- **останавливается только по подтверждению собственника «Оплата
  получена»** (ADR-0012) — клик арендатора «Я оплатил» пеню не
  останавливает, это лишь заявление, ждущее подтверждения второй
  стороной (см. «Экран «Счета»» выше);
- **опционально: собственник может простить пеню** (по договорённости,
  например если задержка была уважительной) — кнопка «Простить пеню»
  доступна на любом счёте с начисленной пеней, пока счёт не оплачен.
  Одностороннее решение собственника, подтверждения арендатора не
  требует. После прощения пеня фиксируется как прощённая (сумма и дата
  видны обеим сторонам в счёте, не просто исчезает) и дальше не растёт;
  отменить прощение нельзя.

### Экран «Счета» (черновик → финал)

Счёт по периоду проходит два состояния:

- **предварительный (черновик)** — создаётся автоматически в начале
  периода, обновляется в реальном времени по ходу месяца: в первом
  периоде обязательно есть позиция аренды, дальше автоматически
  добавляются ежемесячные услуги, вручную — разовые услуги, по подаче
  показаний — пересчитанная стоимость коммуналки;
- **финальный** — фиксируется по наступлению нового периода (авто) или
  по кнопке «Сформировать счёт» (вручную); кнопка доступна и
  собственнику, и арендатору. После финализации создаётся новый
  черновик на следующий период, а закрытый счёт уходит в историю
  платежей со статусом **ожидается → оплата заявлена → оплачен**
  (ровно эти три значения хранятся, см. «Подтверждение оплаты» ниже и
  ADR-0012). «Просрочен» — не отдельный статус, а отображаемый флаг:
  дата оплаты прошла, а счёт ещё не в статусе «оплачен».

> **Важное исключение.** Если к моменту перехода периода показания
> счётчиков ещё не поданы — счёт **не финализируется автоматически**,
> остаётся нерассчитанным/незакрытым, пока показания не введут. Вместо
> тихого закрытия без коммуналки — алерт обеим сторонам (см.
> «Напоминания по периоду» выше). Ручная кнопка «Сформировать счёт» в
> этом состоянии тоже недоступна/предупреждает о недостающих данных.

Для собственника: список счетов по каждому договору с детализацией по
статьям (аренда + коммуналка отдельно), кнопка «создать счёт» для
нестандартных разовых начислений вне каталога услуг.

Для арендатора (кабинет арендатора): лента платежей, реквизиты/ссылка
по клику на счёт, индикатор просрочки и напоминания.

**Подтверждение оплаты — номинальный флоу (ADR-0012), без реального
эквайринга:**

1. Финальный счёт получает статус «ожидается».
2. Арендатор оплачивает вне сервиса — как удобно (перевод, наличка,
   что угодно) — и нажимает «Я оплатил». Статус → «оплата заявлена».
3. Собственнику приходит уведомление «проверьте, что оплата пришла».
4. Собственник проверяет у себя (банк/наличные) и нажимает «Оплата
   получена». Только это переводит счёт в статус «оплачен».

Клик арендатора — заявление, не финансовое доказательство: пеня за
просрочку **продолжает начисляться** в статусе «оплата заявлена» и
останавливается только по клику собственника «Оплата получена» —
намеренно, чтобы заявление об оплате нельзя было использовать как
способ формально избежать пени без реальной передачи денег.

Реальная интеграция с СБП (ADR-0011) — будущий апгрейд поверх этого же
протокола: провайдер сможет подтверждать оплату автоматически вместо
ручного клика арендатора, но собственнику всё равно решать, встроена
ли эта проверка в MVP или это отдельная задача Phase 2.

При выезде арендатора посреди расчётного периода (не в день оплаты) —
аренда и коммуналка за неполный период считаются пропорционально
прожитым дням, а не как за целый период.

### Экран «График платежей» (таблица периодов, новый)

Единая таблица всех периодов договора: прошедшие (сумма + статус
оплаты), текущий (активный, с предварительным счётом, редактируемый),
будущие (без суммы, статус «предстоящий»). Даёт полную историю и
предстоящие обязательства одним взглядом. Выгрузка (CSV/PDF) в MVP не
нужна — достаточно наглядного экрана.

### Экран «Показания счётчиков»

- список счётчиков, привязанных к объекту; на одном объекте может быть
  несколько счётчиков, в том числе несколько одного типа (например,
  отдельно ГВС и ХВС, или день/ночь для электричества) — при добавлении
  счётчика пользователь выбирает тип (электричество, вода, газ,
  отопление) из списка и даёт счётчику своё название, чтобы отличать
  их между собой в интерфейсе;
- ввод показаний — **фото обязательно** (не опционально): арендатор
  фотографирует счётчик (с телефона — камерой, с десктопа — загрузкой
  файла фото), распознавание (OCR) подставляет цифру в поле
  автоматически, арендатор подтверждает или правит вручную перед
  отправкой (автозаполнение с подтверждением, не слепая автоматика).
  Включено в MVP, а не отложено в Phase 2 — сложность в основном на
  цифровых табло, на механических барабанных счётчиках распознавание
  менее надёжно, само поле остаётся редактируемым в любом случае;
- **валидация**: новое показание не может быть меньше предыдущего,
  расход = новое − предыдущее; если расход больше среднего за объектом
  более чем в 10 раз — мягкое предупреждение «проверьте показания»,
  без блокировки отправки;
- средний расход по счётчику — считается и выводится в карточке
  объекта (см. модуль объектов);
- автоматический расчёт стоимости по заданным тарифам, добавление суммы
  в черновик текущего счёта.

> Автоматическое получение показаний/тарифов по API сбытовой компании
> по номеру счётчика — отдельный открытый технический риск, см.
> `docs/IDEA.md` (п.4) и `docs/ARCHITECTURE.md` — не путать с OCR
> распознаванием фото показаний выше, это разные задачи. OCR
> распознавание квитанций (коммунальных чеков) — тоже отдельная задача,
> остаётся кандидатом на Phase 2 (оценка трудоёмкости у
> `architect`/`backend-dev`), в отличие от OCR показаний счётчика,
> которое теперь в MVP.

### Источник времени и планировщик (решено, 2026-07-20)

Никакого внешнего «сервера времени» — источник истины для дедлайнов,
перехода периодов и пеней всегда бэкенд-сервер, никогда клиент
(иначе пользователь может подвинуть системные часы устройства и
обойти пеню/подделать раннюю подачу показаний). Конкретно:

- **Хранение** — все временные метки в БД в UTC.
- **Часовой пояс периода** — граница периода (день оплаты, 12:00)
  считается в часовом поясе объекта (`Property.timezone`, IANA-имя,
  по умолчанию `Europe/Moscow`), затем переводится в UTC-момент для
  сравнения и планирования. Это учитывает разницу поясов по регионам
  РФ, а не жёстко фиксирует московское время для всех.
- **Переход периода / финализация черновика** — периодический
  планировщик (например, раз в 15–60 минут) проверяет все активные
  договоры и финализирует те, у кого граница периода уже наступила
  (UTC-момент ≤ текущее время сервера) и черновик ещё не финализирован;
  плюс ручная кнопка «Сформировать счёт» делает то же самое немедленно.
  Проверка «уже наступила», а не «наступила именно сейчас» — чтобы
  планировщик сам «догонял» пропущенные переходы после простоя сервера
  (бесперебойность вместо жёсткой привязки к точному часу).
- **Пени** — не батч-начисление, а вычисляются на лету по формуле от
  `dueDate`/текущего времени при каждом показе счёта; меньше мест, где
  что-то может не отработать.
- **Идемпотентность** — на паре (`leaseId`, период) в БД действует
  уникальность финального счёта, повторный/параллельный прогон
  планировщика не создаёт дублей.
- **Тестирование** — время в коде бэкенда абстрагировано (инжектируемые
  часы), чтобы в тестах «перематывать» переходы периодов без ожидания
  реальных месяцев — без сетевого вызова наружу, в отличие от
  `fake-time` API в прототипе клиента.

## 5. Модуль коммуникации и заявок

### Экран «Чат по договору»

- диалог «собственник–арендатор», привязанный к конкретному договору;
- отправка текста и фото (повреждения, показания и т.п.), вложения
  поддерживаются;
- редактирование своего сообщения отправителем — разрешено; удаление
  сообщений пользователями — **не разрешено никому из сторон**, удалить
  может только суперадмин (см. «Роли и доступ» ниже) — сохраняет
  доверие к истории переписки как к «официальной»;
- метка «официальное сообщение» (например, уведомление о повышении
  аренды или ремонте).

### Экран «Заявки на обслуживание»

- заявки создаёт **только арендатор** (собственник заявки не заводит,
  видит и обрабатывает уже созданные);
- форма для арендатора: категория (ремонт, уборка, техника), описание,
  фото;
- статусы: новая, в работе, выполнена;
- для собственника: список заявок с фильтрами по объектам/статусам,
  комментарии, отметка «решено».

**Заявка → счёт.** Если по заявке требуется денежное урегулирование
(например, сломался кран, чинили за деньги) — стороны обсуждают и
договариваются в чате (кто платит: пополам или одна сторона), сумма
вносится в систему и требует **обязательного двустороннего
подтверждения** (не может одна сторона просто вписать цифру и закрыть
без подтверждения второй — это не опция, а правило для каждой такой
заявки). После подтверждения обеими сторонами сумма сразу добавляется
строкой в **текущий (открытый) черновик счёта**, а не в следующий
период.

**Расторжение договора — отдельный тип заявки/тикета, правило
пересмотрено 2026-07-21.** В отличие от обычных заявок (только
арендатор создаёт) и от урегулирования по заявке (обе стороны
подтверждают сумму) — здесь другая модель прав:

- создать тикет «хочу расторгнуть» может **любая сторона** — в том
  числе арендатор, если сам хочет съехать (это его способ формально
  уведомить о намерении);
- но **исполняет/финализирует расторжение только собственник** —
  подтверждение арендатора не требуется, это не взаимное согласование,
  а решение собственника (даже если тикет создал сам арендатор);
- минимальный срок уведомления — **не позже чем за 30 дней** до
  фактической даты расторжения;
- при финализации собственник может **изменить дату окончания
  текущего расчётного периода** (сдвинуть границу периода на дату
  расторжения вместо стандартной даты оплаты) — это и даёт
  пропорциональный расчёт аренды/коммуналки за неполный период (см.
  «Экран «Счета»» выше).

**Обеспечительный платёж (задаток) и его возврат.** Хранится и
отображается отдельно, **не смешивается со счетами за аренду и
коммуналку** — это не строка в `Bill`. При расторжении договора
собственник **единолично** решает сумму возврата (полностью, частично
из-за повреждений, или не возвращать) — в отличие от урегулирования по
обычной заявке, здесь не нужно двустороннее подтверждение суммы.
Решение о возврате фиксируется как часть процесса расторжения.

## 6. Модуль отчётов и аналитики

### Экран «Доходы и просрочки»

- карточки по объектам: сколько получено за месяц/год, есть ли долги;
- график поступлений по времени (простой, по месяцам);
- список текущих просрочек с контактами арендаторов.

### Экран «Сроки договоров»

- лента договоров с датой окончания;
- виджеты: «договоры, истекающие в ближайшие 30/60/90 дней»;
- кнопка «создать продление» или новый договор.

## 7. Онбординг и настройки

### Роль пользователя

Роль **не выбирается при регистрации** (пересмотрено 2026-07-23).
Регистрация — только email/пароль/ФИО. Роль определяется **по связям**:
собственник — тот, кто владеет объектом/создал договор; арендатор — тот,
кто принял приглашение на договор. Один и тот же человек может быть
арендодателем по одному объекту и арендатором по другому одновременно —
роль не атрибут профиля, а следствие связи объект/договор (см. модель
User в `docs/ARCHITECTURE.md`).

### Роли и доступ (уточнено 2026-07-21, ПДн — пересмотрено 2026-08-19)

- **Суперадмин** — отдельная системная роль (не landlord/tenant,
  сотрудник сервиса, не арендодатель и не арендатор). У неё есть право
  удалять документы/сообщения — ни арендодатель, ни арендатор не могут
  удалять переписку или документы сами.
- **После смены арендатора** — доступ к истории переписки/платежей по
  завершённому договору сохраняется только у **собственника**; бывший
  арендатор доступ теряет.
- **Персональные данные сторон (паспорт, ФИО, адрес регистрации,
  телефон) — не собираются и не хранятся системой** (ADR-0017, решение
  2026-08-19). Прежний план (хранение в БД зашифрованными, уведомление в
  РКН, 3-летний ретеншен) был реализован 2026-07-22 и удалён 2026-07-23
  по фидбэку клиента — вопрос срока хранения снят, хранить нечего.
  Персональные поля в тексте договора — прочерки, заполняются Сторонами
  от руки на бумаге.

### Экран «Онбординг собственника»

При первом входе — мини-мастер:

- добавить первый объект;
- добавить первого арендатора;
- создать первый договор;
- настроить платёж.

Краткие подсказки по каждому шагу.

### Экран «Настройки»

- профиль собственника (ФИО, контакты, реквизиты для платежей);
- настройки уведомлений (email/SMS/мессенджер);
- язык интерфейса — фиксированный (рынок РФ, см. `docs/IDEA.md`), выбор
  страны для шаблона договора не требуется, пока рынок один.

## 8. Что входит в MVP, а что — нет

**Входит в MVP:**

- 1 шаблон договора (долгосрочная аренда квартиры, РФ) с конструктором.
- Модуль объектов + договоров + базовых платежей — без интеграции с
  банками/эквайрингом, фиксация факта оплаты вручную.
- Показания счётчиков — ввод арендатором с обязательным фото и
  OCR-распознаванием с подтверждением (не слепая автоматика), без
  автоматической интеграции с РСО/сбытовыми компаниями.
- Чат и заявки в упрощённом формате (текст + фото, базовые статусы),
  включая двустороннее подтверждение суммы по заявке и её попадание в
  текущий счёт.
- Простой отчёт по доходам и срокам договоров.
- OCR распознавание квитанций — включить в MVP как отдельную оценку
  трудоёмкости от `architect`/`backend-dev`; если высокая сложность —
  допустимо перенести в начало Phase 2 без потери ценности MVP.
- **Веб-интерфейс адаптивный под мобильный браузер обязательно** (не
  опционально) — по оценке клиента, ~90% использования будет с
  телефона (фото показаний счётчиков и т.п.), десктоп — вторичный
  сценарий с загрузкой файла вместо камеры.

**Осознанно откладывается на следующие итерации:**

- Автоматическая интеграция с платёжными системами (эквайринг).
- Автоматическое получение показаний/тарифов через API сбытовых
  компаний (высокий технический/регуляторный риск, требует отдельного
  исследования).
- Расширенные шаблоны договоров для разных типов недвижимости/регионов.
- Продвинутая аналитика, экспорт в 1С/бухгалтерские системы.
- **Нативное мобильное приложение (Android APK)** — запланировано
  клиентом на после MVP (см. `docs/ROADMAP.md`, Phase 3); в MVP вместо
  этого — адаптивный веб (см. выше).
- Монетизация самого сервиса (не путать с биллингом между сторонами) —
  направление: подписка + вероятная реферальная программа. Точные
  цены/лимиты не определены, в MVP не реализуется, но модель данных не
  должна блокировать добавление `Subscription`/`Plan` и учёта рефералов
  позже (см. `docs/ARCHITECTURE.md`).
- Импорт/миграция существующих данных — не нужен для запуска (стартуем
  с нуля), но стоит не проектировать модель так, чтобы это было
  невозможно добавить позже (например, массовый импорт объектов/
  арендаторов из другого источника).
