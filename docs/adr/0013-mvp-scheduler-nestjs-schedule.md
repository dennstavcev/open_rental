# 0013. Планировщик периодов в MVP — @nestjs/schedule (BullMQ отложен)

Дата: 2026-07-22
Статус: Принято

## Контекст

ADR-0004 (backend-фреймворк) как следствие назвал механизм планировщика
расчётных периодов: `@nestjs/schedule` + **BullMQ поверх Redis**
(идемпотентные джобы, ретраи). Пришло время реализовать авто-переход
периодов (авто-финализация черновика счёта на границе периода —
`docs/MVP_SCOPE.md`, «Расчётный период», `docs/USER_FLOWS.md` §1.3).

Ограничения: разработка/тесты идут на localhost, Redis сейчас не
поднят (нет Docker в среде); ключевая доменная логика уже устроена так,
что **пеня и «просрочка» считаются лениво** (по времени сервера, чистые
функции), то есть не требуют планировщика вовсе. Планировщику остаётся
одна идемпотентная операция: перевести «дозревшие» черновики в финал и
создать следующий черновик.

## Рассмотренные варианты

1. **BullMQ + Redis сразу (как в ADR-0004).** Даёт очередь, ретраи,
   распределённость. Но требует Redis как рантайм-зависимость уже в
   dev/тестах; для единственной идемпотентной периодической операции на
   масштабе MVP (1–20 объектов на собственника) очередь — избыточная
   инфраструктура, усложняет локальный запуск и тесты.
2. **Только `@nestjs/schedule` — периодический идемпотентный скан.**
   `@Cron` раз в час сканирует черновики с наступившей границей периода и
   финализирует их. Идемпотентность — по конструкции: скан выбирает
   только `stage=draft` с `periodEnd <= now`, повторный проход ничего не
   меняет; «показания не поданы» → черновик просто пропускается и
   дозреет позже. Нет внешних зависимостей, работает на localhost и в
   unit-тестах.

## Решение

Вариант 2 для MVP: планировщик периодов — `@nestjs/schedule`
(периодический идемпотентный скан `BillingService.runPeriodTransition`).
BullMQ/Redis **отложены** до появления реальной потребности
(распределённый запуск в нескольких инстансах, тяжёлые ретраибл-джобы,
внешние интеграции вроде эквайринга/уведомлений с гарантией доставки).
Это уточняет (не отменяет) ADR-0004: фреймворк-планировщик тот же
(`@nestjs/schedule`), слой очереди вводится позже.

## Последствия

- Авто-переход периодов работает на localhost без Redis; тестируется
  как чистый вызов сервиса.
- Идемпотентность обеспечивается выборкой (`stage=draft` +
  `periodEnd<=now`) и гардом показаний, а не семантикой очереди.
- Полная привязка границ периода к `Property.timezone` остаётся
  отдельным пунктом (сейчас границы — 12:00 UTC, см. `docs/CHANGELOG.md`):
  планировщик к ней готов (сравнивает моменты времени), уточнение tz не
  меняет механизм.
- Когда понадобится BullMQ — вводится как слой поверх той же доменной
  операции `runPeriodTransition`, без переписывания бизнес-логики.
