# 0003. Выбор стека — React/Next.js + Node/Python + PostgreSQL

Дата: 2026-07-20
Статус: Принято

## Контекст

Нужно зафиксировать финальный стек реализации (Phase 0, `docs/ROADMAP.md`),
чтобы `architect`/`backend-dev`/`frontend-dev` могли начинать Phase 1.
Формат — веб-приложение уже решён (ADR-0001). На выбор было два
конкретных варианта: собственный черновой стек из `docs/ARCHITECTURE.md`
и стек прототипа-наброска, присланного клиентом (репозиторий
`electricity_counter_master2`, обзор 2026-07-20, см.
`docs/CHANGELOG.md`).

## Рассмотренные варианты

1. **Черновой стек проекта** — React/Next.js (frontend), Node.js
   (NestJS) или Python (FastAPI) (backend), PostgreSQL, S3-совместимое
   хранилище файлов. Полный контроль над данными и инфраструктурой,
   реляционная БД хорошо ложится на биллинг/периоды/начисления с
   join'ами между Lease/Property/Bill/Service, нет привязки к
   единственному вендору.
2. **Стек клиентского прототипа** — Flutter, компиляция в
   `flutter build web`, Firebase (Auth/Firestore/Storage/Messaging),
   Telegram Mini App поверх. Плюс — уже есть частично рабочий
   прототип, демонстрирующий продуктовую логику (услуги, счета,
   периоды). Минусы — Firestore как документная БД хуже подходит под
   реляционную биллинг-логику, которую усложняет ТЗ от 2026-07-20
   (черновик/финал счёта, каскад периодов, начисление пеней); Flutter
   для веба даёт более тяжёлый рантайм и менее стандартную веб-
   экосистему, чем React; вендор-лок на Firebase.

## Решение

Стек — вариант 1 (черновой стек проекта): React/Next.js + Node/Python +
PostgreSQL. Прототип клиента на Flutter/Firebase **не переносится как
код**: он используется только как референс продуктовой логики. Суть
функционала прототипа (услуги/каталог, жизненный цикл счёта
черновик → финал, расчётные периоды, приглашения, паспортные данные
арендатора) уже перенесена в `docs/MVP_SCOPE.md` и `docs/ARCHITECTURE.md`
(см. `docs/CHANGELOG.md`, запись 2026-07-20) и реализуется заново на
выбранном стеке.

## Последствия

- `docs/ARCHITECTURE.md` — раздел «Предлагаемый стек» становится
  зафиксированным (не черновиком для обсуждения).
- Конкретный выбор backend-фреймворка (NestJS vs FastAPI) остаётся
  отдельным, более мелким решением — не блокирует старт Phase 1,
  уточняется `architect`/`backend-dev` при декомпозиции.
- Открытый вопрос «источник времени» для авто-перехода периодов/
  начисления пеней (см. `docs/MVP_SCOPE.md`, модуль 4) решается в
  контексте своего backend/scheduler, а не через внешний API, как в
  прототипе.
- Roadmap Phase 0: пункт «Зафиксировать финальный стек как ADR»
  закрыт этим ADR.
