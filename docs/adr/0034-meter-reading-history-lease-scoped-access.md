# 0034. История показаний счётчика — доступ по договору, не только активному

Дата: 2026-08-24
Статус: Принято

## Контекст

Живой UX-ревью (Фаза 33, `docs/ux-review/2026-08-24-report-agent-b.md`,
раздел 3) нашёл два связанных дефекта в истории показаний счётчика:

1. Эндпоинт истории требует существования **активного** договора на
   объекте (ADR-0015 задумывался как хаб для действующей аренды) —
   после расторжения запрос отвечает 404 даже собственнику. Проверено
   живьём: у объекта с расторгнутым договором собственник не смог
   получить историю показаний того же счётчика.
2. Эндпоинт не проверяет соответствие `leaseId` из URL и фактического
   договора, к которому относится показание — только `meterId`.
   Воспроизведено: URL расторгнутого договора C с `meterId` объекта,
   где сейчас активен другой договор A, показал историю именно
   договора A. Показания привязаны к `leaseId` в схеме
   (`MeterReading.leaseId`), но эта связь не используется для проверки
   доступа.

Владелец продукта решил (2026-08-24): чинить оба дефекта, и
дополнительно — сохранять бывшему арендатору доступ к истории
показаний, которые он сам подавал, после завершения договора (не
только собственнику).

## Рассмотренные варианты

1. Оставить строго active-only (текущее поведение) — исправить только
   баг #2 (перепутанный `leaseId`), не расширять доступ после
   расторжения. Не выбрано.
2. Восстановить доступ только собственнику после расторжения, не
   бывшему арендатору. Не выбрано.
3. **Сделать эндпоинт lease-scoped**: доступ определяется принадлежностью
   к конкретному `Lease` (`leaseId` из URL), а не его статусом.
   Собственник объекта — доступ к истории по любому своему договору,
   действующему или завершённому. Бывший арендатор — доступ к истории
   ровно своего договора, тоже независимо от статуса.

## Решение

Вариант 3 (выбор владельца, 2026-08-24). Эндпоинт истории показаний
переводится с проверки «есть ли активный договор на объекте» на
проверку «является ли вызывающий стороной именно того договора,
который указан в URL» — тем же паттерном авторизации, что уже
применяется на карточке договора (`leases.getForUser`). Показания
выбираются по паре `(meterId, leaseId)` из URL, не по «текущему»
активному договору объекта. Это одним изменением закрывает и утечку
между договорами (#2), и потерю доступа после расторжения (#1) —
источник обеих находок один и тот же: код искал активный договор
объекта вместо использования уже переданного `leaseId`.

Если у одного счётчика было несколько последовательных арендаторов —
каждый видит показания своего периода аренды (по `MeterReading.leaseId`),
не показания предшественников/преемников — разделение по договору уже
корректно на уровне данных, меняется только код авторизации доступа.

## Последствия

- Уточняет `docs/adr/0015-tenant-meter-readings-screen.md`: тот описывал
  хаб показаний как экран действующей аренды — граница «только active»
  была неявной для чтения истории (хаб для подачи новых показаний
  по-прежнему имеет смысл только для активного договора, это не
  меняется; меняется только чтение уже существующей истории).
- Не требует новых полей в схеме — `MeterReading.leaseId` уже есть,
  меняется только `where`-условие сервиса и маршрут авторизации.
- Собственник и бывший арендатор видят одну и ту же историю показаний
  завершённого договора без ограничения по времени после расторжения —
  это осознанно шире, чем 3-летний ретеншен ПДн (ADR-0033): показания
  счётчика не персональные данные, отдельного срока хранения для них
  не вводится этим решением.
