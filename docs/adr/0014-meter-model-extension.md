# 0014. Расширение модели Meter: серийный номер, отключение, начальное показание

Дата: 2026-08-17
Статус: Принято

## Контекст

При сравнении с более ранним прототипом того же продукта (Flutter-приложение
`electricity_counter_master2`, отдельная наработка, не часть этого репозитория)
обнаружены пробелы в текущей модели `Meter`/`MeterReading`:

1. **Баг базы отсчёта.** `MeterReadingsService.create` берёт `previousValue =
   0`, если у счётчика ещё нет ни одного показания
   (`meter-readings.service.ts`). Но счётчик почти всегда добавляется в
   систему уже с накопленным значением (объект сдавался и раньше, или
   счётчик физически стоит не первый день). Первое же поданное показание
   посчитает расход как «новое значение − 0», что даёт грубо завышенное
   начисление арендатору. Это не гипотетический риск, а прямое следствие
   текущего кода при обычном сценарии использования.
2. **Нет серийного номера счётчика.** Юридически и практически важный
   атрибут (сверка с показаниями в квитанциях ресурсоснабжающей
   организации, поверка), в модели данных отсутствует вовсе.
3. **Нет способа вывести счётчик из эксплуатации без удаления.** Если
   счётчик заменён или временно не используется, единственный вариант —
   удалить его вместе с историей показаний (удаления сейчас даже нет) или
   продолжать считать его активным.

Прототип `electricity_counter_master2` решает (1) и (3) на уровне модели
данных: счётчик создаётся сразу с начальным показанием (совпадающим с
`current`/`previous` на старте), и имеет флаг `isActive`, переключаемый без
удаления. Серийный номер (2) там присутствует как обязательное поле формы.

## Рассмотренные варианты

1. **Ничего не менять, компенсировать на уровне UI** — просить
   арендодателя вручную подать «нулевое» первое показание сразу после
   создания счётчика. Отклонено: требует лишнего шага, который легко
   пропустить, и не решает (2)/(3) вообще.
2. **Хранить «текущее показание» прямо на Meter** (как в прототипе:
   `currentReading`/`previousReading` на самой модели). Отклонено:
   дублирует источник истины — показания уже нормализованы в отдельную
   таблицу `MeterReading` с фото/OCR (см. `docs/ARCHITECTURE.md`), и это
   осознанное решение проекта, чтобы не блокировать переход к
   автоматическому импорту показаний позже. Хранить то же значение в двух
   местах — риск рассинхронизации.
3. **Добавить `initialReading` как неизменяемую точку отсчёta на Meter,
   `serialNumber` и `isActive`; при расчёте расхода использовать
   `initialReading` как базу, если реальных показаний ещё нет.** Не
   дублирует изменяемое состояние (initialReading фиксируется один раз при
   создании и не обновляется), закрывает баг из (1), даёт (2) и (3) без
   архитектурных компромиссов.

Выбран вариант 3.

## Решение

В модель `Meter` добавляются три поля:

- `serialNumber String?` — опционально, вводится при создании счётчика.
- `isActive Boolean @default(true)` — переключается через
  `UpdateMeterDto`; при `isActive = false` `MeterReadingsService.create`
  отклоняет новые показания (`ConflictException`) вместо того, чтобы
  принимать данные по счётчику, выведенному из эксплуатации.
- `initialReading Decimal @db.Decimal(12, 3)` — обязательное поле при
  создании (`CreateMeterDto`), фиксирует значение на момент постановки
  счётчика на учёт в системе. Не изменяется после создания (в
  `UpdateMeterDto` не участвует — если счётчик заменён физически, это
  новый Meter, а не редактирование старого).

`MeterReadingsService.create` использует `meter.initialReading` как базу
для расчёта расхода первого показания вместо `0`:
```
previousValue = prior.length ? prior[last].value : meter.initialReading
```

Список счётчиков (`MetersService.findAll`) дополнительно возвращает
`lastReadingValue` (последнее показание или `initialReading`, если
показаний ещё не было) — вычисляемое поле ответа API, не хранимая
величина, нужно фронтенду для отображения текущего показания на карточке
счётчика и живого пересчёта стоимости в форме подачи показания (см.
`docs/CHANGELOG.md`, 2026-08-17).

## Последствия

- Требуется миграция Prisma (три новых поля на `Meter`; `initialReading`
  без дефолта — для существующих строк, если они появятся до применения
  миграции в проде, потребуется backfill или временный дефолт `0`; на
  момент принятия решения в проде данных нет, миграции ещё не
  накатывались — см. `backend/prisma/migrations/`, папки нет).
- `MeterReadingsService` получает дополнительную проверку `isActive` —
  подача показаний по отключённому счётчику становится невозможной; UI
  должен явно объяснять пользователю, почему форма недоступна.
- Не меняет модель `MeterReading` и не противоречит ADR-0008 (OCR) —
  `initialReading` не проходит через OCR/фото, вводится вручную при
  создании счётчика, как тариф.
- `docs/ARCHITECTURE.md` (раздел Meter) обновляется вместе с этим ADR.
