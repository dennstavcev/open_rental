# 0005. Модульный монолит

Дата: 2026-07-22
Статус: Принято

## Контекст

`docs/ARCHITECTURE.md` со старта держал открытым вопрос "монолит на
старте vs модульный монолит с прицелом на будущее разделение". Команда
маленькая (агентная разработка в CLI), MVP-сегмент — физлица 1–20
объектов, нагрузка не ожидается высокой на старте (см.
`docs/PRODUCT_QUESTIONS.md`, раздел 11 — дефолты по нефункциональным
требованиям). Нужно решить структуру до того, как `backend-dev` начнёт
раскладывать код по модулям.

## Рассмотренные варианты

1. **Простой монолит без чётких внутренних границ.** Быстрее всего
   писать в моменте, но 9 компонентов системы (`docs/ARCHITECTURE.md`,
   «Компоненты системы») с не самой тривиальной бизнес-логикой (расчётные
   периоды, пени, урегулирование заявок) быстро превратятся в
   слипшийся код без границ ответственности.
2. **Микросервисы с самого начала.** Явно избыточно для 1–20 объектов
   на арендодателя и команды из одного бэкенд-агента — операционная
   сложность (деплой, сеть, консистентность между сервисами) не
   окупается на этом масштабе.
3. **Модульный монолит.** Один деплойный артефакт (одно приложение
   NestJS, см. ADR-0004), но с чёткими границами между модулями
   (Auth, Properties, Leases, Billing, Maintenance, Documents,
   Notifications, Analytics — соответствуют «Компонентам системы» в
   `docs/ARCHITECTURE.md`) через встроенный DI/module-механизм NestJS.
   Позволяет выделить модуль в отдельный сервис позже, если понадобится
   (например, Billing при росте нагрузки), не переписывая всё с нуля.

## Решение

Модульный монолит — один деплойный NestJS-артефакт, каждый компонент
из `docs/ARCHITECTURE.md` («Компоненты системы») — отдельный NestJS
module с собственными контроллерами/сервисами/DTO и явно описанным
публичным интерфейсом для вызовов из других модулей (не прямые импорты
внутренних сервисов друг друга в обход границ).

## Последствия

- `backend-dev` раскладывает код по модулям 1:1 с разделом «Компоненты
  системы» в `docs/ARCHITECTURE.md`.
- Не блокирует и не предрешает вопрос хостинга — один артефакт
  разворачивается как один процесс/контейнер независимо от того, где
  физически будет жить прод (решается отдельно, см.
  `docs/READINESS_AUDIT.md`).
- `docs/ARCHITECTURE.md`, «Открытые архитектурные вопросы»: пункт про
  монолит/модульный монолит закрыт этим ADR.
