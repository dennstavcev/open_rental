# 0026. Структурированный адрес объекта и кадастровый номер

Дата: 2026-08-21
Статус: Принято

## Контекст

Сейчас адрес объекта хранится одной свободной строкой. Это не позволяет
надёжно сортировать и группировать объекты по городу, отдельно изменять части
адреса и хранить кадастровый номер. Автоматически разобрать существующие строки
на город, улицу и дом без риска тихо исказить юридически значимый адрес нельзя.
При этом договор и акт уже читают `Property.address`, поэтому одномоментная
замена строки структурой сломала бы документы legacy-объектов.

Кадастровый номер относится к самому объекту и берётся из публичного реестра
Росреестра. Это не персональные данные человека, поэтому правила ADR-0021 к
нему не относятся. В договоре реквизит уже предусмотрен, но до этой фазы всегда
печатался прочерком. Акт приёма-передачи из ADR-0018 продолжает использовать
тот же адрес объекта, что и договор.

## Рассмотренные варианты

1. **Оставить свободную строку единственным источником данных.** Отклонено:
   строка не даёт надёжной сортировки по городу и не позволяет независимо
   редактировать части адреса.
2. **Автоматически разобрать все существующие адреса при миграции.** Отклонено:
   формат строк не ограничен, поэтому бэкфилл неизбежно угадывал бы структуру и
   мог незаметно испортить адрес в документах.
3. **Сделать структурированные поля источником правды, а `address` оставить
   денормализованным кешем; legacy-объекты переводить на новую структуру при
   ручном редактировании.** Выбран: новые записи получают однозначную структуру,
   а старые продолжают печатать проверенную строку до явного переноса данных.

## Решение

Принят вариант 3.

- В `Property` добавляются nullable-поля `city`, `street`, `house`,
  `building`, `floor`, `apartment` и `cadastralNumber`. Все они nullable на
  уровне БД намеренно: иначе миграция не пройдёт по существующим объектам.
  Обязательность города, улицы и дома для новых объектов обеспечивается DTO,
  а не схемой БД.
- Структурированные адресные компоненты — источник правды. Клиент больше не
  передаёт `address` ни при создании, ни при обновлении. Backend собирает кеш
  единственным форматтером в порядке: `г.`, `ул.`, `д.`, `стр.`, `эт.`, `кв.`.
- Точный инвариант кеша: `address` пересобирается при создании объекта и при
  любом изменении адресных компонентов; у немигрированного legacy-объекта
  неадресная правка сохраняет прежний кеш.
- При обновлении проверяется итоговое состояние после слияния DTO с текущей
  записью. Если запрос содержит хотя бы один из шести адресных компонентов,
  итоговое состояние обязано содержать непустые `city`, `street` и `house`.
  Иначе запрос отклоняется целиком без записи. Поэтому изменение одной квартиры
  у объекта с заполненной тройкой допустимо, а у legacy-объекта без города —
  нет.
- Обязательные поля нормализуются обрезкой пробелов и затем проверяются на
  непустоту. Для необязательных полей действует отдельный контракт очистки:
  отсутствие поля сохраняет значение, `null` очищает его, пустая или пробельная
  строка после обрезки превращается в `null` и тоже очищает. Это позволяет, в
  частности, стереть кадастровый номер.
- Кадастровый номер проверяется нестрогим шаблоном четырёх числовых блоков через
  двоеточие: `^\d{1,2}:\d{1,2}:\d{1,7}:\d{1,10}$`. Цель — отсечь явный мусор,
  а не воспроизвести полную проверку ЕГРН. Более строгая длина блоков неверна:
  в действительных номерах встречаются однозначный номер округа и квартал `0`.
- Бэкфилла структурированных полей нет. Старая строка показывается в форме как
  подсказка и остаётся адресом документов, пока пользователь явно не заполнит
  структуру.
- Новый индекс по городу не создаётся: выборка уже ограничена владельцем через
  существующий индекс, а число его объектов невелико.

Форма редактирования объекта создаётся в рамках этой фазы как обязательная
часть решения. Без неё постепенный перенос legacy-объектов на структурированные
поля был бы нереализуем: существующий frontend прежде не вызывал PATCH объекта.

## Последствия

- Контракт создания объекта ломающе меняется: обе формы создания — мастер
  `/onboarding` и форма на `/properties` — обязаны передавать город, улицу и дом
  вместо свободного `address`.
- Список объектов сортируется и группируется по городу; объекты без города
  остаются отдельной последней legacy-группой.
- Договор подставляет кадастровый номер, а при его отсутствии сохраняет прочерк.
  Договор и акт продолжают читать `Property.address`, поэтому документы
  legacy-объектов не меняются.
- Денормализованный кеш требует соблюдения инварианта в каждом будущем месте
  записи адресных компонентов; сборка строки должна оставаться централизованной.
