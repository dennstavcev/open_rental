# 0008. OCR-движок для показаний счётчика — Tesseract

Дата: 2026-07-22
Статус: Принято

## Контекст

Показания счётчика с OCR-распознаванием — часть MVP, не Phase 2 (решено
клиентом 2026-07-21, см. `docs/MVP_SCOPE.md`). Нужен конкретный движок,
чтобы `backend-dev` мог начать модуль платежей и коммуналки. Задача уже
сужена продуктовым решением: распознаём только цифры на фото счётчика
(не документ целиком), поле остаётся редактируемым пользователем после
распознавания (не слепая автоматика) — то есть требования к точности
ниже, чем для юридически значимого документа.

## Рассмотренные варианты

1. **Облачный OCR API (Yandex Vision, Google Cloud Vision и т.п.).**
   Обычно точнее "из коробки" на сложных изображениях, но: требует
   отправки фото пользователя на сторонний сервис (лишний вопрос
   передачи данных третьим лицам, пересекается с сознательно отложенным
   вопросом хостинга/локализации), требует аккаунта/ключей/оплаты,
   не работает офлайн на localhost без реального сетевого вызова наружу.
2. **Tesseract OCR (self-hosted, open-source).** Работает полностью
   локально/на своём сервере, без внешних вызовов и без передачи фото
   третьим лицам — не пересекается с вопросом хостинга/локализации
   вообще, что явно соответствует пожеланию "не трогать пока
   юридическую часть и хостинг". Из коробки менее точен на сложных
   изображениях, но задача — цифры на счётчике (часто цифровое табло),
   а результат в любом случае подтверждается/правится пользователем
   перед отправкой (см. `docs/MVP_SCOPE.md`) — то есть Tesseract не
   обязан быть идеальным.

## Решение

Tesseract, развёрнутый как часть backend-инфраструктуры (библиотека/
локальный процесс, без внешнего сетевого вызова). Если по итогам
тестирования на реальных фото счётчиков точность окажется
неудовлетворительной даже с учётом подтверждения пользователем — в
Phase 2 рассмотреть переход на облачный OCR (Yandex Vision как основной
кандидат для рынка РФ) как отдельное решение, требующее уже решённого
вопроса хостинга/передачи данных.

## Последствия

- Не создаёт новой внешней зависимости и не требует решения по
  хостингу/локализации данных — можно реализовывать и тестировать
  полностью на localhost уже сейчас.
- OCR-компонент реализуется за тем же интерфейсным принципом, что и
  `StorageProvider` (ADR-0007) — `MeterOcrProvider`, чтобы замена на
  облачный сервис в будущем не требовала переписывания модуля Billing.
- OCR квитанций (Phase 2, отдельная задача от OCR показаний) этим ADR
  не решается — там документ сложнее, решение будет приниматься отдельно
  ближе к Phase 2.
