# 0002. Агентная command-and-control структура разработки

Дата: 2026-07-17
Статус: Принято

## Контекст

Разработка ведётся через CLI (Claude Code, модель Fable 5), с явным
требованием: продукт должен получиться правильным с первого раза, и
исполнение должно быть агентным, в режиме параллельного взаимодействия
нескольких ролей, а не одним универсальным агентом последовательно.
Нужна структура, которая распределяет ответственность по зонам,
позволяет параллелить независимую работу и не даёт задачам считаться
"готовыми" без независимой проверки.

## Рассмотренные варианты

1. Один универсальный агент делает всё последовательно — просто, но
   нет разделения ответственности, нет независимой проверки качества,
   плохо масштабируется на параллельные куски работы.
2. Плоский набор агентов-специалистов без единой точки приёмки —
   параллелится, но никто не отвечает за целостность результата и
   конфликты решений между агентами не разрешаются системно.
3. Иерархия: `project-ceo` как единственная точка приёмки и
   декомпозиции + подчинённые агенты-специалисты (product-analyst,
   architect, backend-dev, frontend-dev, qa-engineer, devops, security,
   docs-keeper), каждый обязан формально отчитываться CEO.

## Решение

Вариант 3. Структура и роли — `docs/TEAM_STRUCTURE.md`, определения
агентов — `.claude/agents/*.md`. `project-ceo` выставлен с максимальным
уровнем требовательности: не принимает отчёт без доказательства
выполнения, требует синхронизации документации через `docs-keeper` как
условие приёмки, обязателен параллельный запуск независимых кусков
работы через `Task`.

## Последствия

- Любая крупная задача в проекте теперь стартует через `project-ceo`,
  а не через прямое обращение к отдельному агенту в обход приёмки.
- `qa-engineer` и `security` получают право блокировать приёмку —
  это сознательно увеличивает трение ради качества результата.
- `docs-keeper` встроен как обязательный шаг — снижает риск, что
  правила `docs/DOCUMENTATION_RULES.md` останутся только на бумаге.
- Добавление/изменение ролей в будущем — само по себе реперная точка,
  требует нового ADR (не правится в этом файле задним числом).
