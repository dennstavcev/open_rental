# 0011. Готовность Payment/Bill под будущий эквайринг (СБП)

Дата: 2026-07-22
Статус: Принято

## Контекст

С момента ADR-0003 висел открытый вопрос: готова ли модель
`Payment`/`Bill` под будущий эквайринг без переделки (`docs/IDEA.md`,
открытые вопросы, п.2; `docs/ARCHITECTURE.md`, «Открытые архитектурные
вопросы»). CEO уточнил конкретное направление: в будущем — приём
оплаты по счёту через СБП (Систему быстрых платежей) прямо из сервиса.
В MVP платежи — только ручная фиксация факта оплаты (ADR/решение уже
принято, `docs/PRODUCT_QUESTIONS.md`, 7.1), эквайринг остаётся Phase 2+.
Вопрос — что нужно (если нужно) заложить в модель данных сейчас, чтобы
подключение СБП в Phase 2 не потребовало переделки `Bill`/`Payment`.

Технически к СБП нельзя подключиться напрямую как физлицу/сервису —
нужен банк-эквайер или платёжный агрегатор с поддержкой СБП C2B (приём
от физлица юрлицу/ИП/самозанятому) — например ЮKassa, CloudPayments,
Т-Business, Point, Сбер. Типовой паттерн: сервис создаёт заказ на
стороне провайдера → получает QR/платёжную ссылку → показывает
арендатору → провайдер шлёт вебхук с подтверждением оплаты → сервис
помечает `Bill`/`Payment` оплаченным. Это то же событие «счёт оплачен»,
что сейчас проставляется вручную — меняется источник события, не сама
модель жизненного цикла счёта.

## Рассмотренные варианты

1. **Ничего не менять сейчас.** Дешевле всего сегодня, но при
   подключении СБП в Phase 2 придётся добавлять поля постфактум и
   мигрировать уже накопленные записи `Payment`/`Bill` — небольшой, но
   реальный риск переделки на проде.
2. **Заложить несколько nullable-полей сейчас**, ничего не реализуя:
   `Payment.method` (enum: `manual` | `sbp` | …, по умолчанию `manual`),
   `Payment.providerTransactionId` (nullable, id операции у
   провайдера — для сверки/идемпотентности), `Bill.paymentLink`/
   `Bill.qrPayload` (nullable, ссылка/QR на оплату, когда провайдер
   подключён). Стоимость — несколько полей в схеме и enum, не логика.
   Разработка на localhost без провайдера продолжает работать как
   раньше (все новые поля пустые).

## Решение

Вариант 2. Поля добавляются в модель сейчас (см. `docs/ARCHITECTURE.md`,
`Payment`/`Bill`). Сама интеграция с провайдером СБП (выбор конкретного
агрегатора/банка, вебхук-эндпоинт, обработка колбэка) — не реализуется
в MVP, кандидат на Phase 2, как и было решено ранее.

Отдельно на будущее (не блокирует эту задачу): если landlord работает
как самозанятый (см. `docs/PRODUCT_QUESTIONS.md`, 10.3 — оператор
ПДн уже определён как физлицо/самозанятый), получение оплаты обязывает
выдавать чек через ФНС «Мой налог» — у большинства агрегаторов есть
готовая интеграция с этим сервисом. Не решается сейчас, но стоит
учитывать при выборе конкретного провайдера в Phase 2.
