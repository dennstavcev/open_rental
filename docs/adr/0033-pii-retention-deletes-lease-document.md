# 0033. Ретеншен ПДн удаляет весь LeaseDocument, не только LeasePartyInfo

Дата: 2026-08-24
Статус: Принято

## Контекст

Живой UX-ревью (Фаза 25, `docs/ux-review/2026-08-24-report-agent-a.md`,
находка A-24, помечена **blocker**) нашёл, что автоматический
3-летний ретеншен ПДн (`PartyInfoService.runRetention`, ADR-0021)
удаляет только зашифрованные строки `LeasePartyInfo`. Те же паспортные
данные — расшифрованные — подставляются при генерации текста договора
и сохраняются как обычная строка в `LeaseDocument.content`; пути
удаления `LeaseDocument` в коде нет вообще. Итог: через три года
зашифрованная запись пропадает, а её расшифрованная копия (серия,
номер, кем выдан, дата рождения, адрес регистрации) остаётся в базе
бессрочно и в открытом виде — обещанный политикой срок хранения
(`backend/src/legal/privacy-policy.const.ts`) фактически не соблюдается.

Отдельно та же находка (A-12) зафиксировала, что у пользователя нет
способа воспользоваться правами, перечисленными в политике (отозвать
согласие, запросить удаление до истечения 3 лет) — ни эндпоинта, ни
экрана. UI для этого — часть будущего `/profile` (Фаза 29, блок
«Данные и приватность» — владелец решил строить `/profile` сразу
целиком, 2026-08-24), но механизм удаления, который эта UI будет
вызывать, должен быть тем же самым, что описан здесь, — один
сервис-метод для автоматического ретеншена и для ручного запроса, а
не два независимых пути с риском разойтись.

## Рассмотренные варианты

1. Перегенерировать все версии `LeaseDocument` с прочерками вместо
   паспортных данных — документ как факт истории отношений остаётся в
   базе, ПДн из него вычищаются.
2. **Удалять `LeaseDocument` целиком** — не остаётся даже факта
   существования конкретного текста договора.

## Решение

Вариант 2 (выбор владельца, 2026-08-24). При наступлении ретеншена
(3 года после завершения `Lease`, срок не меняется) сервис удаляет:

- все строки `LeasePartyInfo` этого договора (как и раньше);
- **все версии `LeaseDocument` этого договора**, включая `contract`,
  `handover_act` и `return_act` — все три вида документа подставляют
  ПДн сторон (ФИО как минимум, `contract` — ещё и паспортные данные).

Это осознанно означает, что после ретеншена у собственника не остаётся
печатной копии исходного текста договора — только запись `Lease` со
структурированными полями (даты, ставка, статус), которые ПДн не
содержат. Прочие данные Lease/Bill/Payment/MeterReading ретеншеном не
затрагиваются — вычищаются только записи, реально содержащие ПДн.

Один и тот же сервис-метод удаления вызывается:
- ежедневным `@Cron`-джобом при наступлении 3-летнего срока (как и
  сейчас), и
- будущим ручным запросом пользователя из `/profile` → «Данные и
  приватность» (Фаза 29) — досрочный отзыв согласия/запрос на
  удаление до истечения 3 лет, с той же честной оговоркой про
  удержание на срок исковой давности, если применимо.

## Последствия

- Уточняет `docs/adr/0021-lease-party-personal-data.md` и
  `0022-party-info-frontend-and-consent.md` в части того, что именно
  считается «удалением по ретеншену» — раньше подразумевалось (неявно)
  только `LeasePartyInfo`, теперь явно весь набор ПДн-содержащих
  записей договора.
- Требует пройтись по всем трём `LeaseDocument.kind` при удалении, не
  только по `contract`.
- Фаза 25 (`docs/DEV_STATE.md`) сводится к backend-фиксу самого
  ретеншена по этому ADR; экран для ручного запроса — в Фазе 29.
- Не требует миграции схемы — меняется только логика
  `PartyInfoService.runRetention`, удаление существующих записей
  делается тем же Prisma-клиентом.
