# 0030. Email-канал уведомлений — self-hosted Postfix на своём сервере

Дата: 2026-08-24
Статус: Принято

## Контекст

`NotificationChannel` (интерфейс, `backend/src/notifications/`) сейчас
имеет единственную реализацию — `ConsoleNotificationChannel`, пишет в
серверный консольный лог, невидимый ни одному реальному пользователю.
ADR-0006 сознательно отложил выбор прод-провайдера «до решения по
хостингу» — направление хостинга с RU-локацией уже выбрано (ADR-0021).
Ревью 2026-08-24 (`docs/DEV_STATE.md`, Фаза 14) зафиксировало это как
главный пробел: без реального канала недоступны верификация email при
регистрации, восстановление пароля, доставка приглашения арендатору и
дублирование уведомлений на почту.

Владелец продукта (2026-08-24) определил направление: поднять Postfix
на собственном сервере и слать уведомления/отчёты через него, а не
подключать стороннего провайдера-агрегатора (SendGrid/Mailgun/Unisender
GO/Yandex Cloud и т.п.).

## Рассмотренные варианты

1. **Сторонний транзакционный email-провайдер (SaaS).** Быстрее в
   настройке, готовая репутация IP/инфраструктура доставляемости из
   коробки, но: ежемесячная стоимость, зависимость от внешнего
   сервиса, содержимое писем (в т.ч. потенциально данные, смежные с
   ПДн — email арендатора, детали договора) уходит на инфраструктуру
   третьей стороны — ещё один внешний получатель данных вдобавок к уже
   принятому RU-хостингу (ADR-0021).
2. **Self-hosted Postfix на собственном сервере (выбор владельца).**
   Полный контроль над данными и инфраструктурой, без ежемесячной
   платы провайдеру, естественно продолжает уже принятое направление
   RU-локализации данных — почта не покидает контролируемую
   инфраструктуру до момента фактической отправки получателю. Обратная
   сторона: доставляемость (spam-фильтры Gmail/Yandex/Mail.ru жёстко
   фильтруют почту с свежих/непрогретых IP без корректных DNS-записей)
   — целиком забота этой стороны, готовой инфраструктуры репутации
   нет, настраивается с нуля.

## Решение

Вариант 2. `NotificationChannel` получает вторую реализацию —
`EmailNotificationChannel` (nodemailer, SMTP-транспорт на локальный/
внутренний Postfix, без стороннего API). Она подключается наряду с
`ConsoleNotificationChannel` (дев/тест окружение продолжает работать на
консольной заглушке), выбор — через конфигурацию окружения, как и
предполагал ADR-0006.

Поверх канала реализуются (Фаза 14, `docs/DEV_STATE.md`):
подтверждение email при регистрации, восстановление пароля, дублирование
существующих уведомлений на почту, доставка приглашения арендатору.

**Обязательный чек-лист доставляемости при реализации — без него письма
массово улетят в спам, это не опционально:**

- SPF-запись на домене отправителя, разрешающая IP сервера;
- DKIM-подпись исходящих писем (Postfix + `opendkim`/аналог);
- DMARC-запись (хотя бы `p=none` для мониторинга на старте);
- корректная PTR-запись (обратный DNS) на IP сервера — многие
  провайдеры (в т.ч. Gmail) отклоняют почту без неё;
- прогрев IP — резкий старт большого объёма писем с нового IP сам по
  себе триггерит спам-фильтры, начинать с малого объёма;
- мониторинг bounce/жалоб — если процент возвратов начнёт расти,
  разбираться сразу, не копить.

Если, несмотря на чек-лист выше, доставляемость на проде окажется
неудовлетворительной (аналогично тому, как ADR-0008 предусмотрел
переход с Tesseract на Yandex Vision при недостаточной точности OCR) —
рассмотреть smart-host через стороннего провайдера как relay, не меняя
остальную архитектуру. Не блокирует старт с self-hosted Postfix.

## Последствия

- `docs/DEV_STATE.md`, Фаза 14 — открытый вопрос «какой провайдер»
  закрыт; технический контур описан выше, чек-лист доставляемости —
  часть определения готовности задачи.
- `docs/adr/0006-auth-mechanism.md` — не отменяется, этот ADR как раз и
  есть решение, которое ADR-0006 откладывал «до решения по хостингу».
- Не отменяет и не заменяет ADR-0029 (сервис не проводит арендную
  плату) — email-канал обслуживает уведомления/верификацию/отчёты, не
  денежный поток.
