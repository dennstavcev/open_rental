# 0028. Портфель объектов в отчёте собственника

Дата: 2026-08-24
Статус: Принято

## Контекст

Отчёт собственника агрегирует доход, задолженность, просрочки и сроки по
договорам, но не показывает объекты как самостоятельные сущности. Поэтому
объект без договора исчезает из отчёта, а собственник не видит в одном месте
статус аренды, незакрытые заявки и согласованные, но ещё не выставленные суммы.
Список объектов уже использует структурированный город и кеш адреса из
[ADR-0026](0026-structured-property-address.md), а денежный тракт заявки и знак
доли арендатора по плательщику определены
[ADR-0025](0025-maintenance-to-service-to-bill.md).

Главный риск нового представления — получить вторую реализацию дохода и долга.
Она неизбежно могла бы разойтись с существующими тематическими блоками отчёта.
Кроме того, `Lease.landlordId` и `Property.ownerId` не связаны инвариантом
равенства на уровне схемы, а уникальный индекс не гарантирует единственный
договор в статусе `active` для объекта.

## Рассмотренные варианты

1. Добавить отдельный запрос и независимо пересчитать деньги по объектам.
   Отклонено: два места вычисляли бы одни показатели и со временем разошлись.
2. Загружать объекты, заявки и услуги широкими вложенными `include` вместе с
   договорами. Отклонено: услуги связаны с объектом, а не с договором, все
   объекты нужны даже без договоров, а запрос договоров уже загружает счета со
   строками.
3. Сохранить существующий проход по договорам единственным источником дохода и
   долга, в нём же заполнить копилки объектов, а остальные данные получить
   тремя узкими запросами. Выбран.

## Решение

- Секция «По объектам» размещается первой на `/reports`. В ней показываются все
  объекты собственника, включая простаивающие; существующие тематические
  секции ниже не меняются. Объекты группируются по городу тем же правилом, что
  список объектов, а объекты без города образуют последнюю группу.
- Доход и задолженность объекта накапливаются в том же проходе по договорам и
  теми же выражениями, которыми растут общие итоги отчёта. Второго запроса или
  отдельной реализации этих расчётов нет.
- Пеня остаётся исторически принятой в отчёте формулой
  `penaltyWaived ? 0 : computeAccruedPenalty(...)`. Известное расхождение с
  внутренним поведением `computeAccruedPenalty`, которое для прощённой пени
  возвращает `penaltyWaivedAmount`, намеренно не исправляется в этой фазе.
- Все объекты читаются по `Property.ownerId`. Незакрытые заявки агрегируются по
  статусу и договорам собственника, включая расторгнутые. Согласованные, но не
  выставленные разовые услуги выбираются только одновременно по владельцу
  объекта и по `landlordId` договора исходной заявки; ручные и уже выставленные
  услуги в сумму «на подходе» не входят.
- Расчёт доли арендатора по плательщику выносится из биллинга в общий
  `tenantShareForPayer`. Им пользуются и выставление услуги, и отчёт. Помощник
  возвращает округлённый до копеек `number`, потому что именно так работает
  существующий денежный код биллинга (`toNumber` и `round2`); введение
  параллельного стиля на `Decimal` изменило бы контракт без пользы для этой
  фазы.
- Деньги и заявки объекта наполняются только из договоров, выбранных по
  `Lease.landlordId` текущего собственника. Если у принадлежащего ему объекта
  есть только чужой договор, объект показывается свободным с нулевыми
  показателями: чужие деньги не попадают в портфель.
- Статус объекта определяется приоритетом `active` → `draft`/`sent` →
  свободен. Если активных договоров несколько, действующим считается договор
  с наибольшим `startDate`; его арендатор и месячная аренда показываются в
  строке. Это делает результат детерминированным при данных, которые схема не
  запрещает.
- Итоги портфеля содержат число объектов по трём статусам, число активных
  заявок и подписанную сумму услуг «на подходе». Новых полей БД и миграции нет.

## Последствия

- Собственник видит сдаваемые, ожидающие арендатора и свободные объекты в одном
  отчёте, включая исторический доход расторгнутых договоров.
- Суммы портфеля по построению остаются согласованы с существующими блоками
  дохода и задолженности; будущие изменения этих расчётов нельзя реализовывать
  отдельным проходом только для портфеля.
- Знак суммы услуги имеет единственную реализацию, поэтому прежнее поведение
  биллинга и новое представление отчёта изменяются совместно.
- Для заявок и услуг сохраняются отдельные узкие запросы, зато не появляется
  широкая повторная загрузка счетов и строк договоров.
- Известное различие трактовки прощённой пени остаётся техническим долгом вне
  Фазы 12.
