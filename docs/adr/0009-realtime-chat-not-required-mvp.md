# 0009. Realtime для чата не обязателен в MVP

Дата: 2026-07-22
Статус: Принято

## Контекст

`docs/PRODUCT_QUESTIONS.md`, вопрос 5.3, оставался открытым: нужен ли
чату мгновенный (realtime) режим уже в MVP, или достаточно обновления
по запросу/уведомления. Это влияет на архитектуру (нужен ли
WebSocket-слой) и было в списке "Открытые архитектурные вопросы"
`docs/ARCHITECTURE.md`.

## Рассмотренные варианты

1. **WebSocket с самого начала** (например, NestJS Gateways/Socket.io).
   Даёт мгновенную доставку, но добавляет отдельный слой
   инфраструктуры (постоянные соединения, что усложняет
   масштабирование и локальное тестирование) ради сценария, где
   стороны обычно не переписываются секунда-в-секунду (это не бытовой
   мессенджер, а переписка по конкретному договору).
2. **Обновление по запросу + email-уведомление о новом сообщении.**
   Проще реализовать и тестировать на localhost, не требует
   WebSocket-инфраструктуры вообще. Соответствует общему MVP-принципу
   проекта — не строить то, что не подтверждено как необходимое
   (тот же подход применён к эквайрингу, автоинтеграции с РСО).

## Решение

Вариант 2. Чат обновляется при открытии/действии пользователя (polling
при открытом окне — приемлемо для MVP-нагрузки), плюс email-уведомление
о новом сообщении (компонент Notifications). WebSocket — кандидат на
Phase 2+, если реальное использование покажет, что задержка ощутима для
пользователей.

## Последствия

- Модуль Messaging не требует отдельной realtime-инфраструктуры в
  Phase 1 — упрощает и ускоряет старт разработки, не требует решений,
  связанных с хостингом WebSocket-соединений.
- `docs/PRODUCT_QUESTIONS.md`, 5.3 — закрыт.
- `docs/ARCHITECTURE.md`, «Открытые архитектурные вопросы» — пункт про
  realtime-транспорт чата закрыт этим ADR.
