# 0004. Backend-фреймворк — NestJS (Node.js/TypeScript)

Дата: 2026-07-22
Статус: Принято

## Контекст

ADR-0003 зафиксировал стек на уровне слоёв (React/Next.js + Node/Python
+ PostgreSQL), но оставил backend-фреймворк открытым ("NestJS или
FastAPI — уточняется") и ошибочно посчитал, что это не блокирует старт
Phase 1. На практике это блокирует: без конкретного фреймворка нельзя
начать модуль Auth (первый пункт `docs/ROADMAP.md`, Phase 1). Решение
принимается сейчас, отдельно от вопросов хостинга и юридического
содержания договора/оферты (сознательно вынесены за скобки — см.
`docs/READINESS_AUDIT.md`), поскольку разработка и тесты пока идут на
localhost.

## Рассмотренные варианты

1. **NestJS (Node.js/TypeScript).** Один язык (TypeScript) с frontend
   (Next.js) — меньше контекстных переключений при agent-driven
   разработке в CLI. Встроенный модульный DI-контейнер естественно
   ложится на решение "модульный монолит" (см. ADR-0005). Официальная
   интеграция `@nestjs/schedule` + BullMQ (Redis) закрывает уже
   спроектированный идемпотентный планировщик расчётных периодов
   (`docs/MVP_SCOPE.md`, «Источник времени и планировщик») без
   самодельной обвязки. Зрелая экосистема для auth (Passport.js),
   загрузки файлов (multipart — нужно почти в каждом модуле: фото
   счётчиков, сканы договоров, квитанции), валидации DTO.
2. **FastAPI (Python).** Быстрый, хорошая типизация через Pydantic,
   отличный выбор, если бы в проекте была отдельная ML/data-heavy
   часть (например, свой ML для OCR) — но OCR-движок выбран как
   Tesseract "из коробки" (см. ADR-0008), собственного ML-пайплайна
   на Python не требуется. Плюс — второй язык в проекте (Python
   рядом с TypeScript на фронте) увеличивает когнитивную нагрузку
   без явной компенсирующей выгоды здесь.

## Решение

NestJS (Node.js/TypeScript). ORM — уточняется `backend-dev` при
декомпозиции (Prisma или TypeORM — оба хорошо ложатся на реляционную
модель `docs/ARCHITECTURE.md`), это не отдельный ADR, а деталь
реализации.

## Последствия

- Единый язык (TypeScript) на frontend и backend.
- Планировщик — `@nestjs/schedule` (проверка перехода периодов) +
  BullMQ поверх Redis (идемпотентные джобы, ретраи) — Redis добавляется
  как новая локальная зависимость (docker-compose для дев-окружения).
- Рендер текста договора — шаблонизатор (Handlebars/аналог) +
  HTML-to-PDF (например, Puppeteer) на том же Node-рантайме без
  дополнительного сервиса.
- `docs/ROADMAP.md`, Phase 1: пункт «Backend-фреймворк» закрыт этим ADR.
- Не затрагивает открытый вопрос хостинга/локализации ПДн по 152-ФЗ —
  NestJS одинаково разворачивается на любом хостинге, выбор остаётся
  независимым и сознательно отложенным.
