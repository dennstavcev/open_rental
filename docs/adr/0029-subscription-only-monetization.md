# 0029. Монетизация — только подписка, сервис не участвует в переводе арендной платы

Дата: 2026-08-24
Статус: Принято

## Контекст

ADR-0011 (2026-07-22) заложил в модель `Payment`/`Bill` нейтральные
nullable-поля (`Payment.method`/`providerTransactionId`,
`Bill.paymentLink`/`qrPayload`) под будущее подключение эквайринга
(СБП C2B через банк/агрегатора) для приёма **арендной платы** прямо
через сервис — с явной оговоркой, что это Phase 2+ и не блокирует MVP.
Отсюда же тянется открытый вопрос 7.5 в `docs/PRODUCT_QUESTIONS.md`:
нужно ли отдельное поле под номер банковской карты арендодателя для
такого перевода.

Владелец продукта закрыл направление явно (2026-08-24, планирующий
чат): сервис **никогда** не будет технически посредником в передаче
денег между арендодателем и арендатором. Карты не нужны — не как
временное упрощение MVP, а как постоянное архитектурное решение.
Арендная плата всегда платится сторонами друг другу напрямую и вне
сервиса — ровно то, что уже реализовано номинальным флоу ADR-0012
(«Я оплатил» → «Оплата получена»), но теперь ясно, что это финальное
состояние, а не промежуточный шаг перед эквайрингом ренты.

Собственный источник дохода сервиса — **подписка**, которую платит
арендодатель за пользование сервисом (см. `docs/ROADMAP.md`, Phase 3,
«Монетизация»). Это единственный сценарий, где сервису вообще
понадобится приём платежей через провайдера/эквайринг — и это деньги
клиента сервису, а не деньги арендатора арендодателю.

## Рассмотренные варианты

1. **Оставить открытым (текущее состояние).** ADR-0011 остаётся в силе,
   7.5 остаётся открытым вопросом клиенту. Проблема — раз владелец уже
   дал однозначный ответ, держать вопрос «открытым» в документации
   вводит в заблуждение будущие сессии и блокирует закрытие 7.5 без
   причины.
2. **Явно закрыть: сервис никогда не проводит арендную плату, эквайринг
   нужен только под подписку.** Соответствует прямому решению владельца
   продукта, снимает открытый вопрос 7.5 окончательно, не оставляет
   пространства для случайного повторного открытия этой темы будущей
   сессией «раз уж эквайринг всё равно понадобится».

## Решение

Вариант 2. Зафиксировано:

- Сервис не хранит и не обрабатывает реквизиты банковских карт ни
  сейчас, ни в обозримом будущем для **функции аренды**. Поле под номер
  карты **не нужно** — вопрос 7.5 закрыт окончательно, не как «сейчас
  не делаем», а как «не нужно по архитектуре».
- Номинальный флоу подтверждения оплаты (ADR-0012, «Я оплатил» / «Оплата
  получена», без участия провайдера) — не временная MVP-заглушка до
  эквайринга ренты, а постоянное целевое поведение. Пеня и вся денежная
  логика по `Bill`/`Payment` продолжают работать по этой модели без
  изменений.
- ADR-0011 помечается **устаревшим**: его результат (nullable-поля
  `Payment.method`/`providerTransactionId`, `Bill.paymentLink`/
  `qrPayload`) физически остаётся в схеме — миграция не требуется, поля
  безвредны и всегда пусты — но их первоначальное назначение (эквайринг
  аренды) больше не актуально. Трогать эти поля сейчас не нужно;
  возможное будущее удаление — самостоятельная задача по техдолгу, не
  приоритет.
- Единственный будущий сценарий, где сервису понадобится интеграция с
  платёжным провайдером — приём **оплаты подписки** от арендодателя
  (Phase 3, монетизация). Это деньги клиента сервису, принципиально
  другой денежный поток, чем аренда между сторонами. Модель данных под
  подписку — отдельная сущность (`Subscription`/`SubscriptionPayment`
  или аналог), не переиспользование `Payment`/`Bill` (те жёстко привязаны
  к `Lease` и семантике аренды). Конкретная модель и провайдер — предмет
  отдельного ADR, когда монетизация дойдёт до реализации; не решается
  сейчас.

## Последствия

- `docs/PRODUCT_QUESTIONS.md`, 7.5 — закрыт окончательно, ссылка на этот
  ADR.
- `docs/adr/README.md` — ADR-0011 помечен «Устарело (заменено ADR-0029)».
- `docs/ROADMAP.md`, Phase 2 — пункт «приём платежей через эквайринг»
  для ренты снят (это не в архитектуре сервиса); Phase 3 «Монетизация» —
  единственное место, где вообще встаёт вопрос эквайринга, и то для
  подписки, не для аренды.
- `docs/ARCHITECTURE.md` — секции `Bill`/`Payment` дополнены пометкой,
  что задел под эквайринг унаследован от устаревшего ADR-0011 и не
  используется по архитектуре сервиса.
- Не влияет на уже принятые решения по реквизитам арендодателя для
  ручного перевода (`payoutPhone`/`payoutBankName`/`payoutNote`,
  ADR-0019) — они остаются, это не эквайринг, а просто данные для
  ручного перевода вне сервиса.
