## Источник

**Claude Design, проект "OpenRent Design System"**
(https://claude.ai/design/p/9d23e4c8-1e7a-44a7-862a-3d3e5fb89e0e) —
импорт через MCP `claude_design` в CLI не подключился (`/design-login`
недоступен в среде); handoff получен как zip-экспорт проекта
(`OpenRent Design System-handoff.zip`), приложенный CEO напрямую в
чат 2026-07-23, и разобран из него. Экспорт содержит токены (CSS custom
properties), 5 готовых React-компонентов, 5 экранов клик-тру прототипа и
2 референсных скриншота исходного Figma-макета
(https://www.figma.com/design/sYKpsyXDvmj0cDWTKC5bTF/OpenPay), из которых
эта дизайн-система была сгенерирована. Figma как отдельный источник
доступа не имела — все данные из неё уже прошли через Claude Design
handoff, повторно Figma не разбирается.

Как и любой референс — отправная точка, не буквальная спецификация;
расхождения с `docs/USER_FLOWS.md`/`docs/MVP_SCOPE.md` решаются в пользу
документации (см. пример ниже, «Экраны вне источника»).

## Тон и стиль текста

Тёплый, спокойный, премиальный лайфстайл-тон — не формально-юридический,
не подчёркнуто игривый (закрыто `docs/PRODUCT_QUESTIONS.md`, 15.3).

- Обращение на «вы», вежливо-нейтральное.
- Короткие императивы на кнопках: «Войти», «Сохранить», «Отмена» — без
  восклицательных знаков.
- Лейблы полей — существительные, не описания: «Почта», «Пароль», «Тип
  счётчика», «Параметр», «Стоимость».
- Заголовки экранов — человеческие, не корпоративные: «Войдите в личный
  кабинет», не «Авторизация пользователя».
- Эмодзи не используются нигде.
- Интонация — «уютный дом», а не банковское приложение: система
  визуально обещает «разберёмся спокойно».

## Цвет

Приглушённая земляная палитра: кремовый/песочный → терракотовый →
холодный серо-голубой низ. Единственный яркий акцент — фиолетовый
градиент на ключевых CTA (уже зафиксировано, `docs/PRODUCT_QUESTIONS.md`
15.3). Полные значения — `frontend/app/globals.css` (раздел «Design
tokens»), исходник — `tokens/colors.css` из handoff.

| Токен | Значение | Назначение |
|---|---|---|
| `--cream-50` / `--cream-100` | `#faf3e7` / `#f1e2c9` | верх фото-фона, светлые поверхности |
| `--sand-200..400` | `#e6cda3`…`#cdb68c` | переход фона, вторичные поверхности |
| `--terracotta-300..700` | `#d98a5c`…`#8a3a1c` | тёплый бренд-акцент (некликабельный, декоративный) |
| `--brass-300..700` | `#b98f45`…`#5c471f` | металлический акцент (декор) |
| `--fog-300/500` | `#9aa39c` / `#7c7761` | низ фото-фона, холодный нейтральный |
| `--ink-900/700` | `#241b12` / `#3a2e1f` | текст на светлых поверхностях |
| `--violet-400/500/700` | `#b585ea` / `#9b52d9` / `#5330cf` | **единственный** насыщенный/холодный акцент — CTA-градиент, ссылки |

Семантические алиасы (используются в коде, не сырые токены):
`--surface-app-gradient`, `--surface-card`, `--surface-input`,
`--surface-btn-primary`, `--gradient-accent`, `--border-subtle`,
`--border-input`, `--text-on-photo`, `--text-on-light`, `--accent-primary`.

Правило: фиолетовый — **только** на первичных CTA и ссылках. На любой
другой поверхности (иконки, декоративные элементы, статусы) — не
используется, иначе теряет функцию «это действие».

## Типографика

Шрифт — **Manrope** (Google Fonts). В источнике не было файлов фирменного
шрифта (только растровые скриншоты Figma) — Manrope выбран как ближайший
геометричный тёплый аналог с поддержкой кириллицы. Если у клиента
появятся фактические файлы бренд-шрифта — заменить в
`frontend/app/globals.css` и учесть лицензию.

| Токен | Значение |
|---|---|
| `--text-xs` … `--text-4xl` | 12 / 13 / 15 / 16 / 18 / 20 / 24 / 28 / 34 px |
| `--leading-tight/normal/relaxed` | 1.15 / 1.4 / 1.6 |
| `--weight-regular/medium/semibold/bold` | 400 / 500 / 600 / 700 |
| `--tracking-tight/normal/wide/label` | -0.01em / 0 / 0.02em / 0.03em |

Заголовки экранов — `--text-xl`, `--weight-semibold`, по центру шапки
(входные формы) или слева (списки/детали). Лейблы полей — `--text-xs`,
`--weight-medium`, `--tracking-label`, приглушённый цвет.

## Отступы и радиусы

| Токен | Значение |
|---|---|
| `--space-1` … `--space-20` | 4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48 / 64 / 80 px |
| `--screen-padding` | 24px (горизонтальный отступ экрана) |
| `--container-mobile` | 400px |
| `--radius-sm/md/lg/pill` | 10 / 16 / 22 / 999px |

Правило радиусов: нигде не острые углы, нигде экстремальное скругление
карточек — 10/16/22px по контексту (мелкий элемент → крупная
поверхность), капсула (`pill`) только на кнопках.

## Эффекты

- `--blur-frost: 18px` — frosted-glass слой поверх фото на экранах с
  формами (см. «Фото-фон» ниже).
- `--shadow-card`, `--shadow-btn` — минимальные, почти не используются;
  тень только на белой primary-кнопке, чтобы читалась как «физический»
  приподнятый объект.
- `--duration-fast: 120ms`, `--duration-base: 200ms`,
  `--ease-standard: cubic-bezier(.4,0,.2,1)` — сдержанные hover/focus
  переходы, без bounce/spring.
- Hover на кнопках — `translateY(-1px)`; на инпутах — светлее фон +
  ярче обводка при фокусе. Press отдельно не задокументирован в
  источнике — используется тот же fade, без shrink/scale.

## Ограничение по разрешению фото-ассета

Единственный UI-свободный вариант фирменного фото в handoff —
`assets/photo-interior-warm.png`, **367×340px**. Все остальные ассеты
источника (`ref-screen-*.png`, скриншоты карусели) крупнее по разрешению,
но с вшитыми в пиксели текстом/плитками/frost — непригодны как чистая
подложка. Растягивать 367px-картинку через `background-size: cover` на
всю ширину широкого десктопного окна даёт заметную пикселизацию.
**Решение:** фото живёт в колонке шириной `--photo-panel-w` (430px, чуть
больше `--container-mobile`), отцентрованной на странице — на реальных
мобильных экранах (основной сценарий, см. `docs/MVP_SCOPE.md`) колонка
равна ширине вьюпорта, ничего не меняется; на широком десктопе по бокам —
`--surface-app-gradient`, а не растянутое фото. Если у клиента появится
исходник фото большего разрешения (без вшитого UI) — можно снять это
ограничение, заменив ассет.

## Фото-фон (фирменный визуальный якорь)

Полноэкранное тёплое интерьерное фото (закатный свет, охристая стена,
терракотовое кресло, латунная кадка, подвесной светильник,
`assets/photo-interior-warm.png` в handoff) — главный визуальный якорь
источника. Frosted-слой (`backdrop-filter: blur`) поверх фото — только на
экранах с формами (вход, регистрация, добавление счётчика), тёмный
полупрозрачный скрим держит текст читаемым. На «витринных» экранах
(первый вход, карточка объекта в источнике) фото видно без скрима.

**Решение по применению вне источника (см. `docs/adr` не заводится,
т.к. это дизайн-детализация, не архитектура — фиксируется здесь):**
источник — это клик-тру всего на 5 экранов минималистичного прототипа
(один объект, без таблиц/списков/отчётов). В реальном MVP есть плотные
экраны с данными (дашборд, таблицы объектов/договоров, отчёты,
уведомления, чат) — полноэкранное фото под таблицей/списком снижает
читаемость и противоречит принципу «форма после функции» для рабочих
экранов. Поэтому:

- **Экраны входа (`/login`, `/register`)** — точное воспроизведение
  референса: `photo-backdrop` с фото + frost, капсульные инпуты/кнопки,
  верхняя панель с одной стрелкой назад, без бокового меню/nav (это
  экраны до входа в приложение, TopBar-с-навигацией там не показывается
  и раньше не показывался). Это единственные экраны, что реально
  показаны в источнике как формы, и единственные без постоянного
  app-shell (сайдбар/таб-бар).
- **Онбординг-мастер (`/onboarding`) и все остальные рабочие экраны**
  (дашборд, объекты, договоры, счета, отчёты, уведомления, чат) —
  используют `--surface-app-gradient` (тот же палитровый переход, что и
  на фото — кремовый → терракотовый → серо-голубой) как фон вместо
  буквального фото. Причина отличия от изначального плана: онбординг
  хоть и «ведущий» по тону (см. `docs/CHANGELOG.md`, 2026-07-23), technически
  это плотная многошаговая форма (4 шага, десятки полей) поверх
  постоянного app-shell (TopBar/сайдбар) — то есть по структуре он ближе
  к «рабочим» экранам, чем к одноразовым экранам входа без навигации.
  Фото под таким объёмом полей/карточек ухудшает читаемость — тот же
  аргумент, что и для дашборда/таблиц. Тон и палитра при этом сохраняются:
  карточки/таблицы — полупрозрачные кремовые поверхности (`--surface-card`)
  поверх градиента, той же логики, что инпуты в источнике.
- Это расхождение с буквальным «фото на КАЖДОМ экране» из источника —
  по аналогии с уже решённым прецедентом (`docs/CHANGELOG.md`,
  2026-07-22: макет — не буквальная спецификация порядка/состава
  экранов, а материал для разбора).

## Компоненты

Портированы из handoff почти без изменений (адаптация — Next.js
`className`/CSS вместо inline-`style`, чтобы не тащить сотни style-
объектов в каждый файл):

- **PhotoBackdrop** — фон-фото + опциональный frost (`.photo-backdrop`,
  `.photo-backdrop.frosted`).
- **Button** — 4 варианта: `primary` (белая заливка, capsule, для
  экранов на фото), `accent` (фиолетовый градиент, для CTA на витринных
  экранах), `secondary` (полупрозрачная с обводкой), `text` (без фона).
  На **не-фото** (обычных «рабочих») экранах primary/secondary адаптированы
  под светлый фон — см. «Экраны вне источника» ниже.
- **Input / FormField** — полупрозрачное поле, обводка 1px, radius-md,
  подписанный лейбл сверху (`--text-xs`, `--tracking-label`).
- **AddTile** — пустое состояние «+»: крупный (64px, «Добавить
  помещение») и компактный (72px, строки списков) варианты.
- **TopBar** — шапка: стрелка назад слева, заголовок по центру
  (опционально с ✓), настройки/действие справа.

### Состояния

| Компонент | Обычное | Hover | Фокус | Ошибка | Загрузка | Пусто |
|---|---|---|---|---|---|---|
| Button | заливка/обводка по варианту | `translateY(-1px)` | — | — | `disabled`, opacity .5, текст меняется на «…» (уже в коде: «Вход…», «Сохранение…») | — |
| Input | `--surface-input`, обводка `--border-input` | — | обводка `--border-input-focus`, фон `--surface-input-hover` | красная подпись под полем (`.error`, см. ниже) | — | placeholder = лейбл |
| Список/таблица | строки с `--surface-card` | строка чуть светлее | — | текст ошибки над списком | текст «Загрузка…», приглушённый | `AddTile`/`.empty` — «Объектов пока нет» и т.п. |
| Карточка-ссылка | `--surface-card` | обводка ярче | — | — | — | — |

Ошибки полей/форм в источнике не показаны (5 happy-path экранов) —
расширено по уже существующему паттерну приложения (`.error`, красный
текст под формой, `docs/USER_FLOWS.md` не переопределяет).

## Иконография

Источник использует минимум иконографии — символьные глифы (`←`, `⚙`,
`✓`, `+`), без SVG-библиотеки. Это буквально применено на `TopBar` в
входных формах и `AddTile`. Для **бокового меню/нижней таб-навигации**
(sidebar/bottom-nav, есть в приложении, но не показаны в источнике —
источник вообще не включает многопунктовую навигацию) — оставлен
существующий инлайн-SVG icon-набор (`components/TopBar.tsx`, `Icon`) в
стиле line-icons: 5 текстовых глифов недостаточно различимы для 5+
пунктов навигации. Это расширение вне источника, решение `designer`
(не буквальная копия, т.к. источник вопрос не покрывает).

## Логотип

В источниках нет — используется словесный знак «SOFTRENT» обычным
текстом, семейство Manrope, `--weight-bold`, буквенный tracking по
умолчанию. (Проект в Claude Design исторически называется «OpenRent
Design System» — переименование продукта в SoftRent, 2026-07-24.) Если появится реальный логотип — добавить как отдельный ADR/
CHANGELOG-запись и файл `frontend/public/logo.svg`.

## Спеки экранов (из источника)

### Вход (`/login`)

`PhotoBackdrop frosted` → `TopBar` (только стрелка назад) → заголовок
«Войдите в личный кабинет» (по центру) → `Input` «Почта» → `Input`
«Пароль» (type=password) → `Button primary` «Войти» → текст «или»
(по центру, приглушённый) → `Button secondary` «Регистрация». Максимальная
ширина контента — 340px, по центру.

### Регистрация (`/register`)

Аналогично: заголовок «Регистрация» → `Input` «Почта» → `Input` «Пароль» →
`Input` «Повторите пароль» → `Button primary`. (В реализованном
приложении дополнительно есть поле ФИО и пояснение про роль по связям —
это уже принятое продуктовое решение, `docs/CHANGELOG.md` 2026-07-23,
источник его не отменяет, просто не показывает.) **Отклонение от
буквального текста источника:** в исходном экране кнопка сабмита на
регистрации подписана «Войти» — очевидная неточность копирайтинга самого
прототипа (кнопка регистрации не может звать «Войти»), оставлена
«Зарегистрироваться» как в уже реализованном приложении — по тому же
принципу «референс не читается буквально там, где это вводит в
заблуждение» (`docs/CHANGELOG.md`, 2026-07-22).

### Первый экран / «Добавить помещение»

`PhotoBackdrop` без frost → в правом верхнем углу `Button accent`
«Войти» + иконка настроек → внизу экрана (`margin-top: auto`) подпись
«Добавить помещение» + `AddTile` (64px). **Важно**: это не превью-режим
до входа — по уже зафиксированному решению (`docs/PRODUCT_QUESTIONS.md`
15.3.а) добавление объекта доступно только после регистрации; в
реализации этот визуальный паттерн (фото + AddTile снизу) используется
как пустое состояние `/properties` для залогиненного пользователя, а не
как экран до входа.

### Карточка объекта

`PhotoBackdrop` без frost → `TopBar` (заголовок = адрес + ✓, настройки
справа) → `AddTile` с лейблом «Арендаторы» → `AddTile` с лейблом
«Счётчики» (компактный, 72px).

### Добавление счётчика

`PhotoBackdrop frosted` → шапка: «Отмена» (текст-кнопка слева) —
«Новый счётчик» (заголовок по центру) — «Сохранить» (текст-кнопка,
акцентный цвет, справа) → `FormField` «Тип счётчика» → ряд из двух
`FormField` («Параметр» / «Стоимость») → `FormField` «Название».

## Экраны вне источника (расширение designer)

Модули `docs/MVP_SCOPE.md`, которых нет в 5 экранах источника (дашборд,
объекты-список/таблица, договоры, счета/платежи, заявки, чат, отчёты,
уведомления, настройки) — оформляются тем же токенным набором
(`--surface-app-gradient` фон, `--surface-card` карточки/таблицы,
`Button`/`Input` в светлой адаптации, `--radius-md/lg`, та же
типографика), без буквального фото-фона (см. «Фото-фон» выше). Sidebar/
bottom-nav — расширение вне источника, см. «Иконография». Если в
будущем появятся конкретные Claude Design/Figma-экраны под эти модули —
они приоритетнее данного раздела, уточняется у CEO при расхождении.

## Определение «готово»

Экран можно реализовывать без уточнений по визуальным решениям, если он
покрыт разделом «Спеки экранов» выше буквально, или явно описан в
«Экраны вне источника» как использующий базовые токены/компоненты. Новые
паттерны, не покрытые ни тем ни другим — эскалация `designer`/CEO, не
самостоятельное изобретение `frontend-dev`.
