# Идея проекта

> Статус: черновик для обсуждения. Не финальная версия — правится по мере
> уточнения с владельцем продукта.

## Рынок и позиционирование

**Целевой рынок — Россия (РФ), физические лица.** Не маркетплейс и не
сервис поиска/подбора недвижимости — продукт не помогает найти
арендатора или объект. Это коммуникационно-биллинговый слой поверх уже
существующих отношений аренды: договор/договорённость уже есть (или
заключается через сервис), сервис делает жизнь вокруг него проще.

Сегмент MVP: **физлица-собственники, 1–20 объектов** (не управляющие
компании и не крупные портфели).

## Проблема

Коммуникация между арендодателем и арендатором помещения сейчас размазана
по мессенджерам, звонкам, бумажным распискам и устным договорённостям:

- нет единой истории переписки и договорённостей по конкретному объекту;
- заявки на ремонт/обслуживание теряются или решаются "на словах";
- нет прозрачной истории платежей и напоминаний об оплате;
- документы (договор, акты, чеки) разбросаны по почте/чатам;
- при смене арендатора или споре сложно восстановить, что было согласовано;
- начисление коммуналки — ручная рутина: снять показания, посчитать по
  тарифу, свести с арендной платой в один счёт;
- квитанции/чеки по коммуналке нужно вручную разбирать и сверять.

## Решение

Веб-сервис, где на каждый объект/договор аренды заводится общее
пространство для арендодателя и арендатора. Главная цель — **не продать
и не сдать недвижимость, а упростить и унифицировать коммуникацию** между
двумя сторонами уже существующей аренды:

- типовой договор аренды, формируемый внутри сервиса по шаблону (мастер
  с вопросами → готовый текст), не просто загрузка файла;
- переписка, привязанная к объекту/договору, с меткой "официальное
  сообщение" для юридически значимых уведомлений;
- заявки на обслуживание/ремонт техники со статусами;
- **выставление счетов за аренду**, где собственник сам выбирает состав
  счёта (аренда, интернет, коммуналка, что угодно ещё);
- **показания счётчиков**: ввод показаний (в MVP — вручную арендатором,
  с фото), с прицелом на автоматизацию получения показаний/тарифов через
  API сбытовых компаний в будущем (риск/уточнение — см. открытые вопросы
  и `docs/ARCHITECTURE.md`);
- **автоматическое распознавание данных с квитанций** (OCR) — чтобы не
  вбивать суммы вручную;
- хранение документов (договор, акты, чеки, фото состояния объекта);
- история платежей, напоминания об оплате и о просрочках;
- уведомления о новых сообщениях/заявках/платежах/приближении окончания
  договора.

Подробная разбивка по модулям и экранам — `docs/MVP_SCOPE.md`.

## Целевые пользователи

- **Арендодатель (собственник)** — физлицо, владеет 1–20 объектами,
  сдающимися в аренду. Хочет меньше ручной работы: не считать коммуналку
  вручную, не гонять переписку по мессенджерам, видеть по каждому
  объекту, кто должен и сколько.
- **Арендатор** — снимает помещение. Хочет быстро донести проблему,
  видеть прозрачный состав счёта (что именно и почему начислено), не
  терять договорённости и историю оплат.

## Ценность

Единый источник правды по отношениям "арендодатель — арендатор — объект":
история сохраняется, заявки структурированы, счета прозрачны и
автоматизированы там, где это возможно, коммуналка не требует ручного
пересчёта.

## Закрыто брифом CEO (2026-07-17)

- **Рынок** — только РФ, физлица-собственники 1–20 объектов. Не
  маркетплейс, поиска/подбора объектов нет.
- **Договор** — формируется внутри сервиса по шаблону/мастером, а не
  просто загружается файлом (см. `docs/MVP_SCOPE.md`, модуль договоров).
- **Платформа MVP** — веб (см. ADR-0001), явного требования на мобильное
  приложение к MVP нет.
- **Платежи в MVP** — фиксация факта оплаты вручную, без интеграции с
  платёжным шлюзом на старте (см. `docs/MVP_SCOPE.md`, раздел 8).

2. ~~Реальный приём платежей (эквайринг) — нужно ли уже в MVP
   закладывать архитектуру под это?~~ **Закрыто (2026-07-22):** да,
   заложены nullable-поля (`Payment.method`/`providerTransactionId`,
   `Bill.paymentLink`/`qrPayload`) без реализации в MVP. Направление —
   СБП через банк/платёжного агрегатора (не прямое подключение к
   СБП/НСПК). См. `docs/adr/0011-payment-bill-future-acquiring-readiness.md`.
3. Юридическая сила документов и подписи в сервисе — **закрыто (клиент,
   2026-07-22), больше не блокер.** Сервис не вводит собственную
   электронную подпись — основное юридическое подтверждение
   заключения договора: подписанный скан документа на руках у обеих
   сторон (физическая подпись вне сервиса + загрузка скана каждой
   стороной). Обычная письменная форма, юридическая сила которой не
   вызывает вопросов — консультация юриста по e-signature не требуется
   для старта разработки. См. `docs/MVP_SCOPE.md`, модуль договоров.
4. Автоматическое получение показаний счётчика и тарифов по API
   сбытовой компании — **решено для MVP (не блокирует старт):** в MVP
   только ручной ввод показаний с фото + OCR-распознавание с
   подтверждением (см. `docs/MVP_SCOPE.md`, модуль платежей).
   Автоинтеграция через API остаётся риском для Phase 2, требует
   отдельного технического исследования `architect` до включения в
   спринт — сам риск не снят, просто не блокирует MVP.
5. OCR распознавания квитанций — на какие поля/провайдеров квитанций
   ориентируемся в первую очередь (единый формат квитанции в РФ
   отсутствует)? **Остаётся открытым, кандидат на Phase 2** (не путать
   с OCR показаний счётчика — это решено и в MVP).
6. Монетизация — **частично закрыто (клиент, 2026-07-21):** направление
   — подписка + вероятная реферальная программа. Точные цены/лимиты не
   определены, см. `docs/PRODUCT_QUESTIONS.md`, раздел 3.

Ответы на эти вопросы фиксируются как ADR в `docs/adr/` по мере принятия
решений (см. `docs/DOCUMENTATION_RULES.md`).

   инфраструктура (Google/Mozilla/Microsoft) только ретранслирует
   зашифрованный payload, сервис ни с кем не делится данными сверх

   работает только после «Добавить на экран» (с iOS 16.4). Реализуется
   как второй `NotificationChannel` рядом с будущим email-каналом —
   вызывающий код (`NotificationsService.notify()`) не меняется.

13. **История изменения тарифа счётчика — не баг.** `Meter.tariff`
    действительно плоское поле без истории
    (`prisma/schema.prisma:553`), но это не создаёт риска: стоимость
    расхода считается и записывается в `BillLineItem.amount` **один
    раз, в момент подачи показания** (`meter-readings.service.ts:114`,
    `cost = round2(consumption * meter.tariff)`), значение навсегда
    фиксируется в уже созданной строке счёта. Смена тарифа задним числом
    никак не трогает прошлые `BillLineItem` — влияет только на
    следующее показание. Единственный нюанс (не баг, стандартное для
    такого рода начислений поведение): если тариф меняется в середине
    периода между двумя показаниями, весь расход за интервал считается
    по тарифу, действующему на момент подачи показания, без деления
    периода пропорционально. Если понадобится — отдельное решение, не
    сейчас.
