# Правила фиксации реперных точек

Цель: любое значимое решение или изменение по проекту должно быть
восстановимо позже — кто/что/когда решил и почему. Реперная точка —
любое из перечисленного ниже, не только технические решения.

## Что считается реперной точкой

1. **Архитектурное/техническое решение** — выбор стека, структуры
   данных, паттерна, стороннего сервиса, отказ от варианта.
2. **Смена скоупа** — добавили/убрали фичу или сущность из плана.
3. **Смена статуса этапа** — этап roadmap начат, закрыт, отложен.
4. **Продуктовое решение** — что и для кого делаем, целевая аудитория,
   ценностное предложение (см. `docs/IDEA.md`).
5. **Изменение модели данных** — новая сущность, изменение связи между
   существующими.
6. **Отклонение от ранее принятого решения** — если меняем то, что уже
   зафиксировано ADR.

Мелкие технические детали реализации (имя переменной, форматирование
кода) — не реперная точка, в md не фиксируются.

## Куда и как записывать

| Тип точки | Куда | Как |
|---|---|---|
| Архитектурное/техническое решение (п.1, п.6) | `docs/adr/NNNN-название.md` | Новый ADR по шаблону `0000-template.md`. Если решение отменяет старое — старому ADR ставится статус "Устарело (заменено ADR-XXXX)", новому — "Принято". |
| Смена скоупа / модель данных (п.2, п.5) | `docs/ARCHITECTURE.md` или `docs/IDEA.md` (в зависимости от природы) + запись в `docs/CHANGELOG.md` | Обновить актуальный раздел документа (без истории внутри него) + одна строка в CHANGELOG с датой. |
| Смена статуса этапа (п.3) | `docs/ROADMAP.md` + `docs/CHANGELOG.md` | Обновить статус/чекбоксы в ROADMAP + запись в CHANGELOG. |
| Продуктовое решение (п.4) | `docs/IDEA.md` + `docs/CHANGELOG.md` | Обновить IDEA.md, закрыть соответствующий "открытый вопрос", если он был + запись в CHANGELOG. |

Правило по умолчанию: **CHANGELOG.md получает запись при любой
реперной точке**, независимо от того, куда ещё она записана. Остальные
файлы (ARCHITECTURE, IDEA, ROADMAP) хранят только актуальное состояние
— их не нужно захламлять историей, история живёт в CHANGELOG и ADR.

## Формат записей

**ADR** — по шаблону `docs/adr/0000-template.md`: Контекст → Рассмотренные
варианты → Решение → Последствия. Нумерация сквозная, без пропусков.
Статус: `Предложено` / `Принято` / `Отклонено` / `Устарело`.

**CHANGELOG** — группировка по дате (`## YYYY-MM-DD`), новые записи
сверху, внутри секции `### Добавлено` / `### Изменено` / `### Статус`
(по аналогии с Keep a Changelog). Ссылаться на ADR по номеру, если
применимо.

**ROADMAP** — чекбоксы `[ ]` / `[x]`, статус этапа одним из значений:
`не начат` / `в работе` / `готово` / `отложен`.

Даты — везде в формате `YYYY-MM-DD`.

## Когда обновлять

Обновление документации — часть самого решения, а не отдельная задача
"на потом". Решение считается принятым только после того, как
соответствующий md-файл обновлён.

## Чек-лист при добавлении сущности/события (с 2026-08-24)

Ревью 2026-08-24 (`docs/DEV_STATE.md`, Фазы 13–17) нашло повторяющийся
паттерн: у нескольких сущностей (`Lease` draft, `Property`,
`MaintenanceRequest`) и у нескольких межсторонних событий (приглашение,
сообщение чата, заявка на обслуживание, расторжение) вопрос «можно ли это
удалить/отменить» и «нужно ли уведомление другой стороне» никогда явно не
решался — просто не сделали, не потому что осознанно решили, что не
нужно. Чтобы не повторять тот же класс пробела, при добавлении новой
сущности или нового события, видимого другой стороне, отвечать на два
вопроса явно — даже если ответ «нет» — и коротко фиксировать ответ рядом
с моделью (комментарий в схеме/коде) или в PR/CHANGELOG, если ответ
неочевиден:

1. **Может ли пользователь удалить/отменить/отозвать эту сущность после
   создания?** Если нет — почему это осознанное решение, а не пропуск?
   (Пример обоснованного «нет»: `Meter` не удаляется насовсем, только
   архивируется `isActive: false` — иначе теряется история показаний,
   ADR-0014.)
2. **Видно ли это событие другой стороне без её собственного действия —
   приходит ли уведомление?** Если нет — почему?

Отдельный ADR на каждый такой ответ заводить не нужно — это не реперная
точка сама по себе, если ответ соответствует уже принятым паттернам.
ADR нужен, только если ответ — новое архитектурное решение (например,
выбор между hard-delete и soft-delete там, где есть каскад, или новый
внешний канал доставки).

## Кто следует правилам

Любой участник — человек или агент, работающий над проектом (включая
Claude в последующих сессиях) — обязан применять эти правила при любом
изменении, попадающем под определение реперной точки выше. Это
закреплено в `CLAUDE.md` в корне проекта.
