# Продуктовый UX-отчёт: повседневная операционная работа

**Ограничения проверки.** Живой проход выполнен 24 августа 2026 года на мобильной раскладке через same-origin iframe 390×844 (фактическая ширина контента 386 px): проверены тексты, структура, геометрия, цвета и поведение трёх ролей. Скриншоты в среде недоступны, поэтому визуальная иерархия «на глаз», читаемость и перекрытия при реальном скролле не считаются проверенными; горизонтального переполнения в пройденных состояниях не было. Polling живьём не проверен из-за `visibilityState: hidden`: хук вызывает обновление только внутри интервала при видимой вкладке (`frontend/lib/usePolling.ts:11`, `frontend/lib/usePolling.ts:12`). Наблюдения, полученные только чтением кода или прямым API-вызовом, отмечены явно. Сравнения с Домиленд, TenantCloud, Buildium и AppFolio ниже — экспертное знание о механизмах, живьём в рамках этого прохода аналоги не проверялись.

## 1. `/dashboard` — «Сегодня»

### Текущее состояние

Экран параллельно загружает объекты, договоры, приглашения, уведомления и landlord-сводку, причём каждый сбой превращает в пустой массив или `null` (`frontend/app/dashboard/page.tsx:58`, `frontend/app/dashboard/page.tsx:62`). Две верхние суммы всегда берутся из `/reports/summary` и показываются без ветвления по роли (`frontend/app/dashboard/page.tsx:73`, `frontend/app/dashboard/page.tsx:199`). Действия по оплате строятся только по первому найденному финальному неоплаченному счёту активного договора (`frontend/app/dashboard/page.tsx:151`). В живом проходе у арендатора при просроченном счёте 48 070 ₽ экран показал `Получено всего 0 ₽`, `Ожидается к оплате 0 ₽` и не показал оплату в «Сегодня»; у собственника была карточка `Подтвердите оплату`, но не было карточки просрочки.

### Находки

- **Баг — главная не понимает роль пользователя.** Арендатор с просроченным счётом видит нулевые показатели портфеля собственника, потому что backend без проверки роли строит landlord-сводку по `user.id` (`backend/src/reports/reports.controller.ts:14`, `backend/src/reports/reports.controller.ts:15`). В ситуации «открыл главную, чтобы понять, сколько заплатить сегодня» пользователь получает ложное спокойствие вместо суммы и действия. Механизм раздельных tenant-balance и owner-portfolio summary используется в TenantCloud; сравнение экспертное, живьём не верифицировалось.
- **Баг — одно более новое состояние скрывает старую просрочку.** Счета приходят от нового периода к старому (`backend/src/billing/billing.service.ts:104`), а `find()` останавливается на первом неоплаченном (`frontend/app/dashboard/page.tsx:151`). Если новый счёт уже имеет статус `оплата заявлена`, арендатор не получает действие по более старому `pending`-счёту, а собственник видит проверку чека, но не взыскание просрочки; обеим сторонам приходится самим искать проблему почти в трёх экранах списка счетов.
- **Баг, проверено только по коду — частичный сбой маскируется под отсутствие дел.** Ошибки объектов/договоров превращаются в `[]`, а ошибка отчёта — в `null` (`frontend/app/dashboard/page.tsx:58`, `frontend/app/dashboard/page.tsx:62`); ниже тем же способом `listBills()` превращается в `[]` (`frontend/app/dashboard/page.tsx:125`). Собственник при временном 500 может прочитать `Всё под контролем`, хотя система просто не смогла получить обязательства.

### Предложения

1. Разделить финансовую сводку главной по контексту: арендатору показывать его `к оплате / оплата заявлена / просрочено`, собственнику — доход и портфель; для пользователя в обеих ролях показывать два явно подписанных блока. **Тип:** bug. **Усилие:** M. **ADR:** нет, это развитие принятого хаба ADR-0020 и денежного флоу ADR-0012. **Конфликт с принятым:** нет; не добавляет проведение платежа и сохраняет ADR-0029.
2. Строить действия по всем неоплаченным счетам и сортировать их по срочности: `просрочен` → `оплата заявлена` → `ожидается`; при нескольких однотипных событиях показывать количество и общую сумму. **Тип:** bug. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет; статусы ADR-0012 не меняются.
3. Заменить локальные `.catch(() => [])` на результат с признаком частичной ошибки: оставить успешно загруженные блоки, а над «Сегодня» показать спокойный alert `Не удалось обновить счета` с кнопкой `Повторить`. **Тип:** bug. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет; реализация должна использовать существующий alert/`Button` и сначала обновить состояние в Stitch по ADR-0023.

## 2. `/properties` и `/properties/[id]`

### Текущее состояние

Список объединяет собственные объекты и договоры, где пользователь — арендатор, но tenant-строка выводит только сумму и ISO-диапазон, хотя адрес уже есть в `LeaseView` (`frontend/app/properties/page.tsx:314`, `frontend/app/properties/page.tsx:315`). Карточка объекта owner-only: backend ищет запись по паре `id + ownerId` и возвращает одинаковый 404 для чужого объекта (`backend/src/properties/properties.service.ts:81`, `backend/src/properties/properties.service.ts:84`). В подзаголовок карточки напрямую попадают `propertyType` и IANA-таймзона (`frontend/app/properties/[id]/page.tsx:370`), а при создании без таймзоны backend оставляет дефолт БД `Europe/Moscow` (`backend/src/properties/properties.service.ts:61`). История завершённых аренд возвращает только email арендатора и счётчики оплат (`backend/src/properties/properties.service.ts:109`).

### Находки

- **Баг — арендатор не может различить договоры по объекту.** В живом проходе две строки выглядели как `Договор · 28 000 ₽/мес` и даты без адреса; код действительно не использует `l.property.address` (`frontend/app/properties/page.tsx:314`). Арендатор с двумя договорами вынужден открывать каждый, чтобы понять, к какой квартире относится строка.
- **Баг — расчётная таймзона неверна и неуправляема из интерфейса.** Объект в Иркутске живьём показывал `Europe/Moscow`; backend допускает произвольную строку `timezone` (`backend/src/properties/dto/create-property.dto.ts:76`), но frontend-контракты создания и обновления заканчиваются без этого поля (`frontend/lib/properties.ts:29`, `frontend/lib/properties.ts:42`). Для собственника это не техническая подпись: от часового пояса должны зависеть границы расчётного периода, а сейчас он не может исправить значение.
- **UX-полировка — тип объекта и тариф говорят языком данных, не человека.** Сид с `propertyType: apartment` показал сырое `apartment`, потому что DTO принимает любую непустую строку (`backend/src/properties/dto/create-property.dto.ts:62`), а карточка выводит её без маппинга (`frontend/app/properties/[id]/page.tsx:370`). Тариф в списке показан как `4,5 ₽` без `кВт·ч` или `м³`, хотя единицы уже заданы в каталоге (`frontend/app/properties/[id]/page.tsx:474`, `frontend/lib/catalog.ts:68`); собственник при проверке настроек не понимает размерность цены.
- **UX-полировка — история арендаторов дублирует долг и скрывает имя.** В живом проходе строка сначала сообщала `1 не оплачено`, затем повторяла то же отдельным бейджем; код строит оба текста из одного `unpaid` (`frontend/app/properties/[id]/page.tsx:435`, `frontend/app/properties/[id]/page.tsx:440`). Заголовком служит email (`frontend/app/properties/[id]/page.tsx:424`), поэтому собственник после смены жильца хуже опознаёт человека, хотя договор в других местах уже отдаёт `fullName`.

### Предложения

1. В tenant-строке сделать адрес главным заголовком, а сумму, даты и статус — подписью/значением; переход оставить на текущую карточку договора. **Тип:** bug. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет; переиспользуется `LeaseView` из ADR-0020.
2. Ввести закрытый каталог типов объекта на API и единый русский маппинг на UI; существующие латинские значения мигрировать/нормализовать. **Тип:** bug. **Усилие:** M. **ADR:** да, короткий ADR на нормализацию поля `Property.propertyType` и миграцию данных. **Конфликт с принятым:** нет; ADR-0026 про структуру адреса не меняется.
3. Добавить выбор IANA-таймзоны при создании/редактировании с человеческой подписью `Иркутск (UTC+8)` и валидировать её на backend; до полного таймзонного расчёта явно пометить, что значение влияет на периоды. **Тип:** bug. **Усилие:** M. **ADR:** да, расширить решение ADR-0013 отдельным ADR о календарных границах по `Property.timezone`. **Конфликт с принятым:** нет.
4. В строке счётчика выводить `₽/кВт·ч`, `₽/м³` или `₽/Гкал`; в истории аренды запросить `tenant.fullName`, сделать его заголовком, email — подписью, а итог оплаты показать один раз. **Тип:** UX-polish. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет; используются существующие токены и `Row`/`StatusPill` ADR-0023.

## 3. `/leases/[id]/meters` и история показаний

### Текущее состояние

Хаб доступен обеим сторонам договора, берёт границы самого раннего открытого черновика и затем вычисляет статус каждого счётчика (`backend/src/meters/meters.service.ts:97`, `backend/src/meters/meters.service.ts:124`). Счётчики возвращаются по `createdAt desc`, поэтому недавно отключённый прибор может оказаться первым (`backend/src/meters/meters.service.ts:111`). При подаче показания backend рассчитывает расход, стоимость и мягкое предупреждение более чем о десятикратном скачке (`backend/src/meters/meter-readings.service.ts:104`, `backend/src/meters/meter-readings.service.ts:168`), но основной экран не сохраняет результат вызова (`frontend/app/leases/[id]/meters/page.tsx:80`). История на frontend запрашивается только по `meterId`, хотя URL содержит ещё и `leaseId` (`frontend/app/leases/[id]/meters/[meterId]/history/page.tsx:18`, `frontend/app/leases/[id]/meters/[meterId]/history/page.tsx:27`).

### Находки

- **Баг — защита от аномального расхода не достигает пользователя.** Сид вернул API-предупреждение `Расход более чем в 10 раз превышает средний — проверьте показания` для скачка 1250 → 2600, но после отправки живой экран показал только `Текущее: 2600 кВт·ч`. UI сразу закрывает диалог и перезагружает список (`frontend/app/leases/[id]/meters/page.tsx:80`), поэтому арендатор у счётчика не получает шанса заметить опечатку до начисления 6 075 ₽.
- **Баг — история счётчика исчезает после расторжения.** Проверено прямым API-вызовом: собственник создал счётчик на объекте с расторгнутым договором и получил 404 `Счётчик не найден`. Сервис ищет только активный договор объекта и при его отсутствии запрещает доступ даже владельцу (`backend/src/meters/meter-readings.service.ts:156`). Пользователь, разбирающий финальный расчёт или спор после выезда, теряет доступ к сохранённым доказательствам.
- **Баг — договорный сегмент URL не участвует в авторизации истории.** В живом проходе URL расторгнутого договора C с `meterId` другого объекта показал историю активного договора A; frontend передаёт в API только `meterId` (`frontend/lib/catalog.ts:152`), а backend самостоятельно выбирает активный договор объекта (`backend/src/meters/meter-readings.service.ts:156`). Сторона, открывшая старую закладку или вручную полученную ссылку, может видеть правдивые показания в ложном договорном контексте.
- **UX-полировка — действие заслонено архивом, а история не объясняет скачки.** На 390×844 первым был `Газ (снят)`, потому что список не приоритизирует `isActive`; четыре строки истории показывали только дату и сырое значение (`frontend/app/leases/[id]/meters/[meterId]/history/page.tsx:81`, `frontend/app/leases/[id]/meters/[meterId]/history/page.tsx:87`) рядом с `Копировать`. Арендатору при ежемесячном вводе приходится пройти мимо недоступного действия, а собственнику при сверке вручную вычислять дельту 1250 → 2600.
- **UX-полировка — пустое состояние обращается к собственнику как к арендатору.** На расторгнутом договоре собственник увидел `Счётчиков пока нет` и `Собственник ещё не добавил счётчики по этому объекту.`; текст задан без ветвления по роли (`frontend/app/leases/[id]/meters/page.tsx:148`, `frontend/app/leases/[id]/meters/page.tsx:149`). Пользователю сообщают в третьем лице, что он сам не выполнил действие, но не дают пути к его выполнению.

### Предложения

1. Сделать аномалию двухшаговой: backend на подозрительном значении возвращает `requiresConfirmation` без фиксации строки счёта, UI показывает расход, сумму и предупреждение, а отдельное `Всё верно, сохранить` подтверждает ввод. В тот же диалог добавить уже реализованный на карточке объекта предпросмотр расхода и цены (`frontend/app/properties/[id]/page.tsx:932`). **Тип:** bug. **Усилие:** M. **ADR:** нет, API-контракт меняется без новой сущности. **Конфликт с принятым:** нет; подтверждение человеком усиливает ADR-0008.
2. Заменить историю на договорно-скоупированный endpoint `GET /leases/:leaseId/meters/:meterId/readings`: валидировать соответствие договора, объекта и счётчика; собственнику разрешить историю по всем его договорам, арендатору — только по своему договору, включая завершённый. **Тип:** bug. **Усилие:** M. **ADR:** да — пересматривает active-only границу ADR-0015; нужен явный ответ владельца и правило приватности между бывшими арендаторами. **Конфликт с принятым:** явный пересмотр ADR-0015, без решения владельца не реализовывать.
3. Сортировать `active + due/overdue` перед `submitted`, а отключённые — последними; в истории вычислять и показывать дельту к предыдущей записи и выделять аномальный скачок текстом+иконкой+цветом. **Тип:** UX-polish. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет; соответствует `StatusPill` и правилу статуса ADR-0023.
4. Ветвить пустое состояние по роли: арендатору оставить объяснение, а собственнику показать `Добавьте счётчики на карточке объекта` со ссылкой на объект. **Тип:** UX-polish. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет; меняются только ролевой текст и навигация к существующему действию.

## 4. `/leases/[id]/bills`

### Текущее состояние

Обе стороны могут получить все счета договора; для активного договора сервис лениво создаёт текущий черновик и сортирует периоды от нового к старому (`backend/src/billing/billing.service.ts:96`). UI различает landlord/tenant по `tenantId`, но кнопку финализации черновика показывает без проверки роли (`frontend/app/leases/[id]/bills/page.tsx:331`). При расторжении backend пропорционально меняет аренду и финализирует последний счёт без следующего периода (`backend/src/billing/billing.service.ts:201`). На живом мобильном экране было 2,82 высоты вьюпорта: реквизиты → черновик → оплаченный → `оплата заявлена` → просроченный счёт в самом низу.

### Находки

- **Баг прав доступа — арендатор формирует финансовый документ собственника.** Живой API-вызов `POST /bills/:id/finalize` под tenant-токеном вернул 200 и `stage: final`; это соответствует сервису, где финализация использует гард `getBillAsParty`, а не `getBillAsLandlord` (`backend/src/billing/billing.service.ts:136`, `backend/src/billing/billing.service.ts:902`). Арендатор может преждевременно закрыть черновик на 53 890 ₽ и создать следующий период, хотя ADR-0012 определяет формирование счёта как действие собственника.
- **Баг — после расторжения исчезает путь к обязательному последнему счёту.** В карточке договора вкладки рендерятся только для `active` (`frontend/app/leases/[id]/page.tsx:363`), но backend продолжает отдавать счета стороне договора без требования активного статуса (`backend/src/billing/billing.service.ts:96`). Прямой `/leases/C/bills` живьём работал: выехавший арендатор должен оплатить финальный счёт, однако из интерфейса к нему не попасть.
- **UX-полировка с денежным риском — приоритет и подписи противоречат задаче.** Единственный просроченный счёт оказался последним почти на трёх мобильных экранах из-за сортировки по периоду, а оплаченный счёт всё равно имел подпись `к оплате`, потому что лейбл зависит от ненулевой суммы, не от статуса (`frontend/app/leases/[id]/bills/page.tsx:285`, `frontend/app/leases/[id]/bills/page.tsx:290`). У просрочки были сумма и пеня, но не было `45 дней` и пояснения о ежедневном росте, хотя диалог оплаты прямо говорит, что пеня идёт до подтверждения собственника (`frontend/app/leases/[id]/bills/page.tsx:423`). Просроченное состояние в тесте получено SQL-backdating’ом, а не естественным ожиданием 45 дней.
- **Баг состояния ошибки.** При подмене `/bills` на 500 экран одновременно показал `Внутренняя ошибка` и `Загрузка…` без выхода: alert рендерится отдельно (`frontend/app/leases/[id]/bills/page.tsx:171`), а отсутствие `lease` безусловно трактуется как загрузка (`frontend/app/leases/[id]/bills/page.tsx:236`). Арендатор, пытающийся приложить чек, не может повторить запрос и не понимает, загрузка ещё идёт или уже завершилась ошибкой.

### Предложения

1. На backend заменить `getBillAsParty` на `getBillAsLandlord` для ручной финализации; на frontend показывать `Сформировать счёт` только при `isLandlord`. Добавить авторизационный тест tenant → 404/403. **Тип:** security. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет; исправление приводит код к ADR-0012.
2. ## 5. `/leases/[id]/requests`

### Текущее состояние

Создание заявки разрешено только арендатору, а статус меняет только собственник (`backend/src/maintenance/maintenance.service.ts:55`, `backend/src/maintenance/maintenance.service.ts:102`). Согласование обеими сторонами создаёт разовую услугу, а перевод в `resolved` выставляет её в текущий счёт (`backend/src/maintenance/maintenance.service.ts:186`, `backend/src/maintenance/maintenance.service.ts:105`). Список отдаётся по `createdAt desc` (`backend/src/maintenance/maintenance.service.ts:92`), а карточка показывает категорию, описание, статус и урегулирование (`frontend/app/leases/[id]/requests/page.tsx:99`). В живом проходе цепочка `услуга создана — попадёт в счёт после закрытия` → `выставлено в счёт` была понятной и содержательной.

### Находки

- **Недостающая функция — приложенное доказательство нельзя посмотреть.** Форма принимает JPEG/PNG/PDF (`frontend/app/leases/[id]/requests/page.tsx:338`), backend сохраняет файл и ключ (`backend/src/maintenance/maintenance.service.ts:59`), но последний endpoint контроллера — подтверждение урегулирования (`backend/src/maintenance/maintenance.controller.ts:68`), после него класс заканчивается без выдачи файла (`backend/src/maintenance/maintenance.controller.ts:75`). Арендодатель, решающий, вызывать ли мастера по течи, не видит фото, ради которого арендатор прошёл загрузку.
- **Недостающая функция — нет времени и истории движения заявки.** Frontend-тип заканчивается полем `service`, не включая `createdAt`/`updatedAt` (`frontend/lib/maintenance.ts:16`), поэтому живой экран не показал ни одной даты. Собственник с открытой заявкой не отличает вчерашнюю проблему от трёхмесячной, а арендатор не может восстановить, когда заявка перешла в работу. В Buildium/AppFolio work order обычно содержит вложения и датированную ленту статусов; сравнение экспертное, живьём не верифицировалось.
- **UX-полировка — ожидание второй стороны понятно только по оформлению.** Строка всегда начинается словом `подтвердили`, после чего показывает обе роли с галочкой или прочерком (`frontend/app/leases/[id]/requests/page.tsx:160`). При чтении текстом R3 выглядела как подтверждённая обеими сторонами, хотя подтвердил только собственник; пользователю нужно расшифровывать иконки вместо прямого `Ждём подтверждения арендатора`.
- **UX-полировка — закрытое вытесняет срочное.** Новая решённая R5 была первой, а открытые заявки, сумма на подтверждение и работа в процессе ушли ниже, потому что backend сортирует только по дате (`backend/src/maintenance/maintenance.service.ts:92`). Собственник на телефоне тратит скролл на завершённое прежде, чем увидит действия.

### Предложения

1. Добавить авторизованный endpoint скачивания вложения по образцу чата и кнопку/миниатюру `Открыть фото` в заявке; PDF открывать как файл, изображения — в `Dialog`. **Тип:** missing-feature. **Усилие:** M. **ADR:** нет, используется существующий `StorageProvider` ADR-0007. **Конфликт с принятым:** нет.
2. Сразу вывести `Создана <дата>` и `Обновлена <дата>`; для полноценной датированной ленты завести append-only `MaintenanceEvent` со сменой статуса и денежными подтверждениями. **Тип:** missing-feature. **Усилие:** M. **ADR:** да, новая сущность истории и правила ретеншена требуют отдельного ADR. **Конфликт с принятым:** нет; денежный переход ADR-0025 остаётся источником истины.
3. Заменить блок подтверждений на явную фразу по состоянию: `Подтвердил собственник · ждём арендатора`, `Подтвердил арендатор · ждём собственника`, `Согласовано обеими сторонами`; иконки оставить как дополнительный канал. **Тип:** UX-polish. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет; выполняет правило «статус не одним цветом» ADR-0023.
4. Группировать карточки `Нужно действие` (`open`, `in_progress`, неподтверждённая сумма) и `Завершено`, внутри — новые сверху. **Тип:** UX-polish. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет; статусы и биллинг ADR-0025 не меняются.

## 6. `/leases/[id]/chat`

### Текущее состояние

Backend загружает всю переписку договора одним запросом от старых сообщений к новым (`backend/src/messages/messages.service.ts:81`), frontend опрашивает её каждые 15 секунд и после каждого обновления прокручивает к концу (`frontend/app/leases/[id]/chat/page.tsx:46`, `frontend/app/leases/[id]/chat/page.tsx:48`). Композер закреплён `sticky bottom-0` (`frontend/app/leases/[id]/chat/page.tsx:148`) и в мобильной проверке 390×844 оставался в поле зрения и при верхней позиции прокрутки, и в середине переписки. У сообщения выводится только время, а метка официальности повторяется в бейдже и подписи (`frontend/app/leases/[id]/chat/page.tsx:112`, `frontend/app/leases/[id]/chat/page.tsx:138`).

### Находки

- **Недостающая функция — переписка не имеет календарного контекста.** Все семь сообщений показывали только `19:51`; код берёт лишь часы и минуты из ISO (`frontend/app/leases/[id]/chat/page.tsx:136`). При споре через месяц обе стороны не могут определить день обещания или отделить сегодняшний диалог от вчерашнего.
- **Недостающая функция, проверено только по коду — история не пагинируется.** `findMany` заканчивается условиями `where` и `orderBy`, без `take/cursor` (`backend/src/messages/messages.service.ts:79`, `backend/src/messages/messages.service.ts:81`), а frontend заменяет весь массив на каждый polling (`frontend/app/leases/[id]/chat/page.tsx:32`). В договоре с годом ежедневной переписки каждое открытие и фоновое обновление снова тянут всю историю.
- **UX-полировка — малые цели и двойная метка.** Живой замер кнопки `Отправить` дал 28×40 px; компонент `size="icon"` задаёт 40×40 и не запрещает flex-сжатие (`frontend/components/ui/button.tsx:35`). Арендатору, который отвечает одной рукой с телефона, сложнее точно нажать основное действие; официальное сообщение вдобавок дважды говорит `Официальное`, занимая место и добавляя визуальный шум.

### Предложения

1. Добавить разделители `Сегодня`, `Вчера`, `24 августа` и полную дату в доступной подписи; оставить бейдж `Официальное` только один раз, а в нижней строке — время и `изменено`. **Тип:** UX-polish. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет; юридическая метка сохраняется.
2. Ввести cursor-pagination (`последние 50`, `Показать более ранние`) и при polling запрашивать только сообщения после последнего id/времени, не сбрасывая позицию пользователя. **Тип:** missing-feature. **Усилие:** M. **ADR:** нет; это развитие HTTP-polling. **Конфликт с принятым:** нет, ADR-0009 и ADR-0016 сохраняются, WebSocket не предлагается.
3. Для иконок отправки/вложения задать `min-width/min-height: 44px` и `shrink-0`; затем распространить тот же минимум на `Button sm` и вкладки договора. **Тип:** UX-polish. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет; изменение остаётся внутри дизайн-системы ADR-0023 и требует синхронизации со Stitch.

## 7. `/notifications`

### Текущее состояние

Notification хранит только `type`, `title` и `body` входного события, после чего запись сортируется по дате создания (`backend/src/notifications/notifications.service.ts:15`, `backend/src/notifications/notifications.service.ts:17`, `backend/src/notifications/notifications.service.ts:64`). На странице непрочитанная строка кликабельна только для `markRead`; после прочтения она превращается в неинтерактивный `div` (`frontend/app/notifications/page.tsx:109`, `frontend/app/notifications/page.tsx:116`). Дата формируется срезом ISO до `MM-DD HH:mm` (`frontend/app/notifications/page.tsx:101`). В живом проходе три события поместились на экран, но два `Договор заключён` были неразличимы, а `В счёт добавлена услуга` не вело к счёту.

### Находки

- **Недостающая функция — уведомление сообщает событие, но не даёт продолжить действие.** Арендатор, прочитавший `В счёт добавлена услуга`, может только погасить непрочитанность, затем вручную искать договор и счёт. Контракт заканчивается полями `type/title/body` и не хранит `leaseId/billId/href` (`backend/src/notifications/notifications.service.ts:15`, `backend/src/notifications/notifications.service.ts:18`), хотя для операционного уведомления главный смысл — переход к объекту события.
- **Баг контекста — одинаковые события невозможно различить и текст устаревает.** Триггер активации дважды отправляет один и тот же заголовок/тело без адреса или номера договора (`backend/src/leases/lease-signed-scans.service.ts:192`). Уведомление по уже расторгнутому договору продолжало утверждать `договор действует`; пользователю с несколькими объектами непонятно, к чему относится запись и актуальна ли она сейчас.
- **Недостающая функция — нет массового прочтения.** Контроллер имеет только `POST :id/read` (`backend/src/notifications/notifications.controller.ts:26`). Пользователь, вернувшийся после отпуска к десяткам уже просмотренных напоминаний, должен нажать каждое по отдельности, причём после первого нажатия строка теряет интерактивность.

### Предложения

1. Расширить уведомление структурированной целью (`targetType`, `targetId`, опциональный `leaseId`) и сделать всю строку deep-link’ом; отметку прочтения выполнять вместе с переходом, но сохранять ссылку после прочтения. **Тип:** missing-feature. **Усилие:** M. **ADR:** да, нужен ADR на схему адресуемых уведомлений, допустимые цели и поведение после удаления/архивации сущности. **Конфликт с принятым:** нет.
2. Добавлять в снимок события адрес/период, формулировать исторические события в прошедшем времени (`Договор вступил в силу`), дату выводить локально как `24 августа, 19:51` с годом для старых записей. **Тип:** UX-polish. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет; тон остаётся спокойным и предметным по ADR-0023.
3. Добавить `POST /notifications/read-all` и вторичное действие `Прочитать всё`, доступное только при наличии непрочитанных; обновлять список оптимистично с возвратом при ошибке. **Тип:** missing-feature. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет.

## 8. `/reports`

### Текущее состояние

Endpoint называется landlord summary, но защищён только JWT и передаёт в сервис id любого авторизованного пользователя (`backend/src/reports/reports.controller.ts:8`, `backend/src/reports/reports.controller.ts:14`, `backend/src/reports/reports.controller.ts:15`), а глобальная навигация показывает `Отчёты` всем (`frontend/components/AppShell.tsx:53`). Сервис считает задолженностью любой финальный счёт, чей статус не `paid`, включая `payment_claimed` (`backend/src/reports/reports.service.ts:163`, `backend/src/reports/reports.service.ts:165`). Статус объекта определяется только наличием активного или draft/sent-договора, тогда как деньги накапливаются по всем договорам объекта (`backend/src/reports/reports.service.ts:255`, `backend/src/reports/reports.service.ts:267`). Таблица просрочек получает `billId` и `leaseId` (`backend/src/reports/reports.service.ts:21`, `backend/src/reports/reports.service.ts:22`), но рендерит обычные ячейки без ссылок (`frontend/app/reports/page.tsx:286`).

### Находки

- **Баг роли — арендатору показан пустой отчёт собственника.** T1 живьём увидел `Объектов 0`, `К оплате 0 ₽`, `Просрочек нет` и призыв добавить объект, хотя его собственный счёт просрочен на 48 070 ₽. Пользователь нажимает постоянный пункт `Отчёты`, ожидая историю своих платежей, а интерфейс предлагает ему стать арендодателем.
- **Баг семантики денег — `Долг` смешивает разные действия.** По P1 сумма 94 835 ₽ включала и реальную просрочку 48 070 ₽, и 46 765 ₽ со статусом `оплата заявлена`, где чек уже у собственника. Владелец портфеля может повторно требовать деньги с арендатора вместо своего действия `проверить поступление`; это противоречит смысловому разделению ADR-0012, хотя арифметика кода формально последовательна.
- **Баг контекста — долг переживает договор, а должник исчезает.** Расторгнутый P4 показывался как `Свободен` с `Долг 28 000 ₽`, но tenant email выводится только для `activeLease` (`backend/src/reports/reports.service.ts:281`). Собственник видит проблему, но не видит, кто должен и по какому завершённому договору.
- **UX-полировка — отчёт не продолжает операционную работу.** Строка просрочки содержит точные `billId/leaseId`, но ни адрес, ни сумма, ни арендатор не кликабельны (`frontend/app/reports/page.tsx:285`). Владелец с несколькими объектами должен запомнить сумму, перейти в аренду, найти договор, затем счёт или чат; в Buildium/AppFolio delinquency row обычно ведёт в ledger/коммуникацию, сравнение экспертное и живьём не проверялось.
- **UX-полировка — корзины сроков выглядят взаимоисключающими, хотя они накопительные.** Backend увеличивает один договор одновременно в `within60` и `within90` (`backend/src/reports/reports.service.ts:211`, `backend/src/reports/reports.service.ts:212`), а подпись `30 дн. — 0, 60 — 1, 90 — 1` этого не объясняет (`frontend/app/reports/page.tsx:313`). Собственник может прочитать это как два договора, а не один.

### Предложения

1. Сделать `/reports` landlord-only по наличию собственных объектов/договоров и скрывать пункт у пользователя без landlord-контекста; tenant-финансы показывать на главной и в счетах, а не нулевым портфелем. **Тип:** bug. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет; ADR-0028 прямо определяет экран как портфель собственника.
2. Разложить финансовый риск на `Просрочено`, `Ожидается к оплате` и `Оплата заявлена — проверить`; общий exposure можно оставить отдельной нейтральной суммой, но не называть весь его объём долгом. **Тип:** bug. **Усилие:** M. **ADR:** нет, используются уже принятые статусы. **Конфликт с принятым:** нет; соответствует ADR-0012 и не останавливает пеню до подтверждения.
3. Для объекта без активного договора, но с задолженностью вернуть контекст каждой суммы: завершённый договор, бывший арендатор и статус счёта; не подставлять бывшего арендатора в текущий статус `Свободен`, а показывать отдельной строкой `Долг по завершённому договору`. **Тип:** bug. **Усилие:** M. **ADR:** нет. **Конфликт с принятым:** нет; сохраняет единый денежный проход ADR-0028.
4. Сделать строку просрочки ссылкой на `/leases/:leaseId/bills` с фокусом/якорем на `billId` и добавить действие `Написать` в чат договора; для завершённого договора переход должен работать через архивную навигацию из раздела 4. **Тип:** UX-polish. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет; сервис остаётся коммуникационно-биллинговым слоем и не нарушает ADR-0029.
5. Либо сделать корзины взаимоисключающими (`0–30`, `31–60`, `61–90`), либо явно подписать накопительные пороги `≤30 / ≤60 / ≤90`. **Тип:** UX-polish. **Усилие:** S. **ADR:** нет. **Конфликт с принятым:** нет.

## Итоговая сводка: пять самых ценных исправлений

1. **Запретить арендатору финализировать черновик счёта.** Это не косметика, а нарушение прав на финансовое действие: живой API подтвердил поведение, а сервис действительно допускает любую сторону договора (`backend/src/billing/billing.service.ts:136`).
2. **Довести предупреждение об аномальном показании до подтверждения до записи.** Уже работающая серверная защита (`backend/src/meters/meter-readings.service.ts:168`) сейчас молча выбрасывается на основном мобильном экране (`frontend/app/leases/[id]/meters/page.tsx:80`).
