## Проект

SoftRent — веб-сервис для коммуникации между арендодателем и
арендатором помещения в РФ. NestJS-бэкенд + Next.js-фронтенд, репозиторий
`C:\Users\Denn\claude_projects\soft_rent\open_rental`. Целевой рынок —
физлица-собственники 1–20 объектов, не управляющие компании. Сервис
**не маркетплейс** и **не проводит арендную плату** — это
коммуникационно-биллинговый слой поверх уже существующих отношений
аренды (`docs/IDEA.md`, «Рынок и позиционирование»; `docs/adr/0029-*`).

## Методология — как именно проводить ревью

На каждый экран/блок из твоего списка (ниже) применяй одну и ту же
дисциплину:

1. **Прочитай реальный код** — backend-контроллер/сервис и
   frontend-страницу/компонент, которые за этим экраном стоят. Каждое
   утверждение о текущем поведении — с `file:line`, как в code review,
   не по памяти и не по догадке.
2. **Пройди экран живьём в браузере**, не только по коду — код не
   покажет, удобно ли реально пользоваться формой, видно ли состояние
   ошибки, достаточно ли крупная кнопка на телефоне. См. раздел
   «Как поднять стенд и пройти экраны живьём» ниже — это обязательный
   шаг, не опциональный. Если инструмент браузера в твоей среде
   недоступен (как это было в сессии редизайна, см.
   `docs/DEV_STATE.md`, R1) — прямо укажи в отчёте, какие пункты
   проверены только по коду, не выдавай это молча за живую проверку.
3. Оцени экран по нескольким осям, не только «работает/не работает»:
   - **Функциональная полнота** — сравни с тем, как аналогичный блок
     решён в сравнимых продуктах (Домиленд, TenantCloud/Buildium/
     AppFolio по духу) — не копируй бездумно, а спрашивай «чего тут не
     хватает конкретно этому пользователю в этой ситуации».
   - **Скорость повторяющегося действия** — экраны в твоей зоне
     используются не один раз (как договор), а регулярно, часто с
     телефона и часто в неидеальных условиях (в подвале у счётчика,
     между делами). Считай реальное число шагов/тапов; ищи, где можно
     срезать путь без потери ясности.
   - **Своевременность и заметность** — большая часть найденного
     2026-08-24 ревью (Фаза 13/14) — это то, что события происходят
     «тихо», без сигнала другой стороне. В твоей зоне это тоже
     актуально: посмотри, не только приходит ли уведомление
     (это уже разобрано в Фазе 13), а видно ли вообще на **самом
     экране** нужную информацию без лишних кликов — например, сводки,
     счётчики непрочитанного, статусные бейджи.
   - **Обратная связь и состояния** — загрузка/пустое/ошибка/успех.
     Важно: при редизайне (ADR-0023, R1) содержательные состояния
     (просрочено, ждём вторую сторону) рисовались только там, где
     реально меняется состав экрана, общие состояния (загрузка/ошибка)
     — один раз как образец и дальше по аналогии. Значит часть экранов
     могла унаследовать обобщённый шаблон там, где ситуация на самом
     деле заслуживает специфичного текста/поведения — целенаправленно
     ищи такие места, особенно у счетов (разные статусы оплаты) и
     заявок на обслуживание.
   - **Мобильность** — показания счётчиков, чат, заявки — то, чем
     тенант реально пользуется с телефона намного чаще, чем с
     десктопа. Проверяй мобильную раскладку в первую очередь, не
     десктопную.

4. Не ограничивайся тем, что явно нащупывается — думай и о том, что
   *отсутствует целиком*, а не только о полировке того, что есть.

### Разобранный пример (задан владельцем продукта, ориентир по глубине) — блок Auth/Password

Не в твоей зоне (это у Агента A), но ориентир по уровню детализации,
который ожидается от **каждого** твоего пункта. Текущее состояние
(уже подтверждено ревью 2026-08-24): регистрация собирает
email/пароль/имя; `PATCH /auth/me` меняет только реквизиты для
перевода, не имя; email-верификации нет; восстановления пароля нет.
Владелец продукта запросил: верификацию email кодом на почту,
полноценное восстановление пароля, требования к сложности пароля,
визуальный индикатор надёжности пароля (красный/жёлтый/зелёный),
обновляющийся по мере набора текста. Именно такого уровня
конкретности — «что конкретно сделать», не «улучшить UX» — жду от
находок по твоим экранам.

### Второй пример (в твоей собственной зоне — это стартовая точка, не потолок)

`leases/[id]/meters` — подача показания счётчика. Текущее: фото
обязательно, OCR — заглушка (`MockMeterOcrProvider` всегда возвращает
`null`), значение подтверждает пользователь, мягкое предупреждение при
аномальном расходе (`meter-readings.service.ts`), будущая дата
запрещена.

Идеи такого же уровня конкретности: client-side blur-check (дисперсия
Лапласиана) перед загрузкой фото — просить переснять сразу, без похода
на сервер (эта идея уже отдельно всплывала в обсуждении OCR,
`docs/DEV_STATE.md`, чекпойнт про OCR — не изобретай заново, сошлись на
неё, если найдёшь то же самое); живой пересчёт «при таком значении
расход выйдет X ₽» прямо во время ввода, до отправки; направляющая
рамка на экране камеры, подсказывающая, как кадрировать табло счётчика.
Это только стартовая точка для этого конкретного экрана — иди дальше,
это твоя зона, разбери её так же, как разобран auth-пример выше.

## Как поднять стенд и пройти экраны живьём

Инфраструктура (если ещё не поднята):

```bash
cd backend && docker compose up -d   # Postgres 16 + Redis 7
cd backend && npm run start:dev      # :3000
cd frontend && npm run dev -- -p 3001  # :3001
```

Заведи throwaway-аккаунты **напрямую через API**, не через форму — так
надёжнее и быстрее получить реалистичные данные для просмотра
непустых состояний (пустой договор ничего не покажет про UX истории/
статусов):

```
POST http://localhost:3000/api/auth/register
{ "email": "ux-review-b-landlord-<timestamp>@test.local", "password": "Test12345!", "fullName": "Тест Тестов" }
```

Заведи landlord и tenant с общим префиксом `ux-review-b-<timestamp>` в
email. Для твоей зоны особенно важно получить **разнообразные, не
пустые состояния**: минимум 2-3 объекта у одного собственника (для
портфельного вида в `/reports`), хотя бы один счёт в статусе
«просрочен» и один «оплата заявлена» (для `bills`), хотя бы одну заявку
на обслуживание на разных статусах, несколько сообщений в чате с обеих
сторон, несколько показаний счётчика подряд (для истории). Пустой
экран почти ничего не скажет о качестве UX — не экономь на подготовке
данных.

В браузере логинься не через форму, а раскладывая токены из ответа
`/auth/login` (или `/auth/register`) в `localStorage`:
`softrent.accessToken` / `softrent.refreshToken`, затем переходи сразу
на нужный экран.

**Обязательно убрать за собой после ревью:**

```sql
DELETE FROM properties WHERE "ownerId" IN
  (SELECT id FROM users WHERE email LIKE 'ux-review-b-%');
DELETE FROM users WHERE email LIKE 'ux-review-b-%';
```

Плюс удалить залитые файлы, если что-то грузилось в
`backend/uploads/leases/<leaseId>`.

## Формат отчёта — куда и как писать

Итоговый файл: `docs/ux-review/2026-08-24-report-agent-b.md` (создать
рядом с этим брифом). Один markdown-документ, по разделу на каждый
экран/блок из списка выше, в этом порядке внутри раздела:

1. **Текущее состояние** — 2-5 предложений, с `file:line` на ключевые
   утверждения.
2. **Находки** — список. На каждую: что не так/чего не хватает,
   конкретный сценарий, где это реально мешает пользователю,
   насколько это баг vs недостающая функция vs полировка UX.
3. **Предложения** — конкретные, реализуемые пункты (не «сделать
   лучше», а что именно сделать). На каждый: тип
   (bug/missing-feature/UX-polish/security), грубая оценка усилий
   (S/M/L), нужен ли ADR (новая сущность, изменение схемы, внешний
   сервис, пересмотр закрытого решения — если да, явно укажи какого
   именно) и есть ли конфликт с уже принятым (ссылка на конкретный
   ADR/раздел IDEA.md, если есть).

В конце отчёта — сводный список из 3-5 находок, которые ты сам считаешь
самыми ценными по всей своей зоне (не по одному экрану), с коротким
обоснованием почему.

Не старайся дать одинаковую глубину каждому экрану — на простом экране
может быть 1 находка, на сложном (bills, reports) — 5-8; это нормально,
важна обоснованность, не единообразие.
