# Production-деплой и безопасность SoftRent

Дата: 2026-08-24  
Статус: базовая инструкция и security gate перед запуском реальных пользователей  
Связанные решения: ADR-0021 (ПДн и RU-хостинг), ADR-0030 (Postfix),
ADR-0031 (контур production-деплоя)

## 1. Назначение документа

Этот документ — исходная инструкция для последующей реализации и проверки
production-инфраструктуры SoftRent на Ubuntu-сервере, физически расположенном
в России. Он описывает:

- целевую схему развертывания;
- автоматические и ручные обновления из Git;
- Docker-контур, reverse proxy, PostgreSQL, Redis и файловое хранилище;
- Postfix и требования к доставляемости почты;
- усиленные меры защиты персональных данных;
- резервное копирование, восстановление, мониторинг и реагирование на
  инциденты;
- обязательные условия допуска реальных пользователей.

Отсутствие доступа к ИИ на сервере не является ограничением. ИИ может помогать
готовить код и конфигурацию в среде разработки, но production-сервер должен
выполнять только заранее проверенные детерминированные команды и скрипты.

Документ не заменяет юридическую проверку выполнения 152-ФЗ, подзаконных актов
и требований регуляторов. Технические меры должны быть дополнены
организационными документами и консультацией специалиста по защите ПДн.

## 2. Исходные условия проекта

Текущий стек:

- frontend: Next.js 14;
- backend: NestJS 10;
- база данных: PostgreSQL 16;
- Redis 7 зарезервирован под будущие задачи, но для текущего планировщика не
  является обязательным компонентом приложения;
- файлы: `StorageProvider` с текущей реализацией на локальной файловой системе;
- email: принято решение использовать self-hosted Postfix, ADR-0030;
- ПДн сторон договора: часть полей шифруется AES-256-GCM, ключ задается через
  `ENCRYPTION_KEY`, ADR-0021;
- сервер: Ubuntu на российской площадке.

Имеющийся `backend/docker-compose.yml` является только dev-конфигурацией. В
production его использовать нельзя: PostgreSQL и Redis опубликованы на хост,
используются тестовые учетные данные, отсутствуют frontend/backend, TLS,
healthcheck, ограничения ресурсов и production-политики безопасности.

## 3. Целевая архитектура

Для MVP принимается один Ubuntu VPS с Docker Compose. Kubernetes на текущем
масштабе не нужен.

```text
Интернет
   |
   | TCP 80/443
   v
Caddy или Nginx (TLS, security headers, rate limits)
   |-- /api/* --> backend:3000
   `-- /*     --> frontend:3000

Внутренняя Docker-сеть, без публикации портов наружу
   |-- backend
   |-- frontend
   |-- PostgreSQL
   `-- Redis (только когда реально потребуется)

Persistent data
   |-- PostgreSQL volume
   |-- uploads volume
   `-- backup staging directory

Host services
   |-- SSH
   |-- firewall
   |-- fail2ban
   |-- automatic security updates
   |-- Postfix + OpenDKIM
   `-- backup/monitoring timers
```

Наружу публикуются только `80/443` и ограниченный SSH. Порты PostgreSQL,
Redis, backend и frontend не публикуются на `0.0.0.0`. Если reverse proxy
работает на хосте, порты приложений привязываются только к `127.0.0.1`. Если
proxy находится в Compose, он общается с приложениями по внутренней сети.

На старте допустим один сервер, но это не высокая доступность. Отказ диска,
ошибка хостера или компрометация хоста остановят весь сервис. Поэтому
зашифрованная резервная копия должна регулярно уходить на вторую независимую
площадку, также соответствующую требованиям локализации данных.

## 4. Структура production-файлов в репозитории

Рекомендуемая структура:

```text
deploy/
|-- compose.prod.yml
|-- Caddyfile
|-- env.example                 # только имена переменных, без секретов
|-- scripts/
|   |-- deploy.sh
|   |-- rollback.sh
|   |-- backup.sh
|   |-- restore.sh
|   `-- smoke-test.sh
|-- systemd/
|   |-- softrent-backup.service
|   |-- softrent-backup.timer
|   `-- softrent-healthcheck.timer
`-- fail2ban/
    `-- jail.local.example

backend/Dockerfile
frontend/Dockerfile
.github/workflows/ci.yml
.github/workflows/deploy-production.yml
```

Production-секреты, базы, uploads, backup и сгенерированные ключи никогда не
коммитятся в Git.

## 5. Стратегия сборки и доставки релиза

### 5.1. Основной вариант

Сборка выполняется на GitHub-hosted runner, а не на production-сервере:

1. Изменение попадает в защищенную ветку `main` через pull request.
2. CI запускает unit-тесты backend, typecheck/build backend и typecheck/build
   frontend.
3. CI собирает immutable Docker-образы frontend и backend.
4. Образы получают тег полного Git commit SHA. Тег `latest` не является
   источником правды и не используется для rollback.
5. После прохождения CI production deployment требует отдельного GitHub
   Environment и ручного подтверждения уполномоченного пользователя.
6. GitHub-hosted runner подключается по SSH к отдельному пользователю
   `deploy` и запускает строго ограниченный deploy-скрипт с SHA релиза.
7. Сервер скачивает образы из registry либо получает их непосредственно по
   SSH, если доступ к registry нестабилен.
8. После проверки healthcheck и smoke-теста релиз помечается успешным.

На production-сервер не ставится постоянный GitHub self-hosted runner: код
workflow не должен получать неограниченное локальное выполнение рядом с БД,
uploads и production-секретами.

### 5.2. Резервный канал без зависимости сервера от GitHub Registry

Если российский сервер не может стабильно обращаться к GitHub/GHCR, CI:

1. собирает образы;
2. экспортирует их в архивы с контрольными суммами;
3. передает архивы на сервер по SSH;
4. сервер проверяет SHA-256 и выполняет `docker load`;
5. deploy-скрипт запускает конкретные загруженные теги.

Резервный ручной путь:

```bash
sudo /opt/softrent/bin/deploy.sh <full-git-commit-sha>
```

Запуск `git pull && docker compose up -d --build` прямо на production допустим
только как временный аварийный вариант. Он смешивает сборочную и production-
среду, расходует ресурсы сервера и ухудшает воспроизводимость релиза.

### 5.3. Требования к SSH-деплою

- отдельный пользователь `deploy`, без входа по паролю;
- отдельный deploy key, не личный ключ разработчика;
- ключ имеет минимально необходимый срок жизни и регулярно ротируется;
- host key сервера закреплен в `known_hosts`, `StrictHostKeyChecking` не
  отключается;
- `deploy` не читает содержимое БД, uploads и общие production-секреты;
- `sudoers` разрешает только конкретный deploy-скрипт и необходимые
  read-only проверки, а не произвольный shell от root;
- SSH-ключ не передается скрипту аргументом и не выводится в лог;
- workflow имеет минимальные `permissions`, сторонние Actions закрепляются по
  полному commit SHA;
- pull request из недоверенной ветки не имеет доступа к production secrets.

## 6. Алгоритм безопасного деплоя

`deploy.sh` должен быть идемпотентным и завершаться при любой ошибке. Порядок:

1. Получить и проверить полный SHA релиза.
2. Взять файловую блокировку, чтобы два деплоя не выполнялись одновременно.
3. Проверить свободное место, Docker daemon, доступность текущего сервиса и
   существование требуемых образов.
4. Сохранить предыдущие теги frontend/backend в release metadata.
5. Создать свежий backup PostgreSQL и зафиксировать успешность backup.
6. Скачать или загрузить новые immutable-образы и проверить digest.
7. Выполнить `prisma migrate deploy` отдельным одноразовым контейнером.
8. Обновить backend и frontend.
9. Дождаться успешных Docker healthcheck.
10. Выполнить smoke-тест: главная страница, `/api/health`, соединение с БД,
    авторизация на synthetic/служебном аккаунте без реальных ПДн.
11. При успехе записать SHA, время, инициатора и результат деплоя.
12. При ошибке вернуть предыдущие образы и снова выполнить healthcheck.

Автоматический rollback контейнеров не гарантирует rollback схемы БД. Поэтому
миграции обязаны следовать стратегии expand/contract:

- сначала добавлять совместимые nullable-поля/таблицы;
- затем выкатывать код, умеющий работать со старой и новой схемой;
- отдельно выполнять backfill;
- удалять старые поля только в следующем релизном цикле после проверки;
- destructive migration требует отдельного backup, плана восстановления и
  явного ручного подтверждения.

Для Prisma в production используется только `prisma migrate deploy`, не
`prisma migrate dev`.

## 7. Docker hardening

Каждый production-образ и сервис должен соответствовать следующим требованиям:

- multi-stage build;
- версии базовых образов закреплены, желательно также по digest;
- процесс работает не от root;
- в runtime-образ не попадают исходники, тесты, `.git`, `.env`, npm cache и
  инструменты сборки;
- `NODE_ENV=production`, устанавливаются только production dependencies;
- файловая система контейнера `read_only`, где это возможно;
- временные каталоги подключены как ограниченный `tmpfs`;
- `security_opt: no-new-privileges:true`;
- удалены Linux capabilities через `cap_drop: [ALL]`, необходимые capabilities
  добавляются точечно;
- заданы лимиты CPU, памяти и PID;
- настроены healthcheck и restart policy;
- включена ротация Docker-логов по размеру и количеству файлов;
- базы и uploads находятся в именованных volume/явных каталогах, а не в
  writable layer контейнера;
- PostgreSQL и Redis находятся только во внутренней сети;
- Docker socket не монтируется внутрь application-контейнеров;
- production-контейнер не запускается с `privileged: true` и не использует
  host network;
- образы регулярно пересобираются с security updates и сканируются на
  известные уязвимости;
- SBOM и digest релиза сохраняются вместе с release metadata.

Важно: Docker может создавать firewall-правила в обход ожидаемого поведения
UFW. Отсутствие разрешающего правила UFW не защищает ошибочно опубликованный
Docker-порт. Необходимо проверять фактические bind-адреса через `ss` и правила
цепочки `DOCKER-USER`.

## 8. Hardening Ubuntu и SSH

### 8.1. Минимальная конфигурация хоста

- поддерживаемая Ubuntu LTS с автоматическими security updates;
- минимальный набор установленных пакетов;
- отдельные учетные записи администратора и деплоя;
- вход `root` по SSH запрещен;
- SSH password authentication запрещена;
- SSH public-key authentication включена;
- по возможности SSH разрешен только через VPN или allowlist IP;
- при публичном SSH используется нестандартный порт только как снижение шума,
  не как мера безопасности;
- firewall разрешает только `80/tcp`, `443/tcp` и ограниченный SSH;
- IPv6 либо настраивается теми же правилами, либо осознанно отключается;
- синхронизация времени включена;
- ненужные службы остановлены и отключены;
- AppArmor остается включенным;
- доступ в группу `docker` выдается минимальному числу администраторов: член
  этой группы практически равен root;
- изменения системной конфигурации и доступ администраторов журналируются.

### 8.2. Fail2ban

Fail2ban устанавливается как дополнительный слой защиты:

- jail для SSH;
- jail для повторяющихся ошибок аутентификации reverse proxy/API;
- постепенное увеличение срока блокировки для повторных нарушителей;
- allowlist только для подтвержденных административных IP;
- уведомление о необычно большом количестве блокировок.

Fail2ban не заменяет запрет паролей, rate limiting приложения, MFA и firewall.

## 9. TLS, reverse proxy и HTTP-защита

Рекомендуемый proxy для первого сервера — Caddy из-за автоматической выдачи и
продления сертификатов. Nginx + Certbot допустим, если команда лучше умеет его
эксплуатировать.

Обязательные настройки:

- только TLS 1.2/1.3;
- автоматическое обновление сертификата и мониторинг срока действия;
- redirect HTTP на HTTPS;
- HSTS включается после успешной проверки домена и всех поддоменов; preload не
  включается без отдельного решения;
- `X-Content-Type-Options: nosniff`;
- строгая `Content-Security-Policy`, сначала в report-only режиме;
- `Referrer-Policy` и `Permissions-Policy`;
- запрет встраивания интерфейса чужим сайтом через CSP `frame-ancestors`;
- ограничения размера request body и времени выполнения;
- rate limiting для login, register, refresh, password reset, приглашений и
  загрузки файлов;
- точный production `CORS_ORIGIN`, без wildcard и отражения произвольного
  Origin;
- скрытие лишних version headers;
- access log не содержит Authorization, cookie, тела запросов и ПДн.

## 10. Усиленная защита персональных данных

### 10.1. Минимизация и классификация

До запуска создается реестр данных:

- какие поля являются ПДн;
- где они хранятся и в каких backup присутствуют;
- кто и на каком основании имеет доступ;
- срок хранения и событие удаления;
- какие данные попадают в документы, письма, журналы и аналитику;
- какие внешние лица и организации имеют технический доступ.

Не собирать данные «на будущее». Письма и push-уведомления не должны содержать
паспортные данные, полные реквизиты документов или секретные ссылки без
необходимости.

### 10.2. Шифрование

- весь внешний трафик — только HTTPS;
- поля `LeasePartyInfo` продолжают использовать AES-256-GCM;
- документы, сканы, чеки и uploads требуют шифрования на диске/томе либо
  application-level envelope encryption до допуска реальных пользователей;
- PostgreSQL volume и backup шифруются на уровне доступного диска/хранилища;
- каждый backup шифруется до отправки на удаленную площадку;
- ключи шифрования не хранятся в Git, Docker image, общем Compose-файле или
  рядом с зашифрованным backup;
- ключ `ENCRYPTION_KEY` имеет минимум две защищенные копии вне сервера;
- потеря этого ключа делает соответствующие данные невосстановимыми, поэтому
  его backup и тест восстановления входят в обязательную процедуру;
- ротация ключей проектируется с версией ключа в ciphertext metadata, а не
  заменой переменной без перешифрования существующих данных.

Полное шифрование диска VPS само по себе не защищает данные от атакующего,
который получил root на работающем сервере. Оно дополняет, но не заменяет
field-level encryption, разграничение доступа и аудит.

### 10.3. Секреты

Production-секреты размещаются вне репозитория, например в root-owned
`/etc/softrent/` с правами `0600`, и монтируются только тем процессам, которым
они нужны. Предпочтительно передавать секреты через файлы, а не аргументы
командной строки.

К секретам относятся:

- JWT access/refresh secrets;
- `ENCRYPTION_KEY` и последующие версии ключей;
- пароли PostgreSQL/Redis;
- SMTP/DKIM private key;
- deploy keys;
- ключи шифрования backup;
- учетные данные мониторинга.

Нужны реестр владельцев, дата создания, дата последней ротации и инструкция
экстренного отзыва каждого секрета. Секреты не печатаются в CI, application
logs, process list и диагностические архивы.

### 10.4. Аутентификация и сессии

Текущая реализация хранит access и refresh JWT в `localStorage`. Это следует
считать production security blocker: успешная XSS-атака сможет прочитать оба
токена и захватить длительную сессию.

До допуска реальных пользователей необходимо отдельным решением выбрать и
реализовать более безопасную схему, предпочтительно:

- refresh token в `HttpOnly; Secure; SameSite` cookie;
- access token короткоживущий и хранится только в памяти либо используется
  BFF/session cookie;
- CSRF-защита для cookie-authenticated state-changing запросов;
- rotation refresh token при каждом обновлении;
- обнаружение повторного использования старого refresh token и отзыв семейства
  сессий;
- экран активных сессий и возможность завершить все сессии;
- MFA обязательно для SuperAdmin и администраторов инфраструктуры;
- отдельная step-up authentication перед просмотром особо чувствительных ПДн;
- защита регистрации, входа, восстановления пароля и email verification от
  brute force, enumeration и массовой рассылки;
- пароль хранится только через Argon2 с актуальными параметрами;
- сообщения об ошибках не раскрывают существование email;
- после изменения email/пароля и при подозрительной активности пользователь
  получает уведомление.

### 10.5. Авторизация и административный доступ

- backend проверяет права на каждый объект, договор, документ и файл; UI не
  считается защитным слоем;
- тесты покрывают IDOR: подмена ID не должна раскрывать чужие данные;
- SuperAdmin не используется для повседневной работы;
- число SuperAdmin минимально, все их действия с ПДн журналируются;
- просмотр расшифрованных ПДн фиксирует кто, когда, чьи данные и по какой
  причине открыл; сами значения ПДн в audit log не записываются;
- destructive действия требуют повторного подтверждения и отдельного audit
  event;
- учетные записи сотрудников немедленно отзываются при прекращении доступа;
- прямой доступ к production DB разрешается только по аварийной процедуре и
  также журналируется.

### 10.6. Файлы и загрузки

- строгий allowlist MIME/type и расширений;
- проверка magic bytes, а не доверие заголовку клиента;
- ограничение размера, количества и частоты загрузок;
- случайные серверные имена, исходное имя хранится только как metadata;
- запрет path traversal и исполнения загруженных файлов;
- uploads лежат вне web root и выдаются только через авторизованный endpoint
  или короткоживущую подписанную ссылку;
- изображения декодируются/перекодируются безопасной библиотекой;
- документы проверяются антивирусом/сканером вредоносных файлов;
- SVG/HTML и другие активные форматы запрещены или отдаются только как
  attachment с безопасным Content-Type;
- удаление файла учитывает основное хранилище, кеши и сроки жизни backup.

## 11. PostgreSQL и Redis

- никакого публичного `5432`/`6379`;
- уникальные случайные production credentials;
- отдельная роль приложения с минимальными правами;
- по возможности отдельная роль мигратора: право менять схему не остается у
  постоянно работающего backend;
- подключения, ошибки аутентификации и медленные запросы мониторятся без
  логирования значений ПДн;
- регулярные minor updates;
- Redis, если включен, требует аутентификацию, внутреннюю сеть и запрет опасных
  административных команд; он не является источником долговременных данных;
- DB backup проверяется не наличием файла, а фактическим восстановлением в
  изолированную тестовую БД.

## 12. Postfix и доставляемость

Перед установкой Postfix у хостера проверяются:

- выделенный статический IPv4;
- разрешенный исходящий TCP/25;
- возможность установить PTR/rDNS `IP -> mail.softrent.ru`;
- отсутствие IP в основных blocklist;
- правила хостера для почтовых серверов.

Обязательная схема:

```text
backend -> внутренний SMTP -> Postfix -> OpenDKIM -> сервер получателя
```

Требования:

- Postfix принимает relay только от localhost/внутренней Docker-сети;
- публичный open relay исключен и проверяется внешним тестом;
- если входящая почта не нужна, SMTP listener не открывается всему интернету;
- SPF разрешает только фактический IP/relay;
- DKIM с отдельным private key и современным размером ключа;
- DMARC начинается с `p=none` и отчетов, после наблюдения усиливается;
- корректные `A`, `MX`/return-path и PTR согласованы;
- hostname, HELO и PTR не противоречат друг другу;
- включены TLS, ограничения скорости и размера очереди;
- email templates не содержат лишние ПДн;
- очередь, bounce, deferred mail и жалобы мониторятся;
- новый IP прогревается постепенно;
- предусмотрен переход на smart-host/relay без изменения application API,
  если самостоятельная доставляемость неудовлетворительна.

Postfix лучше держать отдельным host service для первого VPS. Это упрощает
работу с портом 25, очередью, OpenDKIM и системными журналами. Backend общается
с ним по закрытому интерфейсу.

## 13. Резервное копирование и восстановление

Резервируется:

- PostgreSQL;
- uploads и документы;
- release metadata и проверенные конфигурации без секретов;
- зашифрованные секреты/ключи по отдельной процедуре;
- DKIM key и параметры DNS;
- audit logs, если они требуются для расследований.

Минимальная политика для MVP:

- ежедневный логический `pg_dump`;
- ежедневный инкрементальный или полный backup uploads;
- backup перед каждой миграцией;
- шифрование до отправки;
- минимум одна копия на независимой RU-площадке;
- ориентировочно 7 ежедневных, 4 недельных и 6 месячных копий, окончательные
  сроки согласуются с политикой хранения ПДн;
- контрольная сумма каждого архива;
- мониторинг пропуска backup;
- ежемесячное автоматизированное тестовое восстановление;
- ежеквартальное полное учение: чистый сервер -> БД -> uploads -> ключи ->
  запуск и smoke-тест;
- задокументированные RPO/RTO до запуска. Начальная цель для обсуждения:
  RPO не более 24 часов, RTO не более 8 часов.

Правило 3-2-1 используется с поправкой на локализацию ПДн: три копии, два
разных носителя/площадки, одна удаленная копия, но данные российских граждан не
переносятся на иностранную площадку без отдельной правовой оценки.

Backup считается существующим только после успешного теста восстановления.
Ключ расшифрования backup хранится отдельно от backup. Удаление ПДн из основной
системы учитывает срок жизни резервных копий и запрет повторного возврата
удаленных данных в рабочую систему при восстановлении старого backup.

## 14. Логи, аудит и мониторинг

### 14.1. Запрещено писать в application logs

- пароли и токены;
- Authorization/cookie headers;
- паспортные данные;
- полные банковские реквизиты;
- тела документов и загружаемых файлов;
- секреты и ключи;
- полные request/response body по умолчанию.

Email и IP в технических логах маскируются либо хранятся только при
обоснованной необходимости и с ограниченным сроком.

### 14.2. Что мониторить

- доступность frontend/API;
- `/api/health` и соединение с БД;
- CPU, RAM, load average, inode и свободное место;
- состояние и рестарты контейнеров;
- ошибки 5xx и аномальный рост 4xx;
- задержку запросов и медленные DB queries;
- ошибки login, password reset и rate-limit events;
- успешность и возраст последнего backup;
- срок TLS-сертификата;
- Postfix queue, bounce/deferred rate;
- fail2ban и firewall events;
- изменения административных учетных записей;
- необычный массовый просмотр/выгрузку ПДн.

Алерты должны уходить по каналу, независимому от самого SoftRent/Postfix, иначе
при падении сервера уведомление также не будет доставлено.

Audit log отделяется от обычного debug log, защищается от изменения и имеет
ограниченный круг читателей. Срок хранения логов определяется политикой, а не
принципом «хранить навсегда».

## 15. Реагирование на инциденты

До production назначаются ответственные и создается короткий runbook:

1. Зафиксировать время, признаки и затронутые системы.
2. Ограничить доступ или изолировать хост, не уничтожая доказательства.
3. Сохранить журналы и snapshot в соответствии с процедурой.
4. Отозвать deploy/JWT/DB/SMTP ключи, если они могли быть раскрыты.
5. Завершить подозрительные пользовательские сессии.
6. Определить категории и объем затронутых ПДн.
7. Привлечь ответственного за ПДн/юриста для оценки обязательных уведомлений и
   сроков по действующему законодательству.
8. Восстановить систему из известного чистого релиза и проверенного backup.
9. Устранить первопричину, провести postmortem без поиска виноватых.
10. Зафиксировать корректирующие меры и проверить, что они выполнены.

Не следует автоматически переустанавливать или очищать скомпрометированный
сервер до сохранения необходимых материалов для расследования.

## 16. Организационные меры и 152-ФЗ

До реальных пользователей технический контур должен быть дополнен как минимум:

- определением оператора ПДн и ответственного лица;
- утвержденной политикой обработки и защиты ПДн;
- актуальным согласием с версионированием и фиксацией принятой версии;
- проверкой необходимости и корректности уведомления Роскомнадзора;
- моделью угроз и требуемым уровнем защищенности информационной системы ПДн;
- перечнем лиц с доступом и обязательствами о конфиденциальности;
- регламентами выдачи/отзыва доступа, backup, удаления и реагирования;
- договорными условиями с хостером и другими обработчиками;
- подтверждением физического размещения основной БД, uploads, логов и backup;
- процедурой ответа субъекту ПДн, исправления и удаления данных;
- документированным сроком хранения, включая ранее принятое правило ретеншена
  `LeasePartyInfo` через 3 года после завершения договора;
- запретом включения реальных ПДн в dev/test/staging и диагностические дампы.

Сам факт размещения сервера в России не означает автоматического выполнения
всех требований 152-ФЗ.

## 17. Security gate перед реальными пользователями

Запуск с реальными ПДн запрещен, пока не выполнены все критичные пункты:

- [ ] Подтвержден российский хостинг основной БД, uploads, логов и backup.
- [ ] Подготовлены production Dockerfile и отдельный `compose.prod.yml`.
- [ ] PostgreSQL/Redis/application ports недоступны из интернета.
- [ ] Настроены SSH keys, firewall, fail2ban и security updates.
- [ ] Реализован CI/CD с immutable SHA-тегами и ручным approval production.
- [ ] Реализованы healthcheck, smoke-test и безопасный deploy lock.
- [ ] Все production-миграции используют `prisma migrate deploy` и проверены
      на копии production-like БД.
- [ ] JWT больше не хранит длительный refresh token в `localStorage`.
- [ ] Для SuperAdmin включены MFA, audit и ограниченный административный путь.
- [ ] Rate limiting покрывает auth, invitations, notifications и uploads.
- [ ] Проведен IDOR/RBAC security test всех endpoints с договорами и файлами.
- [ ] CORS, CSP, TLS и security headers настроены и протестированы.
- [ ] Uploads защищены авторизацией, type/size validation и malware scanning.
- [ ] ПДн отсутствуют в application/proxy/CI logs.
- [ ] `ENCRYPTION_KEY` и backup keys имеют отдельные защищенные копии.
- [ ] PostgreSQL и uploads backup зашифрован и ушел на независимую RU-площадку.
- [ ] Выполнено полное тестовое восстановление на чистом окружении.
- [ ] Проверены outbound TCP/25, PTR, SPF, DKIM и DMARC.
- [ ] Postfix проверен на отсутствие open relay; очередь и bounce мониторятся.
- [ ] Настроены внешние health/backup/security alerts.
- [ ] Есть incident response runbook и контакты ответственных.
- [ ] Готовы и проверены юридические/организационные документы по ПДн.

## 18. Рекомендуемый порядок реализации

1. Подготовить ADR-0031 и этот документ как источник требований.
2. Создать production Dockerfile и Compose с внутренними сетями/volume.
3. Добавить `/api/health`, контейнерные healthcheck и smoke-test.
4. Добавить production-скрипт Prisma migration.
5. Реализовать ручные `deploy.sh` и `rollback.sh` с SHA релиза.
6. Реализовать backup/restore и выполнить первое восстановление.
7. Установить и усилить Ubuntu/Docker/SSH/firewall/fail2ban.
8. Поднять reverse proxy и HTTPS.
9. Устранить application security blockers: localStorage JWT, rate limits,
   SuperAdmin MFA/audit, uploads, CSP и IDOR tests.
10. Подключить GitHub Actions и production approval.
11. Настроить Postfix/OpenDKIM/DNS и проверить доставляемость.
12. Настроить мониторинг и независимые алерты.
13. Провести security review, restore drill и incident tabletop exercise.
14. Только затем допускать ограниченную группу реальных пользователей.

## 19. Критерий готовности инфраструктуры

Инфраструктура считается готовой не тогда, когда `docker compose up` завершился
без ошибки, а когда команда способна:

- воспроизводимо развернуть конкретный Git SHA на чистом сервере;
- доказать, какие образы и миграции работают в production;
- безопасно обновить и откатить приложение;
- восстановить БД, uploads и ключи после полной потери сервера;
- обнаружить недоступность, переполнение диска, сбой backup и аномальный доступ;
- показать, кто и когда обращался к расшифрованным ПДн;
- выполнить процедуру реагирования на компрометацию.
