# Архитектура

> Статус: стек и ключевые технические решения приняты (ADR-0003–0009,
> 0011, 0012 — см. `docs/adr/README.md`). Модель данных ниже —
> актуальное состояние, не черновик для обсуждения; менять — только
> через новый ADR, который явно отменяет старый. Остаются открытыми
> только хостинг/152-ФЗ и юридический текст договора/оферта (сознательно,
> см. `docs/READINESS_AUDIT.md`) — они не блокируют разработку на
> localhost.

## Ключевые сущности (модель данных, черновик)

- **User** — пользователь. Роль **не** глобальное поле профиля (в
  отличие от прототипа клиента, где было одно поле `status` на
  пользователя) — определяется по каждой связи: `ownerId` на
  Property/Lease даёт роль landlord для этого объекта, `tenantId` на
  Lease — роль tenant для этого договора. Один и тот же User может быть
  landlord по одному объекту и tenant по другому одновременно
  (подтверждено клиентом, 2026-07-20). Отдельно — **SuperAdmin**:
  системная роль (сотрудник сервиса, не landlord/tenant), единственная
  с доступом на просмотр «сырых» ПДн (паспортные данные арендатора) и
  правом удаления документов/сообщений — ни landlord, ни tenant этого
  не могут (подтверждено клиентом, 2026-07-21).
- **Property** — объект недвижимости (адрес, описание, владелец, фото,
  часовой пояс `timezone`, IANA-имя, по умолчанию `Europe/Moscow` —
  нужен для корректной границы расчётного периода по регионам РФ, см.
  `docs/MVP_SCOPE.md`, модуль платежей).
- **Lease** — договор аренды: связывает Property, landlord и **ровно
  одного** tenant (без со-арендаторов на один договор в MVP,
  подтверждено клиентом 2026-07-21), срок, условия, статус
  (черновик/отправлен/подписан). На Property в любой момент времени —
  **не более одного активного Lease** (посуточная/параллельная сдача не
  поддерживается). Юридический текст — либо генерируется по шаблону
  внутри сервиса, либо альтернативно загружается готовый файл; в обоих
  случаях «заключение» фиксируется явным подтверждением обеих сторон (см.
  `LeaseDocument`). Персональные данные сторон (ФИО, паспорт, дата
  рождения, адрес регистрации) сервисом **не собираются и не хранятся**
  ни в одном виде — см. следующий пункт и ADR-0017.
- **TenantInfo** (паспортные данные арендатора) — **исключено из MVP
  (2026-07-23)** по решению клиента: хранение ПДн убрано, сущность и
  шифрование удалены. **Расширено (2026-08-19, ADR-0017):** ФИО сторон
  тоже больше не подставляется в договор — раньше считалось вне зоны
  `TenantInfo` и продолжало браться из регистрации. Теперь все
  персональные поля в тексте договора (ФИО, паспорт, адрес регистрации,
  телефон, кадастровый номер) остаются прочерками, заполняются на
  бумаге — сервис их не собирает и не хранит вообще, чтобы не заходить в
  периметр 152-ФЗ.
- **Lease** дополнительно — обеспечительный платёж (`depositAmount`,
  по умолчанию 0, не обязателен) и отдельно поля возврата при
  расторжении (`depositReturnAmount`, кто решил — всегда landlord
  единолично, не требует двустороннего подтверждения в отличие от сумм
  по обычным заявкам). Задаток **не смешивается** с `Bill`/коммуналкой —
  отдельный трек, не строка счёта.
- **Invitation** — приглашение landlord → tenant на конкретный Property
  со статусом (pending/accepted/declined); механизм, которым стороны
  находят друг друга в системе (отвечает на открытый вопрос 2.4 в
  `docs/PRODUCT_QUESTIONS.md`).
- **LeaseDocument** — текст договора: либо сгенерирован по шаблону
  внутри сервиса, либо загружен готовым файлом как альтернатива
  (подтверждено клиентом 2026-07-21) + версии. «Заключён» (решено
  2026-07-22) = обе стороны загрузили скан документа со своей
  физической подписью (подписывается вне сервиса) — это основной
  юридический факт, не клик «подтверждаю» сам по себе. Сервис хранит
  сканы + отметку «подтверждаю» от каждой стороны как техническое
  событие. Снимает вопрос про уровень e-signature — используется
  обычная письменная форма (бумага + скан).
  **Реализация (2026-07-21):** сканы с подписью реализованы отдельной
  сущностью `LeaseSignedScan` (по одной на сторону, активируют договор
  при наличии обеих). **Текст договора (`LeaseDocument`, 2026-07-22):**
  генерируется из Handlebars-шаблона РФ (исходник —
  `dogovor_arendy.docx`) как HTML, версионируется; персональные данные
  сторон (ФИО, паспорт, адрес, телефон, кадастровый номер) — прочерки для
  заполнения от руки, сервис их не собирает (ADR-0017). PDF-рендер
  отложен (см. `docs/CHANGELOG.md`).
- **Message** — сообщение в переписке, привязанной к Lease, с флагом
  "официальное сообщение", вложениями (фото/файлы), редактируемое
  отправителем. Удаление — недоступно ни landlord, ни tenant, только
  `SuperAdmin` (сохраняет доверие к истории как к «официальной»).
- **MaintenanceRequest** — заявка/тикет: категория, статус, описание,
  фото, привязка к Lease. Обычные заявки (ремонт и т.п.) создаёт
  **только tenant**; landlord заявки не создаёт, только обрабатывает.
  Может иметь согласованную денежную сумму урегулирования
  (`agreedAmount`, кто платит — tenant/owner/пополам) — требует
  подтверждения **обеих** сторон (не считается согласованной по вводу
  одной стороны); после двустороннего подтверждения сумма становится
  строкой (`BillLineItem`) в текущем открытом черновике `Bill` за
  период, в котором согласовали, а не в следующем.

  Отдельная категория `termination` (расторжение договора) — **правило
  пересмотрено 2026-07-21**, отличается от остальных заявок: создать
  тикет может **любая сторона** (в т.ч. landlord, как исключение из
  правила «только tenant создаёт»), включая tenant, который сам хочет
  съехать — это его способ формально уведомить. Но **финализирует
  (исполняет) расторжение только landlord** — подтверждение tenant не
  требуется, это не двустороннее согласование, а решение владельца
  (даже если тикет создал сам tenant). Минимальный срок уведомления — 30
  дней до даты расторжения (`requestedTerminationDate`); при
  финализации landlord может задать кастомную границу периода
  (`periodEndOverride` на Bill/Lease) вместо стандартной даты оплаты —
  это и даёт пропорциональный расчёт за неполный период.
- **Service** — услуга каталога, привязана к Property (не к Lease, чтобы
  переживать смену арендатора): название, стоимость, тип
  (`monthly`/`one_time`), описание. Ежемесячные — автоматически в каждый
  новый период; разовые — добавляются в конкретный период вручную. См.
  `docs/MVP_SCOPE.md`, модуль платежей (обновлено ТЗ клиента, 2026-07-20).
- **Bill** — счёт по Lease за расчётный период: настраиваемый набор
  статей (аренда, коммуналка, услуги из каталога, урегулирования по
  заявкам, произвольные). Проходит два состояния — **черновик**
  (создаётся автоматически в начале периода, обновляется по ходу
  месяца) → **финал** (фиксируется автоматически при смене периода или
  вручную по кнопке, доступной обеим сторонам); у финального — статус
  из трёх значений: **ожидается** → **оплата заявлена** (арендатор
  нажал «Я оплатил», ждём подтверждения) → **оплачен** (собственник
  нажал «Оплата получена» — только это финализирует; ADR-0012,
  номинальный флоу без реального эквайринга). Ровно 3 значения статуса
  хранятся в БД — **«просрочен» не отдельное значение статуса**, а
  вычисляемый флаг для отображения (`dueDate` прошла И статус ∈
  {ожидается, оплата заявлена}) — используется в UI/уведомлениях, не
  меняет хранимый статус. Период счёта — от 12:00
  дня оплаты до 11:59 следующего дня оплаты. **Не финализируется
  автоматически**, пока по объекту есть неподанные обязательные
  показания счётчиков — остаётся в состоянии черновика/нерассчитанного,
  обеим сторонам уходит алерт вместо тихого закрытия без коммуналки
  (см. `docs/MVP_SCOPE.md`, «Напоминания по периоду»). Пеня начисляется
  за просрочку оплаты (% от суммы счёта за день, ставка — поле на
  Lease, задаётся собственником при создании договора) и **продолжает
  начисляться даже в статусе «оплата заявлена»** — останавливается
  только по подтверждению собственника, клик арендатора сам по себе не
  останавливает пеню (ADR-0012, намеренно асимметричная модель
  доверия); просрочка подачи показаний — без денежного штрафа, только
  напоминания/эскалация. Задел под будущий эквайринг (ADR-0011, без
  реализации в MVP): `paymentLink`/`qrPayload` (nullable — ссылка/QR на
  оплату, заполняется, когда в Phase 2 подключится провайдер СБП; в
  MVP всегда пусто, оплата подтверждается вручную обеими сторонами).
  **Прощение пени (2026-07-22):** landlord может простить начисленную
  пеню — одностороннее действие, подтверждения tenant не требует (в
  отличие от согласования суммы по `MaintenanceRequest` — там речь о
  сумме, которую tenant должен заплатить, здесь landlord отказывается
  от суммы в свою пользу). Поля: `penaltyWaived` (boolean, по умолчанию
  false), `penaltyWaivedAmount` (nullable — сумма пени на момент
  прощения, фиксируется для истории, не пересчитывается задним числом),
  `penaltyWaivedAt` (nullable). Доступно на любом Bill с накопленной/
  накапливающейся пеней, пока счёт не в статусе «оплачен»; действие
  необратимо в MVP (отменить прощение нельзя). Пока `penaltyWaived =
  true` — пеня не накапливается дальше и не входит в сумму к оплате;
  счёт показывает зафиксированную сумму как прощённую (не скрывает
  факт, что просрочка была), видно обеим сторонам.
- **BillLineItem** — отдельная статья счёта (тип, сумма, откуда взята —
  вручную / из Service / расчёт по показаниям / согласованная сумма из
  MaintenanceRequest / OCR квитанции).
- **Meter** — счётчик, привязан к Property; тип (электричество, вода,
  газ, отопление) выбирается пользователем из списка, плюс
  пользовательское название (`name`) — на объекте может быть несколько
  счётчиков одного типа (например, ГВС и ХВС раздельно), название
  нужно, чтобы их различать в интерфейсе. Тариф — на счётчике.
  `serialNumber` (опционально) — для сверки с показаниями/поверкой.
  `isActive` (по умолчанию true) — счётчик можно вывести из эксплуатации
  без удаления истории; отключённый счётчик не принимает новые показания.
  `initialReading` — значение на момент постановки счётчика на учёт,
  неизменяемое, задаётся один раз при создании; служит базой для расчёта
  расхода первого показания вместо `0` (ADR-0014 — до этого решения расход
  первого показания считался от нуля, что завышало начисление, если
  счётчик добавлялся уже с накопленным значением). Средний расход по
  счётчику — вычисляемая статистика, отображается в карточке Property
  (см. `docs/MVP_SCOPE.md`, модуль объектов). `calibrationDueDate`
  (опционально) — дата очередной метрологической поверки прибора,
  чисто информационная (ADR-0015), подача показаний по ней не
  блокируется. Список счётчиков доступен и на карточке объекта
  (`properties/:id`, landlord-only — там же создание/редактирование),
  и на вкладке «Показания» хаба аренды (`leases/:id/meters`,
  landlord/tenant — только просмотр + подача, ADR-0015); во втором
  случае к каждому счётчику добавляется вычисляемый
  `currentPeriodSubmitted` — подано ли по нему показание в текущем
  расчётном периоде договора (`computePeriod(now, lease.paymentDay)`).
- **MeterReading** — показание счётчика: значение, дата, фото
  (обязательно, не опционально), значение из OCR-распознавания фото +
  подтверждённое/поправленное пользователем значение, кто ввёл.
  Валидация: новое значение ≥ предыдущего (расход = новое − предыдущее,
  где «предыдущее» — последнее показание, а если показаний ещё не было —
  `Meter.initialReading`, ADR-0014); мягкое предупреждение без блокировки,
  если расход превышает средний по счётчику более чем в 10 раз.
- **Payment** — платёж/подтверждение оплаты по Bill: сумма, дата,
  статус (в MVP — фиксация вручную, без эквайринга). Задел под будущий
  эквайринг (ADR-0011, без реализации в MVP): `method` (enum `manual`
  по умолчанию | `sbp` | …), `providerTransactionId` (nullable — id
  операции у провайдера, для сверки/идемпотентности при подключении
  СБП в Phase 2).
- **Document** — файл (акт, чек, фото состояния объекта), привязан к
  Lease; включает результат OCR-распознавания для квитанций (сырые
  распознанные поля + связь с Bill/BillLineItem, если применимо).
  Удаление — только `SuperAdmin` (как и для `Message`). После окончания
  Lease доступ к документам/истории сохраняется только у landlord,
  бывший tenant доступ теряет.
- **Notification** — уведомление пользователю о событии.
- **Subscription/Plan, Referral** (не в MVP, зарезервировано в модели) —
  монетизация сервиса для landlord: подписка + вероятная реферальная
  программа (подтверждено клиентом 2026-07-21). Не реализуется в MVP,
  но модель данных User/Property не должна требовать переделки, когда
  это добавится — см. `docs/MVP_SCOPE.md`, раздел 8.

Это черновик для первого прохода по ER-диаграмме — уточняется в процессе
обсуждения, финализируется `architect` перед началом реализации Phase 1.

| Слой | Вариант |
|---|---|
| Frontend | React / Next.js |
| Backend | **NestJS (Node.js/TypeScript)** — ADR-0004 |
| Структура | **Модульный монолит**, один деплойный артефакт — ADR-0005 |
| БД | PostgreSQL |
| Файлы/документы | Интерфейс `StorageProvider`, дев/тест-реализация — локальная ФС; прод-провайдер и хостинг — отдельно, не сейчас (см. `docs/READINESS_AUDIT.md`) — ADR-0007 |
| OCR показаний счётчика | **Tesseract** (self-hosted, без внешних вызовов) — ADR-0008 |

| Рендер договора | Шаблонизатор (Handlebars/аналог) + HTML-to-PDF (например, Puppeteer) на том же Node-рантайме — следствие ADR-0004 |
| Уведомления | Интерфейс `NotificationChannel` (email/SMS); дев/тест — локальная заглушка (консоль/файл); прод-провайдер — отдельно, вместе с хостингом |
| Чат (realtime) | Не обязателен в MVP — обновление по запросу + email-уведомление; WebSocket — кандидат Phase 2+ — ADR-0009 |
| Аутентификация | **Email + пароль, собственный JWT** (access+refresh); OAuth — Phase 2+ — ADR-0006 |
| Хостинг | Сознательно не решено — тесты на localhost; провайдер и вопрос локализации ПДн (152-ФЗ) закрываются отдельно, см. `docs/READINESS_AUDIT.md` |

См. `docs/adr/0003-stack-choice.md` и `docs/adr/0004-...`–`0009-...`.
Рассматривался и отклонён вариант
из клиентского прототипа-наброска (репозиторий
`electricity_counter_master2`, обзор 2026-07-20): Flutter (

## Компоненты системы (высокоуровнево)

1. **Auth & Users** — регистрация, роли, профили, онбординг.
2. **Properties & Leases** — управление объектами и договорами, генерация
   текста договора по шаблону, e-signature/подтверждение по коду.
3. **Billing & Utilities** — счета с настраиваемым составом статей,
   счётчики и показания, расчёт по тарифу, фиксация оплаты вручную
   (MVP). Переход периодов/финализация черновика — идемпотентный
   планировщик на бэкенде (`@nestjs/schedule` + BullMQ/Redis, ADR-0004),
   пени вычисляются лениво по времени сервера; детали —
   `docs/MVP_SCOPE.md`, модуль платежей, раздел «Источник времени и
   планировщик». Точка расширения под будущий эквайринг и автоматический
   импорт показаний/тарифов (Phase 2+).
4. **OCR** — два независимых применения через общий интерфейс
   `MeterOcrProvider`: (а) распознавание показаний счётчика с фото, с
   подтверждением пользователем — **в MVP**, движок — Tesseract,
   self-hosted, без внешних вызовов (ADR-0008); (б) распознавание
   квитанций — отдельный сервис/пайплайн, кандидат на Phase 2, движок
   решается отдельно (не обязательно тот же Tesseract — документ
   сложнее одной цифры).
5. **Messaging** — чат, привязанный к Lease, с флагом официальных
   сообщений. Без realtime-транспорта в MVP — обновление по запросу +
   email-уведомление о новом сообщении (ADR-0009); WebSocket — Phase 2+.
6. **Maintenance** — заявки на обслуживание и их жизненный цикл.
7. **Documents** — хранение и доступ к файлам через интерфейс
   `StorageProvider` (ADR-0007; дев/тест — локальная ФС, прод-провайдер
   и хостинг — отдельно), включая результаты OCR.
8. **Notifications** — интерфейс `NotificationChannel` (email в MVP,
   SMS/мессенджер — по возможности); дев/тест-реализация — локальная
   заглушка (консоль/файл), без внешнего провайдера; push/websocket —
   позже, вместе с решением по realtime (см. п.5). Включает уведомление
   собственнику «проверьте, что оплата пришла» при клике арендатора «Я
   оплатил» (ADR-0012) — в дополнение к уже существующему каскаду
   напоминаний по показаниям/оплате (`docs/MVP_SCOPE.md`).
9. **Analytics** — отчёты по доходам/просрочкам/срокам договоров.

## Ключевой риск: интеграция со сбытовыми компаниями (счётчики/тарифы)

Бриф CEO предполагает автоматическое получение показаний счётчика и
тарифов по API сбытовой компании по номеру счётчика. Это **не решённая
техническая задача**, а открытый риск:

- в РФ нет единого публичного API "по номеру счётчика" — сбыт
  организован по регионам, у каждой РСО (ресурсоснабжающей организации)
  свой ЛК/API или его отсутствие;
- ГИС ЖКХ предоставляет часть данных, но обычно через официальную
  интеграцию/соглашение, а не анонимный запрос по номеру счётчика;
- реалистичный путь для MVP — **ручной ввод показаний арендатором** (+
  фото для подтверждения), а автоматическую интеграцию делать пилотом
  на одном регионе/провайдере в Phase 2, после отдельного технического
  и юридического исследования (`architect` должен провести это
  исследование и оформить ADR с результатом до включения задачи в
  спринт).

Модель данных (`Meter`, `MeterReading`) спроектирована так, чтобы не
блокировать переход от ручного ввода к автоматическому импорту позже —
источник показания (`manual` / `api:<provider>`) хранится как поле, а
не как структурное решение, которое пришлось бы переделывать.

## Открытые архитектурные вопросы

Все пункты, закрытые аудитом 2026-07-22 (кроме хостинга и юридической
части — см. ниже), вынесены в историю (CHANGELOG/ADR), здесь остаётся
только реально открытое:

- **Хостинг и физическое размещение данных (152-ФЗ)** — сознательно не
  решается сейчас. Тесты и разработка идут на localhost; провайдер
  прод-хостинга, включая требование о размещении БД с ПДн граждан РФ
  на территории РФ, решается отдельно, до реального запуска (не до
  начала кода). См. `docs/READINESS_AUDIT.md`.
- **Конкретный провайдер файлового хранилища и email/SMS для прод** —
  привязаны к решению по хостингу выше; интерфейсы (`StorageProvider`,
  `NotificationChannel`) и дев-реализации уже есть (ADR-0007), это не
  блокирует Phase 1.
- OCR квитанций (Phase 2, отдельно от OCR показаний счётчика) — движок
  и формат полей решаются позже, ближе к Phase 2.
