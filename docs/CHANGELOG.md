## 2026-07-23 (защита — нельзя пригласить самого себя)

### Изменено

- `LeasesService.send` отклоняет приглашение, если `invitedEmail` равен

## 2026-07-23 (исправление — отправка сообщений в чат)

### Исправлено

- Отправка любого сообщения в чат падала с `400 "isOfficial must be a
  boolean value"`: фронт шлёт multipart (из-за возможного вложения), где

  сообщение → 201, флаг сохраняется корректно.
- Найдено интеграционным прогоном (юнит-тесты не ловили — они шлют JSON,
  а не multipart).

## 2026-07-22 (первый E2E-прогон на реальной БД)

### Проверено — сквозной сценарий против PostgreSQL

Backend запущен (`node dist/main.js`, `:3000/api`) на реальной БД,
пройден полный путь через API (curl):

1. Регистрация landlord + tenant (JWT). ✓
2. Объект + счётчик + услуга. ✓
3. Договор-черновик → отправка → `Invitation`. ✓
4. Tenant принимает приглашение (привязка `tenantId`). ✓
5. Сканы обеих сторон → **авто-активация** договора (`active`). ✓
6. Генерация текста договора (v1, 7352 байта HTML, с ФИО и суммой). ✓
7. Показание счётчика (фото, OCR-заглушка) → коммунальная строка. ✓
8. Авто-черновик счёта: аренда 50000 + услуга 700 + свет 825 = **51525**. ✓
9. Финализация → `pending` → «Я оплатил» (`payment_claimed`) → «Оплата
   получена» (`paid`, `Payment` 51525). ✓
10. Уведомление landlord «Проверьте оплату» создано при claim. ✓
11. Отчёт собственника: доход 51525. ✓
12. **ПДн:** tenant пишет/читает свои; landlord — 403; в БД лежит
    зашифрованный блоб (не открытый текст). ✓

Замечен только нюанс тест-скрипта (строгий JSON-парсер curl-обвязки
спотыкался о переводы строк в HTML договора) — на сервер не влияет,
документ отдаётся корректно.

## 2026-07-22 (расторжение договора — termination)

### Добавлено — расторжение и пропорция последнего периода

- **TerminationRequest** (реализует «категорию `termination`» из
  `docs/ARCHITECTURE.md` отдельной сущностью — как split
  LeaseSignedScan/LeaseDocument): `leaseId`, `initiatedById`,
  `requestedTerminationDate`, `reason?`, `status`
  (`pending`|`finalized`|`cancelled`), `periodEndOverride?`.
- **Создать может любая сторона** (исключение из «только tenant» — в т.ч.
  landlord и сам tenant как способ уведомить). Минимальный срок
  уведомления — **30 дней** (`requestedTerminationDate ≥ now+30д`),
  иначе отказ.
- **Финализирует только landlord** (не двустороннее согласование, а
  решение владельца, per `docs/ARCHITECTURE.md`): договор →
  `LeaseStatus.terminated`, фиксируется `effectiveEndDate`, опционально
  `depositReturnAmount` (решает landlord единолично). Последний счёт
  пересчитывается **пропорционально** прожитым дням (`periodEndOverride`
  → доля аренды) и финализируется без создания следующего черновика.
- `LeaseStatus.terminated` добавлен; `Lease.effectiveEndDate`,
  `Lease.depositReturnAmount` — новые поля.

### Решения реализации (не ADR)

- Пропорция: строка аренды в последнем счёте = `rent × дней(period
  start→effectiveEnd) / дней(полный период)`; коммунальные/услуги/
  урегулирования остаются как есть. Достаточно для MVP.
- `BillingService.applyTermination(lease, effectiveEndDate)` — прората
  текущего черновика + финализация без next-draft (терминальное
  состояние). Переиспользует `finalizeBill` с флагом «без следующего
  периода».

## 2026-07-22 (TenantInfo с шифрованием + роль SuperAdmin)

### Добавлено — шифрование ПДн и системная роль

- `CryptoService` — field-level шифрование AES-256-GCM (ключ
  `ENCRYPTION_KEY` из окружения; формат хранения `base64(iv|tag|ct)`).
  Глобальный модуль, переиспользуется везде, где нужны ПДн.
- `SuperAdminGuard` — доступ к системным операциям по `User.isSuperAdmin`
  (роль сотрудника сервиса, не landlord/tenant; выдаётся вручную, не через
  публичную регистрацию).
- **TenantInfo** (`docs/ARCHITECTURE.md`): паспортные данные арендатора,
  один на договор. Хранится **зашифрованным блобом** (`dataEnc`).
  Арендатор вводит/читает своё; **SuperAdmin** читает любое (единственная
  роль с доступом к «сырым» ПДн); **landlord доступа к сырым ПДн не
  имеет** (152-ФЗ, `docs/MVP_SCOPE.md` «Роли и доступ»).
- Эндпоинты: `PUT /api/leases/:leaseId/tenant-info` (tenant),
  `GET /api/leases/:leaseId/tenant-info` (свой tenant или SuperAdmin).

### Решения реализации (не ADR)

- Генерируемый текст договора для landlord **по-прежнему с прочерками**
  для ПДн: TenantInfo не инжектится в видимый landlord'у документ (он не
  вправе читать сырые ПДн). Данные заполняются от руки перед подписанием
  либо доступны SuperAdmin.
- ПДн хранятся одним зашифрованным JSON-блобом (не по полю) — проще и
  достаточно для MVP; срок хранения/автоудаление (3 года после
  окончания) — с фоновой задачей ретеншена (отдельно).

- Эндпоинты: `POST /api/leases/:id/document` (landlord — новая версия),
  `GET /api/leases/:id/document` (стороны — последняя версия + контент),

## 2026-07-22 (планировщик расчётных периодов — ADR-0013)

### Решение

- **ADR-0013**: планировщик периодов в MVP — `@nestjs/schedule`
  (идемпотентный периодический скан), **BullMQ/Redis отложены**. Уточняет
  ADR-0004 (тот же фреймворк-планировщик, слой очереди — позже). Причина:
  пеня/просрочка считаются лениво, планировщику остаётся одна
  идемпотентная операция; Redis на localhost сейчас не нужен.

### Добавлено — авто-переход периодов

- `BillingService.runPeriodTransition(now)` — выбирает черновики счетов с
  наступившей границей периода (`stage=draft`, `periodEnd<=now`),
  финализирует их (→ `final`/`pending`) и создаёт черновик следующего
  периода. Черновик с непо́данными показаниями **пропускается** (гард), а
  не закрывается тихо — дозреет на следующем проходе (per
  `docs/MVP_SCOPE.md`, «Важное исключение»). Общая логика финализации
  вынесена в `finalizeBill`, переиспользуется ручной финализацией и
  планировщиком.
- `BillingScheduler` (`@Cron`, ежечасно) вызывает `runPeriodTransition`.
  `ScheduleModule.forRoot()` подключён в корне.
- Идемпотентность — по конструкции выборки, без семантики очереди
  (ADR-0013). Зависимость `@nestjs/schedule` добавлена.

### Отложено

- Полная привязка границ периода к `Property.timezone` (сейчас 12:00
  UTC) и BullMQ/Redis — см. ADR-0013. Алерт обеим сторонам при
  пропуске из-за показаний — на модуле Notifications.

## 2026-07-21 (модуль Maintenance — заявки)

### Добавлено — заявки на обслуживание

- **MaintenanceRequest** (`docs/ARCHITECTURE.md`): привязана к Lease.
  Обычную заявку создаёт **только tenant** (опционально с фото через
  `StorageProvider`); landlord ведёт статус `open`→`in_progress`→
  `resolved`. Поля: `category` (свободная строка — таксономия не
  зафиксирована), `description`, `photoStorageKey?`.
- **Двустороннее согласование суммы урегулирования**: любая сторона
  предлагает `settlementAmount` + `settlementPayer` (`tenant`|`owner`|
  `split`) — предложение подтверждает предложившая сторона, вторая должна
  подтвердить отдельно (`confirmedByTenant`/`confirmedByLandlord`). По
  двустороннему подтверждению доля арендатора становится строкой
  (`kind=maintenance`) в **текущем черновике счёта** (per
  `docs/ARCHITECTURE.md`, MaintenanceRequest), `settlementAppliedAt`
  фиксируется.

### Решения реализации (не ADR)

- **Доля арендатора в счёте**: `tenant` → полная сумма, `split` →
  половина, `owner` → 0 (строка не добавляется — арендатор ничего не
  должен). ARCHITECTURE говорит «сумма становится строкой» — трактуем как
  «payable-долю арендатора», т.к. счёт — это то, что арендатор платит
  собственнику.
- Повторное предложение суммы сбрасывает подтверждения обеих сторон;
  после применения (`settlementAppliedAt`) сумма не меняется.
- **Расторжение (`termination`) отложено** — отдельный под-флоу
  (уведомление 30 дней, `periodEndOverride`, финализирует landlord,
  пропорциональный расчёт неполного периода): затрагивает и жизненный
  цикл Lease, и биллинг, оформляется отдельным инкрементом. Чат
  (`Message`) — тоже отдельно.

## 2026-07-21 (модуль биллинга)

### Добавлено — счета, статьи, оплата, пени

- **Bill** (`docs/ARCHITECTURE.md`, Bill): счёт по Lease за период.
  `stage` (`draft`|`final`) + `paymentStatus` (`pending`|
  `payment_claimed`|`paid`, nullable до финализации) — так «ровно 3
  хранимых статуса» из ARCHITECTURE выражены явно. Поля периода
  (`periodStart`/`periodEnd`/`dueDate`), снимок ставки пени
  (`penaltyRatePercentPerDay` — фиксируется на счёте, не пересчитывается
  при смене в договоре), прощение пени (`penaltyWaived`/
  `penaltyWaivedAmount`/`penaltyWaivedAt`), задел под СБП
  (`paymentLink`/`qrPayload` nullable, всегда пусто в MVP — ADR-0011).
- **BillLineItem**: статья (`kind`, `source`, `amount`, `title`,
  `sourceRefId?`). Автостатьи — аренда и ежемесячные услуги при создании
  черновика; ручные — landlord'ом; коммунальные — из показаний
  (инкремент 2).
- **Payment**: запись подтверждения оплаты (`amount`, `method`
  `manual`|`sbp`, `providerTransactionId?` — задел ADR-0011).
- **Флоу оплаты (ADR-0012):** финализация `draft`→`final` (кнопка
  доступна обеим сторонам) → `pending`; tenant «Я оплатил» →
  `payment_claimed`; landlord «Оплата получена» → `paid` + `Payment`.
  Только клик landlord'а финализирует.
- **Пеня — ленивый расчёт** (чистая функция от суммы счёта, снимка
  ставки, `dueDate`, текущего времени): копится по дням просрочки,
  **продолжает копиться в `payment_claimed`**, останавливается только в
  `paid`. **Прощение пени** (landlord, одностороннее) замораживает сумму
  на момент прощения и останавливает накопление; необратимо.
  «Просрочен» — вычисляемый флаг (`dueDate` прошла И статус ∈
  {pending, payment_claimed}), не хранимый статус.

### Добавлено — показания счётчиков (OCR замокан)

- `MeterOcrProvider` (интерфейс) + **`MockMeterOcrProvider`** — реальный
  Tesseract (ADR-0008) подключается позже той же абстракцией.
- **MeterReading**: `value`/`confirmedValue`, `ocrValue`,
  `photoStorageKey` (фото обязательно, через `StorageProvider`),
  `readingDate`, `enteredById`. Валидация: новое ≥ предыдущего (жёстко);
  расход > 10× среднего по счётчику — **мягкое предупреждение** (флаг в
  ответе), без блокировки. Добавляет коммунальную строку
  (расход × тариф) в текущий черновик счёта.
- **Гард финализации**: счёт не финализируется, если по объекту есть
  счётчик без показания в текущем периоде (per `docs/MVP_SCOPE.md`,
  «Важное исключение»).

### Осознанные упрощения / отложено (флаг)

- **Планировщик (`@nestjs/schedule` + BullMQ/Redis) и полный таймзонный
  авто-переход периодов — НЕ реализованы в этом инкременте.** Пока
  только ручная финализация («Сформировать счёт», доступна обеим
  сторонам, per `docs/MVP_SCOPE.md`). Дизайн планировщика (ADR-0004)
  сохраняется, его подключение — отдельный инкремент. Пеня и «просрочка»
  считаются лениво по времени сервера, поэтому не зависят от наличия
  планировщика.
- **Будущие периоды вычисляются, а не пред-создаются** — отклонение от
  формулировки `docs/MVP_SCOPE.md` («график будущих периодов создаётся
  сразу при создании договора»). Причина: пред-создание неограниченного
  числа `Bill` до `endDate` — сомнительно инженерно; для экрана «График
  платежей» будущие периоды считаются чистой функцией от `paymentDay`.
  Хранятся только текущий черновик и прошлые финальные счета.
- **Черновик создаётся лениво** при первом обращении к биллингу
  активного договора (`ensureCurrentDraft`), а не хуком на активацию —
  чтобы не вводить связь leases→billing/событийную шину сейчас.
- Денежные вычисления в домене — на `number` с округлением до 2 знаков
  (достаточно для MVP; переход на Decimal-арифметику при необходимости).
- Уведомление landlord'у при «Я оплатил» и строки-урегулирования из
  Maintenance — **stub/отложены** (модули Notifications/Maintenance ещё
  не реализованы). Пропорциональный расчёт за неполный период при
  выезде — с модулем расторжения.

  зашифрованном виде, доступ только `SuperAdmin`
  (`docs/ARCHITECTURE.md`). Требует field-level шифрования — отдельный
  инкремент с участием роли security.
- **Генерация текста договора** (шаблон РФ / загрузка файла / PDF),
  **расторжение** (deposit return, `termination`) и **режим коммуналки**
  (fixed/по счётчикам) — последующие инкременты (биллинг/termination).
- Инвариант «один активный Lease на Property» на этапе создания черновика
  блокирует только при наличии `active`; более тонкие правила (несколько
  черновиков/sent) — при реализации активации.
